# Carregando dados

Os dados externos API é como qualquer coisa sem um conector entra em CRM AnalyticsUm extrato de armazém, um arquivo de fornecedores, as sessões da Academia e gastar.

## Três passos, em ordem.

::lesson-steps
---
items:
  - title: "Declare o trabalho."
    description: "Criar um registro descrevendo o que você está prestes a carregar: o nome do conjunto de dados, a operação - sobrescrever, adicionar, aumentar, excluir - e os metadados descrevendo os campos. Nada foi carregado ainda."
  - title: "Envie os dados em partes."
    description: "As fileiras sobem como partes numeradas ao invés de uma carga útil. Cada parte é um pedaço do arquivo, e a numeração é como a plataforma os remonta. Grandes cargas são muitas partes, pequenas são uma."
  - title: "Sinal completo."
    description: "Ajuste o status do trabalho para indicar que todas as partes foram enviadas. Só agora o processamento começa. Saltar esta é a falha que todos batem uma vez, e não produz nenhum erro - as partes simplesmente sentar lá e nenhum conjunto de dados aparece."
---
::

::warning{icon="i-lucide-flag"}
**O fracasso silencioso é esquecer o terceiro passo.** A declaração foi bem sucedida, todas as partes carregadas com sucesso, nada errado - e não há nenhum conjunto de dados. Um trabalho não assinado é indistinguível de um trabalho ainda em andamento. Quando uma carga "trabalhava mas não produzia nada", verifique o status do trabalho antes de qualquer outra coisa.
::

## O arquivo de metadados decide seus tipos de campo.

Os metadados enviados com a declaração dizem à plataforma qual é cada campo: seu nome, seu rótulo, e se é texto, numérico ou data, junto com formatos e precisão.

::note{icon="i-lucide-type"}
**Esta é a lição de carga CSV da seção de preparação de dados, em código.** Os mesmos três erros, com os mesmos custos, e agora eles estão em um arquivo que você controla em vez de um diálogo que você clicou através: uma data declarada como texto nunca pode ser tendência, uma identificação numérica declarada como uma medida será resumida por alguém eventualmente, e uma moeda com a escala errada é para fora por um fator de uma centena sem nada para marcar. A vantagem de fazê-lo aqui é que os metadados são código - ele é reviewable, diffable, e idêntico em cada corrida.
::

## Operações

::field-table
---
dataset: "load operations"
grain: "one row per operation"
fields:
  - name: "Overwrite"
    type: "replace everything"
    role: "key"
    note: "O mais simples e o padrão certo para um conjunto de dados moderado reconstruído da fonte toda noite. Também o mais caro como o volume cresce, porque você está enviando tudo para mudar uma fração."
  - name: "Append"
    type: "add rows"
    role: "measure"
    note: "Para acumular dados, eventos, e o padrão de instantâneo dos conjuntos de dados e da seção de modelagem, onde cada execução adiciona um novo período em vez de reafirmar toda a história."
  - name: "Upsert"
    type: "update or insert by key"
    role: "key"
    note: "A opção incremental, e depende inteiramente de uma chave verdadeiramente única. Uma chave que não é única silenciosamente funde fileiras que devem ser separadas, que aparece mais tarde como uma contagem muito baixa."
  - name: "Delete"
    type: "remove by key"
    role: "dimension"
    note: "Para registros que desapareceram na fonte. Sem ele, uma substituição é a única maneira de perder uma linha deletada, e um oleoduto só de apêndice mantém registros que a fonte não tem mais."
---
::

## Incremental não é automaticamente melhor.

::compare-cols
---
items:
  - title: "Substituição completa"
    subtitle: "Send everything"
    icon: "i-lucide-refresh-cw"
    pros:
      - "Self-correcting — a bad run is fixed by the next good one"
      - "No key required, no drift possible"
      - "Far easier to reason about at 2am"
    cons:
      - "Wasteful as the dataset grows"
      - "Longer run, larger API footprint"
    verdict: "Right until volume makes it wrong. Start here."
  - title: "Incremental upsert"
    subtitle: "Send what changed"
    icon: "i-lucide-git-pull-request"
    pros:
      - "Fast, small, cheap on API allowance"
      - "Necessary at large volumes"
    cons:
      - "Needs a reliable change marker and a genuinely unique key"
      - "Drifts silently when a change is missed — nothing errors, the dataset is just slightly wrong, forever"
      - "Needs periodic full reconciliation to catch that"
    verdict: "Adopt when volume demands it, with a reconciliation job."
---
::

::tip{icon="i-lucide-check-check"}
**O que você escolher, verifique a contagem da linha após a carga.** Leia os metadados do conjunto de dados e compare com o que enviou. São algumas linhas de código, funciona toda noite, e pega a carga parcial que seria descoberta por alguém olhando para um painel uma semana depois.
::

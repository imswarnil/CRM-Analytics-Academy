# Segurança de nível de linha e o predicado

compartilhamento de aplicativos decide *Quem pode abrir o painel?*. Segurança de linha decide *O que eles veem quando abre*. Eles são independentes, e você precisa dos dois.

## O predicado de segurança.

A **Predicação de segurança** é um filtro ligado ao próprio conjunto de dados, avaliado por visualizador, no momento da consulta. Cada consulta contra esse conjunto de dados - cada widget, cada lente, cada exportação - tem o predicado aplicado antes que qualquer outra coisa aconteça. Não pode ser contornado do painel, que é exatamente a propriedade que você quer.

A forma é uma comparação entre uma coluna no conjunto de dados e algo sobre o usuário atual:

::field-table
---
dataset: "common predicate shapes"
grain: "one row per pattern"
fields:
  - name: "Own records only"
    type: "'OwnerId' == \"$User.Id\""
    role: "key"
    note: "O mais simples e mais comum. Cada espectador vê as fileiras que possui. Requer que o ID do usuário do proprietário seja uma coluna no conjunto de dados, o que significa que deve ser sincronizado, e levado a cabo cada junção na receita."
  - name: "By a user attribute"
    type: "'Region' == \"$User.Region__c\""
    role: "dimension"
    note: "Combine uma coluna de dados com um campo no registro do usuário. Excelente quando a org já mantém esse campo sobre os usuários, e uma responsabilidade de manutenção quando não, um campo em branco significa que o espectador não vê nada."
  - name: "Role hierarchy"
    type: "'RolePath' contains \"$User.UserRoleId\""
    role: "dimension"
    note: "Um gerente vê suas próprias fileiras e todos abaixo delas. Precisa da hierarquia pré-computada no conjunto de dados por um nó achatado, porque um predicado não pode andar na hierarquia na hora da consulta."
  - name: "Everyone sees everything"
    type: "no predicate"
    role: "measure"
    note: "Uma escolha legítima para dados genuinamente não sensíveis, e deve ser uma decisão escrita em vez de uma omissão. \"Nós deliberadamente não restringimos isso\" e \"ninguém pensou sobre isso\" parece idêntico na configuração."
---
::

## O nó achatado, e por que ele existe

Uma hierarquia de papéis é uma árvore. Um predicado é uma comparação. Uma comparação não pode escalar uma árvore, então a árvore tem que ser achatada em algo comparável **Antes** Os dados são consultados na hora da receita.

::note{icon="i-lucide-git-branch"}
**O que o achatado produz.** Para cada papel, uma coluna contendo esse papel e todos os seus ancestrais, um caminho. O predicado então pergunta se o papel do espectador aparece em qualquer lugar no caminho da fila. O papel de um diretor regional aparece nos caminhos de cada representante abaixo deles, para que eles vejam essas fileiras; não aparece nos caminhos de uma região de irmãos, então não aparece. Toda a questão da hierarquia se torna uma comparação de cordas, por isso é rápido o suficiente para correr em cada consulta.
::

Esta é a razão concreta pela qual a segurança tem que ser projetada. **Antes** o modelo de dados: o predicado precisa de uma coluna, a coluna precisa de um nó de receita, e o nó precisa de campos que devem ser sincronizados. Decidir sobre a hierarquia depois que os painéis são construídos significa reconstruir a receita e cada conjunto de dados a jusante dela.

## O usuário de segurança.

Onde o predicado é uma regra que você escreve, **Compartilhar a herança** Deixa a própria organização decidir. **usuário de segurança** é a conta que avalia isso. Precisa de acesso aos campos de que a avaliação depende, e se não puder vê-los, a herança não pode ser calculada.

Trate-o como o usuário de integração: estreito, deliberado e documentado. Ambas são contas especiais cujo acesso é uma decisão de design ao invés de um pensamento posterior.

::warning{icon="i-lucide-lock"}
**Predica falha fechada, e esse é o padrão certo.** Um erro de digitação, uma coluna desaparecida ou um campo de usuário em branco produz um painel vazio ao invés de um vazamento. Então, quando alguém relata "o painel está em branco para toda a equipe", suspeite do predicado primeiro - e seja grato que quebrou nesta direção.
::

## A armadilha que pega todo mundo uma vez

Você adiciona um predicado, e seus painéis ficam vazios.

Nada está quebrado. O predicado é avaliado para *Você.* E seu usuário não o satisfaz. Você não possui nenhum dos registros, seu papel está fora dos caminhos, seu campo regional está em branco. Administradores não estão isentos por padrão.

::tip{icon="i-lucide-user-cog"}
**Planeje a isenção deliberadamente.** Ao invés de se conceder algo amplo em pânico. Uma condição nomeada no predicado, um papel, uma permissão, um atributo do usuário que a equipe de análise carrega, é explícita, revetível, e não entrega silenciosamente a mesma isenção à próxima pessoa que herda esse perfil.
::

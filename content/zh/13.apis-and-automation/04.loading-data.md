# 正在装入数据

外部数据 API 没有连接器的东西会变成什么样 CRM Analytics:仓库摘录,供应商文件,纳米利奥的网络会话和花费.

## 三个步骤,顺序

::lesson-steps
---
items:
  - title: "申报工作"
    description: "创建一个记录来描述您将要装入的内容:数据集名称,操作——覆盖,附加,上移,删除——以及描述字段的元数据. 还没有上传"
  - title: "以部分方式上传数据"
    description: "排成数组而不是一个有效载荷 每个部分都是文件的一个块,编号就是平台如何重新组装它们. 大型负载是许多部件;小型是一体的。"
  - title: "信号完成"
    description: "设定任务状态以显示所有部分已发送 。 现在才开始处理。 跳过这是每个人一次的失败,它不会产生任何错误——这些部分只是坐在那里,没有出现数据集。"
---
::

::warning{icon="i-lucide-flag"}
**无声的失败正在忘记第三步.** 声明成功,每个部分都成功上传,没有出错——也没有数据集. 一份没有标志的工作与一项仍在进行中的工作是分不开的。 当一个负载"工作但无所作为"时,先检查工作状况,然后再做其他事情.
::

## 元数据文件决定您的字段类型

随宣言一起发送的元数据告诉平台每个字段是什么:它的名称,它的标签,以及它是文本,数字还是日期——以及格式和精确度.

::note{icon="i-lucide-type"}
**这是CSV上载课程 从数据准备部分,代码。** 同样的三个错误,成本相同,现在它们被你控制的文件,而不是你点击过的对话框:一个被宣布为文本的日期永远不能被趋势化,一个被宣布为衡量标准的数字化的ID最终会被某个人汇总,一个被错误的尺度的货币被一个没有标记的百倍的系数输出出来. 这样做的好处是元数据是代码——在每个运行中它是可审查的,可传播的,也是相同的.
::

## 递增不会自动更好

::compare-cols
---
items:
  - title: "完全覆盖"
    subtitle: "Send everything"
    icon: "i-lucide-refresh-cw"
    pros:
      - "Self-correcting — a bad run is fixed by the next good one"
      - "No key required, no drift possible"
      - "Far easier to reason about at 2am"
    cons:
      - "Wasteful as the dataset grows"
      - "Longer run, larger API footprint"
    verdict: "Right until volume makes it wrong. Start here."
  - title: "递增升级"
    subtitle: "Send what changed"
    icon: "i-lucide-git-pull-request"
    pros:
      - "Fast, small, cheap on API allowance"
      - "Necessary at large volumes"
    cons:
      - "Needs a reliable change marker and a genuinely unique key"
      - "Drifts silently when a change is missed — nothing errors, the dataset is just slightly wrong, forever"
      - "Needs periodic full reconciliation to catch that"
    verdict: "Adopt when volume demands it, with a reconciliation job."
---
::

::tip{icon="i-lucide-check-check"}
**无论你选择哪一个,都验证负载后的行数.** 读取数据集的元数据,并与您发送的内容进行比较. 这是几行代码,它每天晚上运行, 它捕捉到部分载荷, 否则,有人会发现 一个星期后,

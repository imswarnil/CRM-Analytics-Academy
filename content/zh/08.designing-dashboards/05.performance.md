# 业绩

一个需要12秒的仪表板 就是人们停止打开仪表板 原因很少,而修补大多是结构性的而不是聪明的.

## 计数查询,而不是部件

每个部件都通过查询得到信息 。 几个部件可以共享一个——如果不能共享的话,一个带有十二个部件的屏幕会发出十二个查询。

::tip{icon="i-lucide-merge"}
**这是最大的杠杆,通常是免费的。** 标题编号、条形图和显示相同度量的表格频繁切除三种方式 *能够* 共享一个查询。 整合常常是十二秒和两秒的区别,它不会改变仪表板的外观或行为.
::

## 谷物贸易

3节说,一个数据集的谷物是一个决定。 这里就是你付钱的地方:

::compare-cols
---
items:
  - title: "细粒"
    subtitle: "Every row preserved"
    icon: "i-lucide-microscope"
    pros:
      - "Any question is answerable from it"
      - "One dataset serves many dashboards"
    cons:
      - "Every widget aggregates a lot of rows, on every load, for every viewer"
      - "Fan-out risk is handed to every designer who touches it"
    verdict: "Right for exploration, expensive for an exec board."
  - title: "预汇总"
    subtitle: "Summarised in the recipe"
    icon: "i-lucide-box"
    pros:
      - "Fast — the aggregation happened once, overnight"
      - "The definition is settled upstream, so nobody can compute it differently"
    cons:
      - "Questions below the chosen grain are no longer answerable"
      - "Another dataset to schedule and maintain"
    verdict: "Right for a dashboard many people open daily."
---
::

::note{icon="i-lucide-layers"}
**正常生产答案是两者兼而有之.** 一个精细的数据集供探索, 一个预先汇总的,在仪表盘后面 每个人都打开。 GTM工程部分的仓库是故意建造的:您所探索的表格并不总是执行董事会所读的表格.
::

## 其他原因,粗略顺序

::field-table
---
dataset: "what makes dashboards slow"
grain: "one row per cause"
fields:
  - name: "Too many distinct queries"
    type: "most common"
    role: "measure"
    note: "12个部件各自运行自己。 合并可以共享的内容,更改对用户来说是无形的,只是页面出现."
  - name: "Aggregating fine grain at query time"
    type: "common"
    role: "measure"
    note: "每个部件总和数百万行。 如果仪表板每天都被许多人打开,则在食谱中预先汇总."
  - name: "Very wide tables"
    type: "common"
    role: "dimension"
    note: "含有二十列和数百行的值表,查询速度缓慢,而且无法读取。 切为五列和十列,同时解决两个问题."
  - name: "Complex bindings"
    type: "occasional"
    role: "dimension"
    note: "链式绑定可以强制顺序而不是平行查询: 部件 C 等待 B, 它等待 A. Worth 检查当一个仪表板慢到不能与其部件计数匹配时是否值得检查 。"
  - name: "Row-level security evaluation"
    type: "structural"
    role: "key"
    note: "预告器,特别是分享遗产 在每个浏览器的查询中成本一定。 这是一个正确的成本,而不是缺陷——但这也是一个仪表板对一个拥有复杂访问权限的观众来说慢于你的原因."
---
::

## 如何实际测量它

::lesson-steps
---
items:
  - title: "装入它作为一个普通用户,而不是你自己"
    description: "您的管理员账户可能跳过安全评价, 即每个查询中真正的查看者付费 。 作为管理员的测试性能可以大大低估它."
  - title: "注意哪个部件最后到达"
    description: "他们随问而回,所以慢者宣布自己。 通常它是最宽的桌子和最优厚的图表。"
  - title: "计算不同的查询"
    description: "仪表盘的查询列表显示了它们. 如果在屏幕上询问的问题比真正不同的问题多,则需要加以合并。"
  - title: "在聪明之前修补结构"
    description: "合并查询,剪切表格列,必要时预汇总. 只有这样,才会考虑任何异国情调——如果答案需要聪明的话,仪表板可能做得太过分了."
---
::

::warning{icon="i-lucide-hourglass"}
**慢的仪表板会悄悄地失效** 没人会写"这需要11秒"的票 他们打开的更少,然后他们问你的号码, 然后他们保留自己的电子表格—— 电子表格与仪表板有分歧, 即一个北极狼最终会得到两个真理。 当有人抱怨时,仪表板已经丢失了.
::

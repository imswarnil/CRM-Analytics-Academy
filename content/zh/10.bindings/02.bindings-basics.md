# 约束

面对是自动的。 页:1 **绑定** 是故意的:它需要一个部件的状态——一个选择、结果、一个值——并将其输入另一个部件的查询、标题或可见度。

## 四个有用的模式

::field-table
---
dataset: "bindings worth using"
grain: "one row per pattern"
fields:
  - name: "Dynamic title"
    type: "start here"
    role: "key"
    note: "'Revenue — EMEA, Q3 FY26' 区域与季度来自目前的选择. 廉价的,低风险的,它修正了任何仪表板上最常见的误读:不知道目前过滤的是什么."
  - name: "Dependent filter"
    type: "common"
    role: "dimension"
    note: "选一个区域将代表名单缩小到该区域的代表。 真正优于四十个名字的清单,值得如此复杂."
  - name: "Query parameter"
    type: "powerful"
    role: "measure"
    note: "选择会改变一个查询量度,而不只是它过滤的量度——在ARR之间切换到同一个图表上进行交易. 一个中有两个部件,它将屏幕空间减半,需要比较。"
  - name: "Conditional display"
    type: "use sparingly"
    role: "dimension"
    note: "部件仅在相关时才会出现——风险表仅在有账户存在风险时才会显示。 优雅 最有可能迷惑下一位维护者 无法看到不存在的部件 。"
---
::

## 从动态标题开始

如果你用一个捆绑,使用这个。 一个在标题中说明自己过滤器的仪表板可以防止分析通信中最常见的单一错误:一个被过滤的视图的截图被读取为全图.

::tip{icon="i-lucide-camera"}
**假设每个仪表板将被截图并粘贴成没有上下文的信息.** 一个读作"Pipeline——只有EMEA,在Q3中创造"的标题可以幸存这段旅程完好无损. 标题读作"Pipeline"在周四之前成为别人争论中全公司的数字.
::

## 哪里出问题了

::warning{icon="i-lucide-network"}
**绑定是存储在部件配置中的逻辑 。** 它们不能一目了然地阅读,它们不会传播,而且它们也没有记录到下一个人会看到的地方。 一个有20个人的仪表板工作得漂亮,变得不可接触——继承者可以看到,改变事物会破坏事物,但不会是什么或为什么,所以他们在它旁边建造了一个新的仪表板。 如此一来,一头猩猩最后有四个输油管仪表板 和关于这个的争论是正确的。
::

实际限制在于可读性而不是数:

::compare-cols
---
items:
  - title: "健康使用"
    subtitle: "A handful, each obvious"
    icon: "i-lucide-check"

    verdict: "Split it into two dashboards instead."

::

## 值得通过的规则

::note{icon="i-lucide-file-text"}
**如果看屏幕看不清捆绑,请写下来** ——在仪表板的描述中,或者在项目说明中,在指标定义之外. 每一捆绑一条线:什么是食物,什么是原因。 这需要一分钟,这是团队拥有的仪表板和一个人拥有的仪表板之间的区别。
::

## 当束缚是错误的答案时

两个值得承认的案件:

- **你在重建一个度量衡** 如果约束存在以计算定义,则属于食谱中. 部件级定义漂移, 绑定比普通更难找到 SAQL 会的
- **你把两个观众挤到一个屏幕上** 用于销售和融资的重新配置的仪表板通常是两个穿战壕外套的仪表板. 两个屏幕,每个简单,击败一个聪明的屏幕——它们可以分享给不同的观众,协作部分显示这是比较容易治理的事情.

# 安全用户 & 行级安全

除了整合用户之外, CRM Analytics 第二特别账户: **安全用户**。 。 。 它有一份狭窄但重要的工作,而且——就像集成用户一样——你绝不能删除它. 这个教训解释了它的两个作用,并用它们来引入平台最强大的想法之一: **行级安全**。 。 。 。

## 安全用户的两个工作

安全保卫 用户存在是为了做两件事:

第二项工作是值得深刻理解的,因为它使排级安保工作发挥作用。

::note{icon="i-lucide-shield-alert"}
**不删除或关闭安全用户** 也一样。 如果它失去对用户字段的访问权限, 您的上游依赖, 行级安全可以无声中断, 而用户可能看到太多行—— 或者根本没有.
::

## 什么行级的安全实际上是

想象一下两个人在同一时刻打开了完全相同的仪表板. **页:1** 运行它,看看 **1 000行数**· ; **老师** 运行它,看看 **2 000行**。 。 。 。 仪表板没有变化, *谁* 是运行它。 这是 **行级安全**:平台根据每个用户的身份过滤数据集的行.

它背后的机制是 **安全前提** ——被评价数据集所附过滤规则. **查询时间** 对运行中的用户。 上游可以说"只显示记录所有者等于运行用户的行"或"只显示运行用户的区域的行"等话. 因为它运行在查询时间,同一个数据集自动为不同的人提供不同的切片服务.

::tip{icon="i-lucide-filter"}
每个查询都对安全上方进行新鲜评价,无论是谁进行的。 正因为如此,一个数据集能够安全地服务于一个只应查看其账户的代表和一个应查看整个区域的甚高频——而不建立单独的数据集。
::

## 保安处 用户进来

为了评估上游 CRM Analytics 必须读取关于 **运行中的用户** - 其用户身份、作用、区域、团队或任何其他领域 **用户对象**。 。 。 。 它读那些字段 **作为安全用户**。 。 。 正因为如此,安全用户需要访问用户对象:是账户查看"这个人是谁,他们的属性是什么?",所以上游可以相应过滤.

## 自定义用户字段获得cha

您可以在 **用户对象上的任何字段** ——标准字段如: `UserId` 和 `Role`,或者你自己的 **自定义 用户字段** (说,习惯) `Region__c` 或 `Team__c`) (中文(简体) ). 但有一个捕捉点 反映了整合用户:

::note{icon="i-lucide-triangle-alert"}
如果您的上游引用 **用户对象上的自定义字段**,则 **警卫 用户必须读取权限** 到那个领域。 错过此和上游无法读取该值, 行级安全不会正确过滤 。
::

## 两个特殊的用户,一个模式

注意这个课和最后一个课的对称性. 整合用户和安全用户都是系统账户,您必须保持生命力,而且双方都共享相同的自定义域: **标准字段自动工作,但自定义字段需要明确的读取权限。** 内化这个模式 和两大类设置错误消失。

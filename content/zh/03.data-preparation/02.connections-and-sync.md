# 连接和同步

两个阶段 感觉像管道 并决定每个仪表板上每个数字的电流

## 连接

页:1 **连接** 是证书加可达到的终点。 当地 Salesforce org 默认连接; 其它的都是一次配置, 然后引用 :

- **又一个 Salesforce 奥尔格** ——在经营不止一家的公司中常见.
- **仓库** ——雪花,大u,红调和类似.
- **对象存储和数据库** ——S3,以及直接的数据库连接.
- **页:1 CSV 上传** - 不是真正的联系,而是同一个目的地。

::note{icon="i-lucide-key"}
**代表证到期,这是整个管道中最友好的失败** - 跑步停了就这么说了 与许可问题相比,它默默地放下了一列. 当连接中断时,你立即发现, 这是值得赞赏的,当你调试 更安静的东西。
::

## 实际的同步效果

数据同步拉动 **选中对象** 和 **选定字段** 输入 CRM Analytics计划上是自己的店 食谱然后读取当地版本.

这有两个原因:

1. ** Speed速.** 加入五个对象的食谱,否则每运行一次将询问五次来源。
2. **礼乐.** 记录系统是服务于现场用户的制作CRM;分析工作不应该是每小时敲打它.

后果值得内在化: **有两个钟。** 同步有时间表,食谱有时间表. 仪表板上的数据和 *早些时候* 两者中,加之无论耗时多长。

## 依赖陷阱

::warning{icon="i-lucide-clock-alert"}
**在同步前预定好的食谱 将会成功运行, 根据昨天的数据,每晚,永远。** 没有错误。 监视器标签显示为绿色 。 仪表板显示的数字完全停留了一天,始终无人质疑,直到有人比较报告,调查需要一个星期。 当一个利益相关者说"数字感觉落后一天"时,相信他们,并在其他事情之前检查两个时间表.
::

修补是订购的,有真正的头室:同步时间为01:00,食谱时间为03:00,而非01:30. 通常需要20分钟的同步 一天需要50分钟

## 同步缩小, 但同步提前

这里重述数据编制部分的紧张情况,因为这就是你们采取行动的地方:

**窄**因为每次跑步都要花费时间和空间 **早点**,因为快照只能记得当时同步的内容. 三月第一次同步的字段没有二月值,永远不会—— Salesforce 对象只持有当前状态,历史不能从中重建。

实际规则:用长的文字和很少使用的描述性栏文省下;慷慨地使用 **日期、所有者、阶段、分部和金额**因为这才是你最终想要的趋势

## 监控员告诉你的

Data Manager 监测是输油管的日志,它回答了四个问题,这四个问题解释了大多数事件:

::field-table
---
dataset: "Monitor"
grain: "one row per question"
fields:
  - name: "Did it run?"
    type: "status"
    role: "key"
    note: "一个失败的运行是容易的情况。 一次从未开始的跑步——因为一个时刻表被禁用,常常是在发布期间——是让人惊讶的."
  - name: "When?"
    type: "timestamp"
    role: "date"
    note: "当有人说一个数字是错的时 最有用的数字 大约三分之一的\"错误数字\"报告到此结束."
  - name: "How many rows?"
    type: "count"
    role: "measure"
    note: "看这个一段时间。 一个连续数月持~2800行,突然持~2100行的数据集在上游有问题,没有仪表板会报告."
  - name: "How long?"
    type: "duration"
    role: "measure"
    note: "持续时间是依赖陷阱的预警:需要20分钟的同步时间,"
---
::

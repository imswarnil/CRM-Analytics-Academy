# Hands-On: Zugang zuweisen

Zeit, die Konzepte umzusetzen. Diese Lektion ist ein praktischer Walkthrough durch Salesforce **Einrichtung** - Überprüfen der Analytics-Einstellungen, Überprüfen, wie ein echter Benutzer lizenziert und autorisiert ist, und dann **Erstellen eines brandneuen Scoped-Berechtigungssatzes** von Grund auf neu. Öffnen Sie Ihre kostenlose Developer Org und folgen Sie.

## Schritt 1 — Überprüfen Sie die Analytics-Einstellungen

Beginn **Setup → Quick Find → Analytics → Einstellungen**. Hier bestätigen Sie, dass die Org bereit ist. Hier sind zwei Dinge erwähnenswert:

- **Verwendete Reihen** — CRM Analytics hat ein Datenzeilenlimit, und diese Seite zeigt, wie viel davon Sie verbraucht haben. Behalten Sie es im Auge, wenn Ihre Datensätze wachsen.
- **Beginnen Sie** Links und Umschalter, die bestätigen, dass Analysen aktiviert sind, und Sie auf das Studio verweisen.

Ein kurzer Blick hier zeigt Ihnen, dass die Plattform eingeschaltet ist, bevor Sie den Zugriff zuweisen.

## Schritt 2 - Überprüfen Sie den Zugriff eines Benutzers

Jetzt gehen Sie zu **Einrichten → Benutzer** Öffnen Sie einen Benutzer, der bereits über Analysen verfügt. Auf ihrem Benutzerdatensatz sehen Sie die beiden Ebenen von früher in diesem Abschnitt nebeneinander:

::lesson-cards
---
columns: 2
items:
  - title: "Lizenzen"
    icon: "i-lucide-key-round"
    description: "Die CRM Analytics ()Tableau CRM) Plus PSL, die den Benutzer berechtigt - und möglicherweise eine App-Lizenz wie Sales Analytics daneben."
  - title: "Zuweisung von Genehmigungssätzen"
    icon: "i-lucide-shield-check"
    description: "Die Berechtigung legt die Gewährung tatsächlicher Fähigkeiten fest. Der Standard-Admin-Satz hat die meisten Analytics-Systemberechtigungen vorgewählt."
---
::

Offen **Systemberechtigungen** Diese Standard-Admin-Berechtigung wird festgelegt, und Sie sehen fast jede Analytics-Berechtigung - einschließlich Manage Analytics - bereits überprüft. So sieht ein vollständiger Administrator aus. Die meisten Ihrer Benutzer sollten nicht so aussehen.

## Schritt 3 — Erstellen eines erweiterten Berechtigungssatzes

Jetzt die eigentliche Übung: Erstellen Sie eine **Neues, engmaschiges Berechtigungsset** für einen alltäglichen Dashboard Builder - jemand, der Analysen erstellen und anzeigen sollte, aber keine Dateninstallation berühren darf.

::lesson-steps
---
items:
  - title: "Erstellen Sie das Berechtigungsset"
    description: "Klicken Sie in Setup → Permission Sets auf Neu, geben Sie ihm einen klaren Namen wie CRMA Dashboard Builder und speichern Sie."
  - title: "Offene Systemberechtigungen"
    description: "Öffnen Sie im neuen Set den Abschnitt Systemberechtigungen und klicken Sie auf Bearbeiten, um Analysefunktionen auszuwählen."
  - title: "Gewähren Sie die alltäglichen Fähigkeiten"
    description: "Aktivieren Sie \"Use Analytics\", die Möglichkeit zum Herunterladen und Verwenden von Dashboards sowie die Berechtigung zum Erstellen von Apps und Dashboards."
  - title: "Zurückhalten der riskanten"
    description: "Lassen Sie die Möglichkeit aus, Datenverbindungen hinzuzufügen und Datenflüsse zu bearbeiten - diese gehören Administratoren, nicht Buildern."
  - title: "Speichern und Zuweisen"
    description: "Speichern Sie den Berechtigungssatz und verwenden Sie dann Verwalten von Zuweisungen, um ihn dem Zielbenutzer zuzuweisen (der bereits die PSL halten muss)."
---
::

Das Ergebnis ist ein Benutzer, der Apps erstellen, Dashboards erstellen und herunterladen und Daten erkunden kann - aber **nicht zulässig** Fügen Sie Verbindungen hinzu oder ändern Sie Datenflüsse. Das ist das geringste Privileg in Aktion, und es ist genau die Art von Set, das Sie am häufigsten in einem echten Einsatz verteilen werden.

::tip{icon="i-lucide-lightbulb"}
Name scoped permission setzt nach dem **Rolle** Sie repräsentieren - "CRMA Dashboard Builder", "CRMA Viewer", "CRMA Data Engineer". Zukünftig - Sie (und jeder Admin, der die Org erbt) werden es Ihnen danken, wenn es offensichtlich ist, wofür jedes Set ist.
::

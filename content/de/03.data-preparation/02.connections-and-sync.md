# Verbindungen und Sync

Zwei Phasen, die sich wie Sanitär anfühlen und entscheiden, wie aktuell jede Zahl auf jedem Dashboard ist.

## Anschlüsse

A **Verbindung** ist Anmeldeinformationen plus einen erreichbaren Endpunkt. Die lokalen Salesforce org ist standardmäßig verbunden; alles andere wird einmal konfiguriert und dann referenziert:

- **Ein anderes Salesforce Org** - Häufig in Unternehmen, die mehr als eine laufen.
- **Ein Lager** - Snowflake, BigQuery, Redshift und ähnliches.
- **Objektspeicher und Datenbanken** S3 und direkte Datenbankverbindungen.
- **A CSV Upload** — nicht wirklich eine Verbindung, aber das gleiche Ziel.

::note{icon="i-lucide-key"}
**Credentials verfallen, und dies ist der freundlichste Fehler in der gesamten Pipeline** Der Lauf stoppt und sagt es. Vergleichen Sie das mit einem Berechtigungsproblem, das lautlos eine Spalte fallen lässt. Wenn eine Verbindung bricht, finden Sie sofort heraus, was es wert ist, geschätzt zu werden, während Sie etwas leiser debuggen.
::

## Was Sync eigentlich macht

Daten-Synchronisierung zieht **Ausgewählte Objekte** und **Ausgewählte Felder** in CRM Analytics' eigenen Laden auf einen Zeitplan. Rezepte lesen dann diese lokale Kopie.

Zwei Gründe dafür:

1. **Geschwindigkeit.** Ein Rezept, das fünf Objekte verbindet, würde ansonsten die Quelle fünf Mal pro Durchlauf abfragen.
2. **Höflichkeit.** Das System der Aufzeichnung ist ein Produktions-CRM, das Live-Benutzern dient; Ein Analysejob sollte es nicht jede Stunde hämmern.

Die Konsequenz lohnt sich zu internalisieren: **Es gibt zwei Uhren.** Sync hat einen Zeitplan und Rezepte haben einen Zeitplan. Die Daten auf einem Dashboard sind so alt wie die *früher* Von den beiden, plus wie lange der lauf dauerte.

## Die Abhängigkeitsfalle

::warning{icon="i-lucide-clock-alert"}
**Ein Rezept, das geplant ist, bevor die Synchronisierung, von der es abhängt, abgeschlossen ist, wird erfolgreich laufen, auf den Daten von gestern, jede einzelne Nacht, für immer.** Nichts ist falsch. Die Registerkarte Monitor zeigt grün an. Das Dashboard zeigt Zahlen, die genau einen Tag alt sind, konsistent genug, dass niemand sie in Frage stellt - bis jemand mit einem Bericht vergleicht und die Untersuchung eine Woche dauert. Wenn ein Stakeholder sagt: "Die Zahlen fühlen sich einen Tag zurück an", glauben Sie ihnen und überprüfen Sie die beiden Zeitpläne vor allem anderen.
::

Der Fix ist die Bestellung, mit echtem Headroom: synchronisieren um 01:00, Rezepte um 03:00, nicht 01:30. Eine Synchronisation, die normalerweise zwanzig Minuten dauert, dauert eines Tages fünfzig.

::tip{icon="i-lucide-message-circle-question"}
**Die Frage, die das Terminargument beilegt** ist nicht "wie frisch würde es dir gefallen" - jeder antwortet "so frisch wie möglich", und sie sind nicht falsch. Es ist "**Was würdest du anders machen, wenn das eine Stunde statt eines Tages alt wäre?**„ Wenn es keine Antwort gibt, ist die Nacht richtig und Sie haben gerade das Org-Geld und sich selbst eine Wartungslast gespart.
::

## Sync schmal, aber Sync früh

Die Spannung aus der Datenvorbereitung Abschnitt, hier neu formuliert, weil dies ist, wo Sie darauf reagieren:

**schmal**Denn jedes Feld kostet bei jedem Lauf Zeit und Platz. **Früh**, weil sich ein Snapshot nur daran erinnern kann, was zu der Zeit synchronisiert wurde. Ein Feld, das erstmals im März synchronisiert wurde, hat keine Februar-Werte und wird es niemals tun - die Salesforce Objekt hält nur aktuellen Zustand, und Geschichte kann nicht daraus rekonstruiert werden.

Die praktische Regel: Sparen Sie mit langem Text und selten verwendeten beschreibenden Spalten; seien Sie großzügig mit **Daten, Eigentümer, Stufen, Segmente und Beträge**, denn das sind, was Sie schließlich wollen Trend.

## Was der Monitor Ihnen sagt

Data Manager → Monitor ist das Protokoll der Pipeline und beantwortet vier Fragen, die die meisten Vorfälle erklären:

::field-table
---
dataset: "Monitor"
grain: "one row per question"
fields:
  - name: "Did it run?"
    type: "status"
    role: "key"
    note: "Ein gescheiterter Lauf ist der einfache Fall. Ein Lauf, der nie begonnen hat - weil ein Zeitplan deaktiviert wurde, oft während einer Veröffentlichung - ist derjenige, der die Leute überrascht."
  - name: "When?"
    type: "timestamp"
    role: "date"
    note: "Die einzige nützlichste Zahl, wenn jemand sagt, dass eine Zahl falsch ist. Etwa ein Drittel der \"falschen\" Berichte endet hier."
  - name: "How many rows?"
    type: "count"
    role: "measure"
    note: "Beobachten Sie dies im Laufe der Zeit. Ein Datensatz, der ~ 2.800 Zeilen für Monate gehalten hat und plötzlich 2.100 hält, hat ein Problem, das kein Dashboard melden wird."
  - name: "How long?"
    type: "duration"
    role: "measure"
    note: "Die Creeping-Dauer ist die Frühwarnung für die Abhängigkeitsfalle: Die Synchronisation, die zwanzig Minuten dauerte, dauert jetzt fünfzig, und sie steht kurz davor, mit dem Rezept zu kollidieren, das ihr folgt."
---
::

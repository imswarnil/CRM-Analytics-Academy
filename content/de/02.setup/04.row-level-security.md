# Row-Level Security und das Prädikat

App Sharing entscheidet *Wer kann das Dashboard öffnen*. Row-Level-Sicherheit entscheidet *Was sie sehen, wenn es sich öffnet*. Sie sind unabhängig, und Sie brauchen beides.

## Das Sicherheitsprädikat

A **Sicherheitsprädikat** ist ein Filter, der an den Datensatz selbst angeschlossen ist, ausgewertet pro Viewer, zum Abfragezeitpunkt. Jede Abfrage gegen diesen Datensatz - jedes Widget, jedes Objektiv, jeder Export - hat das Prädikat angewendet, bevor etwas anderes passiert. Es kann nicht von der Dashboard-Seite umgangen werden, was genau die Eigenschaft ist, die Sie wollen.

Die Form ist ein Vergleich zwischen einer Spalte im Datensatz und etwas über den aktuellen Benutzer:

::field-table
---
dataset: "common predicate shapes"
grain: "one row per pattern"
fields:
  - name: "Own records only"
    type: "'OwnerId' == \"$User.Id\""
    role: "key"
    note: "Die einfachste und häufigste. Jeder Betrachter sieht Zeilen, die er besitzt. Erfordert, dass die Benutzer-ID des Besitzers eine Spalte im Datensatz ist - was bedeutet, dass sie synchronisiert und durch jede Verknüpfung im Rezept durchgeführt werden muss."
  - name: "By a user attribute"
    type: "'Region' == \"$User.Region__c\""
    role: "dimension"
    note: "Kombinieren Sie eine Dataset-Spalte mit einem Feld im Benutzerdatensatz. Hervorragend, wenn die Organisation dieses Feld bereits für die Benutzer beibehält, und eine Wartungshaftung, wenn dies nicht der Fall ist - ein leeres Feld bedeutet, dass der Betrachter überhaupt nichts sieht."
  - name: "Role hierarchy"
    type: "'RolePath' contains \"$User.UserRoleId\""
    role: "dimension"
    note: "Ein Manager sieht seine eigenen Reihen und alle darunter. Benötigt die hierarchie, die von einem flachen knoten in den datensatz vorberechnet wird, da ein prädikat die hierarchie zum abfragezeitpunkt nicht laufen kann."
  - name: "Everyone sees everything"
    type: "no predicate"
    role: "measure"
    note: "Eine legitime Wahl für wirklich nicht sensible Daten, und es sollte eine niedergeschriebene Entscheidung sein und nicht eine Auslassung. \"Wir haben das absichtlich nicht eingeschränkt\" und \"niemand hat darüber nachgedacht\" sehen in der Konfiguration identisch aus."
---
::

## Der flache Knoten und warum er existiert

Eine Rollenhierarchie ist ein Baum. Ein Prädikat ist ein Vergleich. Ein Vergleich kann nicht auf einen Baum klettern, daher muss der Baum in etwas Vergleichbares abgeflacht werden **vor** die Daten werden abgefragt — zum Zeitpunkt des Rezepts.

::note{icon="i-lucide-git-branch"}
**Was flatten produziert.** Für jede Rolle eine Spalte, die diese Rolle und alle ihre Vorfahren enthält - ein Pfad. Das Prädikat fragt dann, ob die Rolle des Betrachters irgendwo im Pfad der Reihe erscheint. Die Rolle eines regionalen Direktors erscheint in den Pfaden jedes Vertreters unter ihnen, so dass sie diese Reihen sehen; es erscheint nicht in den Pfaden einer Geschwisterregion, also tun sie es nicht. Die gesamte Hierarchiefrage wird zu einem String-Vergleich, weshalb sie schnell genug ist, um auf jeder Abfrage zu laufen.
::

Dies ist der konkrete Grund, warum Sicherheit gestaltet werden muss **vor** das Datenmodell: Das Prädikat benötigt eine Spalte, die Spalte einen Rezeptknoten und der Knoten benötigt Felder, die synchronisiert werden müssen. Die Entscheidung über die Hierarchie, nachdem die Dashboards erstellt wurden, bedeutet, das Rezept und jeden nachgelagerten Datensatz neu zu erstellen.

## Der Sicherheitsnutzer

Wo das Prädikat eine Regel ist, die du schreibst, **gemeinsames Erbe** lässt das Teilen der Org selbst entscheiden – und die **Sicherheitsnutzer** ist das Konto, das es auswertet. Er benötigt Zugang zu den Feldern, von denen die Bewertung abhängt, und wenn er sie nicht sehen kann, kann die Vererbung nicht berechnet werden.

Behandeln Sie es wie den Integrationsbenutzer: eng, bewusst und dokumentiert. Beide sind spezielle Konten, deren Zugriff eher eine Designentscheidung als ein nachträglicher Einfall ist.

::warning{icon="i-lucide-lock"}
**Prädikate scheitern geschlossen, und das ist der richtige Standard.** Ein Tippfehler, eine fehlende Spalte oder ein leeres Benutzerfeld erzeugt ein leeres Dashboard anstelle eines Lecks. Wenn also jemand berichtet, dass "das Dashboard für das gesamte Team leer ist", vermuten Sie zuerst das Prädikat - und seien Sie dankbar, dass es in diese Richtung gebrochen ist.
::

## Die Falle, die alle einmal fängt

Sie fügen ein Prädikat hinzu und Ihre eigenen Dashboards werden leer.

Nichts ist kaputt. Das Prädikat wird bewertet für *Sie* auch, und Ihr Benutzer erfüllt es nicht - Sie besitzen keine der Datensätze, Ihre Rolle liegt außerhalb der Pfade, Ihr Regionsfeld ist leer. Administratoren sind nicht standardmäßig befreit.

::tip{icon="i-lucide-user-cog"}
**Planen Sie die Freistellung bewusst** anstatt sich in Panik etwas Breites zu gewähren. Eine benannte Bedingung im Prädikat - eine Rolle, eine Berechtigung, ein Benutzerattribut, das das Analyseteam trägt - ist explizit, überprüfbar und übergibt nicht stillschweigend die gleiche Ausnahme an die nächste Person, die dieses Profil erbt.
::

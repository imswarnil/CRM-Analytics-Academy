# Die REST API

Salesforce Analytics durch seine REST API: Datensätze, Abfragen, Dashboards und die Metadaten dahinter.

## Authentifizierung

Anfragen tragen ein OAuth-Zugriffstoken, das über eine verbundene App erhalten wird. Zwei praktische Punkte sind wichtiger als die Mechanik:

::lesson-steps
---
items:
  - title: "Verwenden Sie einen dedizierten Integrationsbenutzer"
    description: "Keine Person. Eine person geht, ihr konto wird deaktiviert, und jeder job, der authentifiziert wird, wenn sie an einem tag aufhört, den niemand vorhergesagt hat. Ein benanntes Integrationskonto mit nur den erforderlichen Berechtigungen macht auch einen Audit-Trail sinnvoll."
  - title: "Bewahren Sie Ihre Anmeldeinformationen in einem Secret Store auf"
    description: "Umgebungsvariablen aus einem Managed Store, einem Tresor oder dem geheimen Speicher des CI-Anbieters. Niemals im Drehbuch, nie in einem Notizbuch, nie im Repository - und ein öffentliches Repo macht das irreversibel und nicht peinlich."
  - title: "Umgang mit Token Ablauf als normaler Betrieb"
    description: "Tokens verfallen; das ist das Design. Ein Job, der über Nacht auf einem abgelaufenen Token stirbt, ist ein Job, der keine Aktualisierung implementiert hat. Angenommen, ein Lauf kann einen Ablauf überspannen."
  - title: "Geben Sie dem Integrationsbenutzer nur das, was er braucht"
    description: "Ein Loader muss Datensätze schreiben, nicht jedes Objekt in der Org lesen. Enge Berechtigungen begrenzen den Explosionsradius eines durchgesickerten Anmelders und machen deutlich, wofür der Job ist."
---
::

## Versionierung

Endpunkte tragen eine Version im Pfad. Pin it.

::note{icon="i-lucide-pin"}
**Eine gepinnte Version ist ein Skript, das beim Update der Plattform weiter funktioniert, und eine ungepinnte Version ist ein Skript, das das Verhalten an einem Datum ändert, das jemand anderes gewählt hat.** Verbessern Sie absichtlich: Ändern Sie die Version, laufen Sie gegen eine Sandbox, bestätigen Sie, dass die Antwortform das ist, was Sie erwarten, und versenden Sie dann. Dies ist eine zweiminütige Gewohnheit, die die Klasse des Fehlers verhindert, bei der sich nichts in Ihrem Repository geändert hat und der Job sowieso kaputt gegangen ist.
::

## Grenzen des Designs herum

Jede Plattform hat sie und die spezifischen Zahlen bewegen sich, so dass es bei dem nachhaltigen Rat eher um Form als um Zahlen geht:

::compare-cols
---
items:
  - title: "Formen, die skalieren"
    subtitle: "Work with the limits"
    icon: "i-lucide-check"
    pros:
      - "Batch — one call with many rows rather than many calls with one"
      - "Incremental — send what changed, not everything, every night"
      - "Back off and retry on a rate-limit response rather than hammering"
      - "Check the current limits for your edition before sizing anything"
    cons:
      - "More code than the naive version"
    verdict: "Write it this way from the start."
  - title: "Formen, die im Maßstab versagen"
    subtitle: "Fine in a test, not in production"
    icon: "i-lucide-x"
    pros:
      - "Simple, and works beautifully against 100 rows"
    cons:
      - "A call per row exhausts the daily allowance and starves everything else in the org"
      - "A full reload every night when 2% of rows changed"
      - "No retry, so one transient error loses the whole run"
    verdict: "This is how an analytics job takes down an org's API budget."
---
::

::warning{icon="i-lucide-gauge"}
**API Grenzen sind org-weit.** Ein gieriger Analytics-Job verlangsamt sich nicht nur selbst – er verbraucht Zulagen, auf die Integrationen, mobile Clients und andere Teams ebenfalls zurückgreifen. Das macht einen schlecht geformten Loader zu einem Betriebsproblem für Leute, die noch nie von Ihrem Dashboard gehört haben, und es ist der Grund, zu batchen, bevor jemand Sie darum bittet.
::

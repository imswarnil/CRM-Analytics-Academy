## Upload order matters (a little)

Not for correctness — for sanity. Load dimensions first so that when you build a recipe, the lookup targets already exist.

::lesson-steps
---
items:
  - title: "Dimensions first"
    description: "accounts, contacts, products, reps, centers, campaigns. Six small files. Two minutes each, and now every later recipe can look up against them."
  - title: "Then the pipeline facts"
    description: "leads, opportunities, opportunity_products, quotes. These are what the pipeline section runs on."
  - title: "Then post-sale"
    description: "usage_monthly, arr_snapshots, cases, csat_surveys, platform_health_daily — then the classroom pair, batches and enrollments."
  - title: "Demand last"
    description: "web_sessions, seo_keywords, llm_visibility, marketing_spend. They join to nothing, so nothing waits on them."
---
::

::tip{icon="i-lucide-upload"}
Use **Create → Dataset → CSV File**, not a recipe, for the raw upload. A recipe is for shaping. Uploading through one means re-running a job every time you want a raw table back.
::

## Fix the field metadata now, not later

This is the step everyone skips and everyone regrets. When CRM Analytics infers a schema it makes three predictable mistakes on this dataset.

::lesson-cards
---
columns: 3
items:
  - title: "Booleans become text"
    icon: "i-lucide-toggle-left"
    description: "IsWon, SLABreached, DeflectedByAI arrive as the strings 'true'/'false'. Filterable, but you cannot sum them — and counting wins is a sum."
  - title: "Numbers become dimensions"
    icon: "i-lucide-hash"
    description: "LeadScore, Position, MentionRank get read as text because they are small integers. Then you cannot average them."
  - title: "Currency has no format"
    icon: "i-lucide-dollar-sign"
    description: "Amount and ARR render as 120000. Set the format once on the dataset and every chart inherits $120K."
---
::

The fix is dataset **field metadata**, covered in the datasets and modelling section — edit the field, set the type, set the format, save. Do it once per dataset and every lens, dashboard and SAQL query inherits it.

::metric-spec
---
items:
  - name: "Counting won deals"
    formula: "count() filtered to IsWon = true"
    grain: "Per opportunity"
    watchout: "Do NOT sum IsWon as text. If it uploaded as a string, either convert the field or count with a filter — a text 'true' summed gives you zero and no error."
---
::

## Three recipes, built once

Rather than joining inside twenty dashboards, join once and register the result. Three joined datasets carry everything in this section.

### Recipe 1 — `opp_enriched`

The pipeline workhorse. Opportunities, plus the account and rep context every chart filters by.

::lesson-steps
---
items:
  - title: "Input: opportunities"
    description: "608 rows. This is the grain of the output — one row per opportunity, and it must stay that way."
  - title: "Join accounts on AccountId"
    description: "Lookup, not append. Brings Segment, Industry, Region, HealthScore, SupportTier. One-to-one, so no fan-out."
  - title: "Join reps on OwnerId"
    description: "Brings Role, RampStatus, AnnualQuota, Manager. Watch for blank OwnerId on Self-Serve deals — they have no rep, and a default join will silently drop them."
  - title: "Aggregate opportunity_products first, THEN join"
    description: "Group by OpportunityId, take count of products and a comma-joined product list. Joining the raw line items instead multiplies every opportunity by its product count."
  - title: "Join final quote only"
    description: "Filter quotes to IsFinalVersion = true before joining, or one opportunity becomes up to five rows."
  - title: "Output: opp_enriched"
    description: "Still 608 rows. Verify that count before you use it — if it grew, you fanned out."
---
::

::tip{icon="i-lucide-shield-alert"}
**The one assertion to always run.** After every join, check the row count against the input. `opp_enriched` must be 608 rows. If it is 1,192 you joined line items raw; if it is 818 you joined all quote versions. Row count is the cheapest correctness test in analytics.
::

### Recipe 2 — `lead_funnel`

Leads, with the campaign and the outcome attached.

::lesson-steps
---
items:
  - title: "Input: leads"
    description: "2,800 rows, and the output stays 2,800. Disqualified leads stay in — dropping them inflates every conversion rate."
  - title: "Join campaigns on CampaignId"
    description: "Brings Channel, Type, Spend, Region. Leads with a blank CampaignId are real (self-serve signups) — keep them with a left join."
  - title: "Compute the stage flags"
    description: "IsMQL, IsSQL, IsConverted already exist. Add DaysToMQL = MQLDate − CreatedDate and DaysToSQL, so velocity is available without date maths in every chart."
  - title: "Join the opportunity outcome"
    description: "On ConvertedOpportunityId, bring back Stage, Amount, IsWon. Now one dataset answers 'which channel produced revenue', not just 'which produced leads'."
---
::

### Recipe 3 — `account_360`

One row per account, with everything that happened to it.

::lesson-steps
---
items:
  - title: "Input: accounts"
    description: "140 rows. Output must be 140."
  - title: "Aggregate usage_monthly to the account"
    description: "Group by AccountId: sum BilledRevenue, average UtilizationPct, take the latest CommitState. Never join it raw — 2,612 rows against 140 is the textbook fan-out."
  - title: "Aggregate cases to the account"
    description: "Count cases, count SLA breaches, average CSAT, max LinkedToChurnRisk. Support becomes three columns on the account."
  - title: "Take the latest ARR snapshot"
    description: "Filter arr_snapshots to the most recent MonthEnd, then join. Join all months and you multiply by eighteen."
  - title: "Output: account_360"
    description: "140 rows, and the single most useful dataset in the RevOps section."
---
::

::note{icon="i-lucide-repeat-2"}
**Schedule them, then forget them.** Set each recipe to run nightly. Every dashboard downstream reads a dataset, not a join, which means a dashboard cannot be wrong in a way a recipe isn't — a single place to fix, and a single place to audit.
::

## The mistake worth naming

A tempting fourth recipe: join everything into one wide dataset and build every dashboard on it. It feels efficient. It is a trap.

::compare-cols
---
items:
  - title: "Three purposeful datasets"
    icon: "i-lucide-layers-3"
    pros:
      - "Each has one obvious grain"
      - "Row-count assertions are meaningful"
      - "A fan-out is caught at build time"
    verdict: "What this section uses."
  - title: "One wide 'everything' dataset"
    icon: "i-lucide-package"
    pros:
      - "Only one thing to schedule"
    cons:
      - "No single grain, so every sum is suspect"
      - "Slow, and re-runs for any change"
      - "Fan-out is invisible until a number is absurd"
    verdict: "Avoid. The convenience is real and it costs you correctness."
---
::

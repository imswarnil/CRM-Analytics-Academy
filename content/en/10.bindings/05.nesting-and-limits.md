# Nesting and Limits

Bindings compose. A selection feeds a query, whose result feeds a title, which feeds a filter on a third widget. Each step is reasonable; the accumulation is where dashboards die.

## What chaining costs

::warning{icon="i-lucide-git-branch"}
**Three costs, and only the first is visible.** Widgets execute in sequence rather than in parallel, so the screen gets slower in a way its widget count does not explain. A change to the first widget breaks the third for reasons nothing on screen suggests. And the dependency graph exists only in configuration panels, so understanding it means opening every widget one at a time and holding the structure in your head.
::

## The real limit is social

There is no documented ceiling on bindings, and the number is not the point:

::note{icon="i-lucide-user-check"}
**The test: could a colleague add a widget to this dashboard next month without asking you?** If the honest answer is no, the bindings have crossed the line — not because there are too many, but because their effects are unpredictable from the outside. A dashboard only one person can change is a dashboard with a single point of failure who will eventually take a holiday.
::

## Three habits that keep it workable

::lesson-steps
---
items:
  - title: "Document each binding in one line"
    description: "In the dashboard description: 'Region filter → rep filter list; rep filter → all pipeline widgets; company-average query → the colour threshold on the segment chart.' Three lines, and the next person can reason about the screen without opening a single configuration panel."
  - title: "Prefer breadth to depth"
    description: "Five widgets each bound directly to one filter is fine. Three widgets bound in a chain is worse, even though there are fewer bindings — depth is what makes effects unpredictable."
  - title: "Name queries for what they are"
    description: "'company_avg_arr' rather than 'query_7'. Bindings reference queries by name, so the names are the only readable part of the whole arrangement."
---
::

## When to stop and split

Four signals, any one of which is enough:

- You cannot describe the binding structure out loud in three sentences.
- The dashboard serves two audiences that each ignore half of it.
- A new widget requires understanding three existing ones before it can be added.
- The load is sequential enough that the screen fills in visible stages.

::tip{icon="i-lucide-scissors"}
**Splitting is nearly always the right answer, and it is rarely the tempting one.** The clever single dashboard feels like the better artefact; two plain ones are easier to read, faster to load, simpler to share to different audiences, and changeable by somebody else. Section 12's argument about app sharing applies here too — governance is easier when the unit is smaller.
::

## What is genuinely worth the complexity

Not everything should be simplified away. A dependent filter on a forty-item list, a dynamic title, a threshold that follows the current period — these earn their keep and would each be missed if removed. The judgement is not "fewer bindings" but "each binding pays for itself, and the arrangement is legible".

# Results Bindings

A selection binding reads what somebody clicked. A **results binding** reads what a query returned — a total, an average, a maximum, the top category — and feeds it into another widget.

## What it makes possible

  - title: "Context in a title"

## The execution order you just created

::warning{icon="i-lucide-hourglass"}
**A results binding makes one widget wait for another.** Widget B cannot query until widget A has returned, so what would have been two parallel requests becomes two sequential ones. Chain three and the last widget waits for two round trips. This is the cause of the specific complaint "the dashboard is slow in a way that does not match how few widgets it has" — and because the dependency lives in configuration, nothing on screen suggests it.
::

## Debugging is genuinely harder

With a selection binding, the input is on screen: you can see what is selected. With a results binding, the input is a value inside another query, and when the dependent widget shows something odd you have to work out what the source returned before you can say whether the consumer is wrong.

::lesson-steps
---
items:
  - title: "Check the source widget alone"
    description: "What does it actually return — one row, several, a null? A binding expecting a single value that receives three behaves differently from how it reads."
  - title: "Check the empty case"
    description: "When the source query returns nothing — a filter with no matches — what does the consumer do? This is where dashboards break in front of a viewer whose data is genuinely empty, which is often precisely the interesting case."
  - title: "Check the type"
    description: "A number bound into a string context, or a date bound as text, fails quietly and formats strangely rather than erroring."
  - title: "Then document it"
    description: "One line in the dashboard description: which widget feeds which, and what it is for. A results binding is invisible; leaving it undocumented is how the next person concludes the dashboard is haunted."
---
::

## When the recipe should have done it

::note{icon="i-lucide-database"}
**If the computed value is a company metric, it belongs upstream.** A results binding that calculates "average deal size" for every viewer on every load is doing overnight work at view time — and it is defining a metric in a place nobody can find. Compute it in the recipe, store it, and bind to a field. Reserve results bindings for things that genuinely depend on the *current selection*, which a recipe cannot know.
::

## A reasonable limit

One or two results bindings on a dashboard is normal and useful. Five is a dashboard that behaves like an application, loads sequentially, and can only be maintained by whoever wrote it.

::tip{icon="i-lucide-split"}
**When you find yourself wanting a fourth, split the dashboard.** Two screens, each simple, beat one clever one — and they can be shared with different audiences, which is easier to govern anyway.
::

# Designing a Dataset

Start from the questions, not from the tables. The tables tell you what is possible; the questions tell you what to build.

## The four-question design

::lesson-steps
---
items:
  - title: "Write down the questions it must answer"
    description: "Five or six, in plain language. 'Which segments hold our ARR.' 'Which deals have been stuck longest.' If you cannot list them, you are building a copy of a source table rather than a dataset."
  - title: "Derive the grain from the finest question"
    description: "If any question is about individual deals, the grain is one row per deal. If they are all about monthly totals by segment, it can be one row per segment per month — and it will be far faster."
  - title: "List the columns each question needs"
    description: "Dimensions to group by, measures to aggregate, dates to trend. Anything not serving a listed question is a candidate to leave out: every extra column costs run time and makes the field list harder for the next person to read."
  - title: "Decide what is permanently excluded"
    description: "Test records, internal accounts, a product line nobody reports on. If a row should never appear in any answer this dataset gives, filter it here rather than asking every dashboard to remember."
---
::

## Filter in the dataset or on the dashboard?

::field-table
---
dataset: where a filter belongs
grain: one row per case
fields:
  - name: "In the dataset"
    type: "structural exclusion"
    role: "key"
    note: "Test accounts, deleted records, a segment that is not part of this dataset's purpose. Nobody should be able to un-exclude them by clearing a control, and every consumer inherits the exclusion without knowing to ask."
  - name: "In the widget's query"
    type: "this widget always"
    role: "measure"
    note: "'Open pipeline' should never show closed-lost deals because somebody reset a filter. Structural to the widget, not to the dataset, because another widget on the same dataset legitimately wants those rows."
  - name: "On the dashboard"
    type: "exploratory"
    role: "dimension"
    note: "Period, region, segment — things viewers should be able to change. If a filter is a control, it is here."
---
::

::warning{icon="i-lucide-filter-x"}
**A filter in the dataset is invisible to everyone downstream.** That is its value and its risk: an analyst reconciling your dataset against the source will find a difference and have no way to see why. Put every dataset-level filter in the dataset's description — 'excludes test accounts and the internal sandbox org' — or you will be asked about the discrepancy repeatedly.
::

## One dataset or two?

The temptation is always to widen the existing one. Two signals that you should split instead:

::compare-cols
---
items:
  - title: "Split"
    subtitle: "Different grain, or different purpose"
    icon: "i-lucide-split"
    pros:
      - "Each is simple enough to reason about"
      - "The daily dashboard gets a fast pre-aggregated dataset while exploration keeps the detail"
      - "One recipe can produce both outputs, so the logic is still defined once"
    cons:
      - "Two things to schedule and monitor"
    verdict: "Usually right when the grains genuinely differ."
  - title: "Widen"
    subtitle: "Add columns to the existing one"
    icon: "i-lucide-move-horizontal"
    pros:
      - "One thing to maintain"
      - "Fine when the new questions live at the same grain"
    cons:
      - "A dataset serving everybody eventually serves nobody well"
      - "Sixty columns of which fifteen matter is hostile to self-service"
    verdict: "Right only while the grain and purpose still match."
---
::

::tip{icon="i-lucide-git-branch"}
**Two outputs from one recipe is the underused option.** The joins, the cleaning and the definitions happen once; the recipe then writes a detailed dataset and an aggregated one. You get speed where it matters and detail where it is needed, without two copies of the logic drifting apart.
::

## Write the grain in the description

Every dataset, one sentence: *one row per opportunity per product*. It is five seconds of work and the single most useful thing anybody downstream reads — the difference between a colleague summing the right column and summing a duplicated one without ever knowing.

# Field Metadata and Formatting

Every dataset carries metadata about its fields: display label, format, default aggregation, visibility. Setting it once is the difference between a dataset people can use and one that needs a translator.

## Labels

`Sum of Amount__c` is what the data says. "Revenue" is what the business says. The label belongs on the dataset, where every lens and every widget inherits it.

::tip{icon="i-lucide-users"}
**Label for the reader, not for the builder.** The field's technical name is useful to you for about a week; the label is read by everyone who ever opens the dashboard, for years. If two fields could be confused — `Amount` on the opportunity and `LineAmount` on the product line — make the labels unambiguous rather than short: "Deal Amount" and "Line Amount" prevent a real mistake.
::

## Formats

Currency symbols, thousands separators, decimal places, percentages. Fixing these at the dataset removes the most common cosmetic defect in CRM Analytics dashboards — the same measure formatted three different ways on one screen because three people built three widgets.

::note{icon="i-lucide-coins"}
**Decimals are a readability decision, not a precision one.** Nobody makes a decision on the cents of a $13.4M figure, and six decimal places on a conversion rate implies a confidence the data cannot support. Round to what the decision needs: whole currency for totals, one decimal for rates, and let the exact value live in table mode for whoever wants it.
::

## Default aggregation

A measure can carry a sensible default — usually sum, sometimes average, occasionally max. It is a small thing that quietly prevents a real error:

::warning{icon="i-lucide-triangle-alert"}
**A rate field with a default of `sum` is a loaded gun.** The Academy's usage data carries a utilisation percentage per account per month. Summed across twelve months, an account at 80% utilisation reads as 960%. Nothing errors, the chart renders, and the number is nonsense. Set the default to average — and better, follow the data preparation section's advice and compute the rate from aggregated totals instead of storing a per-row rate at all.
::

## Hiding fields

A dataset with sixty columns, of which fifteen are keys and internal flags, is hostile to anyone exploring it. Hide what nobody should group by: surrogate keys, internal booleans, staging columns.

This matters most for **self-service**, which is the exploration section's subject. A field list that is fifteen meaningful items long invites exploration; one that is sixty items long, half of them named `X__c`, teaches people that this tool is for specialists.

## The five-minute pass worth doing on every dataset

::lesson-steps
---
items:
  - title: "Label every field a human will see"
    description: "Business language, unambiguous between similar fields. This is the highest-value part and it takes two minutes."
  - title: "Format the measures"
    description: "Currency where currency, percentages where percentages, decimals set to what the decision needs."
  - title: "Set default aggregations"
    description: "Sum for amounts, average for rates. Especially rates."
  - title: "Hide the plumbing"
    description: "Keys, staging columns, internal flags. If nobody should ever group by it, it should not be in the list."
  - title: "Write the grain in the description"
    description: "'One row per opportunity per product.' The single most useful sentence anyone downstream will read, and the one most often missing."
---
::

::tip{icon="i-lucide-clock"}
**Do this before sharing a dataset, not after.** Once ten widgets exist, changing a label is safe but changing a default aggregation means auditing every one of them. Five minutes at the start costs five minutes; the same five minutes later costs an afternoon of checking.
::

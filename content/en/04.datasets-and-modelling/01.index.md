# A Dataset Is a Decision

The previous section got data into CRM Analytics. This one is about what shape it takes once it is there — and unlike a warehouse, where a clever query can rescue a poor table, a dataset's shape is a decision you live with.

::note{icon="i-lucide-ruler"}
**Because a dataset is built rather than queried, somebody chooses its grain, its joins, its filters and its fields.** Those choices decide which questions are answerable and which are not. A dataset aggregated to monthly totals is fast and can never tell you which segment drove the month; a dataset at the finest possible grain answers everything and hands the fan-out problem to every person who touches it.
::

## Too fine, too coarse, about right

::compare-cols
---
items:
  - title: "Too fine"
    subtitle: "Every row preserved"
    icon: "i-lucide-microscope"
    pros:
      - "Any question is answerable"
      - "One dataset serves many dashboards"
    cons:
      - "Every widget aggregates a lot of rows on every load, for every viewer"
      - "Fan-out risk handed to everyone who builds on it"
      - "Counting anything needs a distinct count, and somebody will forget"
    verdict: "Right for exploration, expensive for a daily dashboard."
  - title: "Too coarse"
    subtitle: "Pre-aggregated"
    icon: "i-lucide-box"
    pros:
      - "Fast, and the definition is settled upstream"
    cons:
      - "'Which segment drove that?' is no longer answerable"
      - "Every new question needs a new dataset"
    verdict: "Right for a screen many people open daily."
---
::

::tip{icon="i-lucide-layers"}
**The production answer is usually both.** A fine-grained dataset for exploration, and a pre-aggregated one behind the dashboard everyone opens. Section 15's warehouse is built this way deliberately — the tables you explore are not always the tables the executive board reads, and pretending one dataset can serve both is how dashboards end up slow and analysts end up blocked.
::

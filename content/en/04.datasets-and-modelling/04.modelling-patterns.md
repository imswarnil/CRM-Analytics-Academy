# Modelling Patterns

CRM Analytics is not a warehouse and its datasets are not a star schema, but the same shapes recur — and recognising them saves you from rediscovering each one.

## Fact and reference

::field-table
---
dataset: the two roles
grain: one row per role
fields:
  - name: "Fact tables"
    type: "things that happened"
    role: "measure"
    note: "Opportunities, leads, cases, usage, sessions. Many rows, carrying measures and dates and keys. These are what you aggregate."
  - name: "Reference tables"
    type: "things that are"
    role: "dimension"
    note: "Accounts, products, reps, campaigns. Few rows, carrying attributes. You join TO them to get labels and groupings — summing anything in one is nearly always a mistake, and an ARR column on an account table is the standing trap because it is both an attribute and a measure."
---
::

::warning{icon="i-lucide-alert-triangle"}
**Joining a reference table onto a fact table is safe; the reverse multiplies.** Bringing an account's segment onto every opportunity keeps the opportunity grain. Bringing every opportunity onto each account row does not — and if you then sum the account's ARR, you have multiplied it by that account's deal count. This is the fan-out from the previous lesson, arriving from the other direction.
::

## Wide versus long

Two ways to hold several metrics per entity:

::compare-cols
---
items:
  - title: "Wide"
    subtitle: "One column per metric"
    icon: "i-lucide-table-columns"
    pros:
      - "Natural for charts — pick the column you want"
      - "Obvious to read in a table preview"
      - "Fine when the metric list is short and stable"
    cons:
      - "A new metric means a schema change and a rebuild"
      - "Charting many metrics together needs one widget per column"
    verdict: "Default for a small, settled set."
  - title: "Long"
    subtitle: "One row per entity per metric"
    icon: "i-lucide-rows-3"
    pros:
      - "New metrics are new rows, not schema changes"
      - "One widget can chart any metric, chosen by a filter"
      - "Natural fit for a metric-toggle binding"
    cons:
      - "Every query must filter to a metric, and forgetting sums unrelated things together"
      - "Harder to read raw"
    verdict: "Right when metrics are added often."
---
::

::note{icon="i-lucide-alert-circle"}
**Long format's failure is spectacular and silent: summing across metrics.** A query that forgets to filter to one metric adds revenue to deal count to conversion rate and returns a number. Nothing errors. If you model long, make the metric filter part of every widget's base query rather than trusting each builder to remember.
::

## Derived layers

A recipe can read another recipe's output. That is how you get a clean base dataset feeding several purpose-built ones — the pattern the GTM engineering section's warehouse uses.

::lesson-steps
---
items:
  - title: "Keep the chain shallow"
    description: "Base, then derived. Three or four links deep and a failure at the start is invisible at the end, and nobody can say which layer introduced a wrong number."
  - title: "Order the schedules with headroom"
    description: "The dependency trap again: a derived recipe that starts before its source finishes runs successfully on yesterday's data, every night, and reports green."
  - title: "Name the layers"
    description: "A prefix that says what a dataset is for — base, reporting, exec — tells the next person where in the chain they are looking, which no other property will."
  - title: "Put the definitions in the base"
    description: "Metrics computed in the base layer are inherited by everything downstream by construction. A definition added to a derived dataset applies to one branch and quietly diverges from its siblings."
---
::

## Bridge tables

When two things have a many-to-many relationship — opportunities and products, campaigns and leads — the join table *is* the grain you must respect.

`opportunity_products.csv` is the Academy's: 1,192 rows bridging 608 opportunities and 6 products. Any query against it is at line grain, so deal counts need a distinct count and parent measures must not be summed. Recognising a bridge table on sight — a table that is mostly keys — tells you all of that before you write anything.

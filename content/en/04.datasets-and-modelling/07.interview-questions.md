interview:
  - q: "What is grain and why does it matter more than anything else?"
    a: "The grain is what exactly one row represents. It matters most because nearly every wrong number in analytics is a grain problem: join 608 opportunities to 1,192 product lines, sum the opportunity amount, and $13.4M becomes $36.9M with no error anywhere — the join is correct, every row is correct, and the total is double. So the first question I ask of any dataset is what one row is, and I write the answer into the dataset description."
  - q: "How do you decide a dataset's grain?"
    a: "From the questions it has to answer, written down first. The finest question sets the grain — if anything is about individual deals, it is one row per deal. If every question is monthly totals by segment, it can be pre-aggregated, which is much faster and permanently unable to answer anything below that. And when two audiences genuinely need different grains, that is two datasets, usually from one recipe with two outputs so the logic is still defined once."
  - q: "Fan-out — two fixes. When do you use each?"
    a: "Aggregate the many side before the join, which keeps the output at one row per deal — right when the dataset is about deals. Or keep the finer grain deliberately and do not carry the parent's measure down, summing the line-level amounts instead — right when the dataset is about products. Which one depends on what the dataset is for, not on which is easier."
  - q: "Why would you build a snapshot dataset?"
    a: "Because Salesforce objects hold only current state. An opportunity knows today's amount and stage and nothing about March, so pipeline movement, slipped deals, forecast accuracy and an ARR waterfall are all unanswerable from the object. A snapshot appends current state each run and accumulates history that cannot be reconstructed afterwards — which is also why I set it up early and sync dates, owners, stages and amounts generously from the start. A field added in March has no February values, permanently."
  - q: "What is the trap with querying a snapshot?"
    a: "The same entity appears many times by design — one row per account per month. Summing ARR across all rows of an eighteen-month snapshot gives eighteen years of revenue. Every query against one must either pick a month or group by one, and 'current' is a filter rather than a property."
  - q: "How do you make a dataset usable by other people?"
    a: "Field metadata, before sharing rather than after. Business labels rather than API names, formats set once, sensible default aggregations — especially on rates, because a utilisation percentage defaulting to sum reads as 960% across a year and renders cleanly. Hide the plumbing so the field list is fifteen meaningful items rather than sixty with surrogate keys among them. And the grain in the description, which is the one sentence everybody downstream actually reads."
  - q: "When would you model long rather than wide?"
    a: "When metrics get added often, or when I want one widget to chart any of them via a filter — new metrics become new rows rather than a schema change and a rebuild. The cost is that every query must filter to a metric, and a query that forgets adds revenue to deal count to conversion rate and returns a number with no error. So if I model long, the metric filter goes into the base query rather than being left to each builder to remember."
  - q: "What is the risk with derived datasets built on other datasets?"
    a: "A scheduling chain where a failure three links back is invisible at the end, and nobody can say which layer introduced a wrong number. I keep the chain shallow — base then derived — order the schedules with real headroom, and put shared definitions in the base layer so everything downstream inherits them by construction rather than diverging branch by branch."

# Datasets and Modelling: Interview Questions

In practice this section is the technical screen. Grain and fan-out come up in almost every CRM Analytics interview, and reaching for them unprompted when shown a wrong number is immediately distinguishable.

::note{icon="i-lucide-ear"}
**What separates strong answers here is the diagnostic instinct rather than the definition.** Anyone can define fan-out. The signal is answering "the total is wrong" with "is it a clean multiple, or is it low?" — that single question splits the problem space in half before any investigation starts.
::

## The three sentences worth memorising

1. **"The grain is what one row represents, and it goes in the dataset description."**
2. **"A clean multiple is fan-out; missing rows are an inner join or permissions."**
3. **"Snapshots hold the history the object cannot, and they cannot be backfilled."**

# Faceting and Filters

**Faceting** is the behaviour where interacting with one widget filters the others. It is what separates a dashboard from a page of pictures, and it is on by default between widgets built on the same dataset.

## Why the default is right

Click a segment in a bar chart and the headline number, the table and the trend all narrow to it. The viewer asked a follow-up question without knowing they were doing it — no filter menu, no reload, no training.

::note{icon="i-lucide-mouse-pointer-click"}
**This is the single feature that makes self-service work.** Most people will never build a lens. Nearly everyone will click a bar to see what is inside it. Designing so that clicking anything produces a sensible narrowing is how a dashboard answers questions you did not anticipate — which is the entire promise of the collaboration section's self-service argument.
::

## When to switch it off

Three cases, and they are worth recognising on sight:

::field-table
---
dataset: when faceting should be off
grain: one row per case
fields:
  - name: "The reference widget"
    type: "must not move"
    role: "key"
    note: "A company-wide total that stays fixed while everything else filters, so the reader can see the part against the whole. If it narrows along with the selection, the comparison it exists for disappears at the moment it becomes useful."
  - name: "Different grain"
    type: "would mislead"
    role: "measure"
    note: "The Academy's platform health data has no account key at all. Filtering it by an account selection is not merely unhelpful — it silently implies a relationship between the platform's uptime and one customer that the data cannot support."
  - name: "Context panels"
    type: "static by design"
    role: "dimension"
    note: "Definitions, a refresh timestamp, a link to the metric spec. These are furniture; they should not react to anything."
---
::

::warning{icon="i-lucide-link-2-off"}
**Faceting across datasets requires deliberate wiring.** Widgets on the same dataset facet automatically; widgets on different datasets do not, unless you connect them. The trap is a dashboard where half the widgets respond to a filter and half quietly do not — the viewer filters to EMEA, four widgets narrow, three keep showing the global figure, and every number on screen is individually correct while the screen as a whole is a lie. Check every widget against a filter before shipping.
::

## Global filters

A filter widget along the top — month, segment, region — that everything obeys. Three rules:

::lesson-steps
---
items:
  - title: "Show the current selection"
    description: "A dashboard filtered to one region that does not say so is the most common way a screenshot ends up in a meeting representing the whole company. The selection must be visible on the screen and ideally in a widget title."
  - title: "Default to the common case"
    description: "Current quarter, all regions, whatever the audience means when they say 'normal'. A dashboard that opens unfiltered and enormous makes everyone do the same three clicks every morning."
  - title: "Keep the list short"
    description: "Three or four filters. More than that and people stop using them entirely, which is worse than having none — they scroll instead, and read the wrong number."
---
::

## Empty states

A viewer filters to something with no data and a widget goes blank. Blank is honest. Blank with no explanation looks broken, and "the dashboard is broken" spreads faster than any correction.

::tip{icon="i-lucide-message-square"}
**Give the important widgets an empty-state message** — "No cases match this filter" rather than nothing at all. It is the difference between a viewer who narrows their filter and a viewer who reports an outage. This matters most for widgets that legitimately go empty often, like a risk table that is empty precisely when things are going well.
::

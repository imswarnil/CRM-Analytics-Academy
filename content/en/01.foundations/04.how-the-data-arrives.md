# How the Data Arrives

Five stages, in order. Knowing which one you are standing in is most of debugging.

::lesson-steps
---
items:
  - title: "Connection"
    description: "Where data comes from: this Salesforce org, another one, Snowflake, S3, Redshift, a database, or an uploaded CSV. A connection is credentials plus a reachable endpoint, configured once."
  - title: "Data sync"
    description: "A scheduled pull of SELECTED objects and SELECTED fields into CRM Analytics' own store. Recipes then read this local copy rather than hitting the source on every run — faster, and gentler on the system of record."
  - title: "Recipe"
    description: "The visual transformation: inputs, then joins, filters, formulas, aggregates, and an output node. This is where grain is decided and where most of the thinking happens."
  - title: "Dataset"
    description: "The materialised, columnar result. What lenses and dashboards actually read. Rebuilt whole on each run."
  - title: "Schedule"
    description: "What drives sync and recipes — nightly, hourly, or on an event. The schedule is the difference between 'the numbers are stale' and 'the numbers are fine', and it is a design choice, not a detail."
---
::

## Sync: select fields, not objects

The instinct is to sync everything and decide later. Resist it.

::tip{icon="i-lucide-filter"}
**Sync narrow.** Every extra field is time on every run and space in the store, and an object synced wholesale drags along dozens of fields nobody will ever group by. Start with the fields your recipes actually use; adding one later takes a minute, and you will know why you added it.
::

The one exception worth making deliberately: fields you will need **history** for. Because a snapshot dataset can only remember what was synced at the time, a field you start syncing in March has no February values and never will. If a field is likely to matter for trend analysis, sync it before you need it.

## The integration user is the silent filter

Sync runs as a specific user — the **integration user** — and it can only see what that user can see.

::warning{icon="i-lucide-eye-off"}
**This failure is invisible.** If the integration user lacks field-level access to `Discount__c`, the field does not arrive. The recipe does not error. The dataset builds cleanly. The dashboard shows a number that is simply computed without discounts, and it looks entirely plausible. Rows missing rather than duplicated is nearly always this, or the security predicate. Section 2 covers both properly — it is the single highest-value administrative topic in this course.
::

## Recipes, and the word dataflow

A **recipe** is the current tool: a visual pipeline you assemble from nodes — input, join, filter, formula, aggregate, transform, output — with a preview at each step.

A **dataflow** is the predecessor: the same idea defined as JSON, edited in a much less forgiving editor. Orgs built years ago are full of them and they still run.

    note: "The subtle one: a recipe scheduled before the sync it depends on finishes. It succeeds, using yesterday's data, every single night, and nothing ever errors."

::note{icon="i-lucide-list-ordered"}
**Debug in pipeline order, not in panic order.** Monitor first: did it run, when, how many rows. Then the recipe's node previews, which localise a grain problem in about a minute. Then the dataset's field types. The dashboard is last, and it is rarely the culprit — it usually just reports faithfully what it was handed.
::

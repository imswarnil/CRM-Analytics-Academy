# Editing Safely

Dashboards are org metadata with no real version history. Whatever discipline exists is the discipline you bring.

## The four habits

::lesson-steps
---
items:
  - title: "Export before you edit"
    description: "Every time, without exception. The undo story for a hand edit is the copy you saved beforehand, and the moment you need it is the moment you did not take one."
  - title: "Validate before saving"
    description: "Paste into any JSON validator. A trailing comma or an unbalanced brace produces a file that will not load, and the error you get back is rarely as specific as the one a validator gives you."
  - title: "Round-trip in the builder"
    description: "Reload and confirm it still opens and still edits visually. Valid JSON the builder cannot reconstruct is the failure mode that matters, and it shows up here rather than in a validator."
  - title: "Check as a restricted user"
    description: "Same rule as everywhere else in this course. Edits that change steps or filters can interact with row-level security in ways that are invisible from an administrator's account."
---
::

## Diffs are the real prize

::note{icon="i-lucide-git-compare"}
**JSON is text, so a change becomes a diff.** That turns "I updated the pipeline dashboard" — unreviewable, and forgotten within a week — into fourteen lines showing exactly which thresholds moved and which filter was added. It is the closest thing to change control this product has, and it costs nothing more than keeping the exported files somewhere with history.
::

A workable, low-ceremony version:

- Export each production dashboard's JSON into a repository, one file per dashboard.
- Re-export after any significant change and commit it with a sentence about why.
- When a number is disputed, the history answers *what changed and when* directly — which is usually the entire investigation.

This is not deployment automation; the dashboards still live in the org. It is a record, and a record is what you want at the moment somebody asks why the figure moved in March.

## Bulk edits, done carefully

::warning{icon="i-lucide-search-x"}
**Find-and-replace is the reason to be here and the way to break everything.** Renaming a field with a short, common name — `Amount`, `Type`, `Region` — will also hit it inside titles, labels and unrelated properties. Match on more context than the bare word, review each replacement rather than replacing all, and keep the edit narrow enough that the diff is readable afterwards.
::

## What not to hand-edit

::compare-cols
---
items:
  - title: "Safe to edit as text"
    subtitle: "Mechanical, repetitive"
    icon: "i-lucide-check"
    pros:
      - "Formatting across many widgets"
      - "Titles, labels, thresholds"
      - "Re-pointing steps after a dataset rename"
      - "Deleting orphaned layout entries"
    cons:
      - "Still needs the round-trip test"
    verdict: "This is the everyday, valuable use."
  - title: "Leave to the builder"
    subtitle: "Structural"
    icon: "i-lucide-x"
    pros:
      - "The builder keeps widgets, steps and every layout consistent"
    cons:
      - "Hand-adding a widget means adding it to each layout correctly, by hand"
      - "Hand-written structures may not round-trip"
    verdict: "Adding and removing widgets belongs in the interface."

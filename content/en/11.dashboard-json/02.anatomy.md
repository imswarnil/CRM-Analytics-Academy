# Anatomy of a Dashboard

Four parts, and once you know which is which, an unfamiliar dashboard file stops being intimidating.

## The four parts

::field-table
---
dataset: top-level structure
grain: one row per part
fields:
  - name: "state"
    type: "the container"
    role: "key"
    note: "Wraps everything below — the dashboard's own settings plus the three collections. When documentation says 'the dashboard JSON', this is usually what it means."
  - name: "steps"
    type: "where data comes from"
    role: "key"
    note: "Query definitions, each with a name. A step names its dataset, its groupings and measures, any filters, and often the SAQL itself. Widgets reference steps by name, which is why naming them properly matters."
  - name: "widgets"
    type: "what is drawn"
    role: "dimension"
    note: "One entry per visible element: type (chart, table, number, text, filter), which step feeds it, and its display parameters -- title, formatting, colours, faceting behaviour."
  - name: "layouts"
    type: "where things sit"
    role: "dimension"
    note: "Position and size, separately from the widgets themselves. Usually several layouts for different screen widths, which is why a change that looks right in the builder can be wrong on a phone."
---
::

## How they reference each other

A widget does not contain its query; it **names a step**. Several widgets can name the same step, which is exactly how a headline number, a bar chart and a table can share one query rather than issuing three.

::tip{icon="i-lucide-merge"}
**Reading the JSON is the fastest way to audit dashboard performance.** Count the steps and count the widgets. Twelve widgets against eleven steps means almost nothing is shared and the screen is making eleven round trips; twelve widgets against four steps is a dashboard somebody thought about. This audit takes thirty seconds in a text editor and is awkward to perform in the builder at all.
::

## Finding your way around

::lesson-steps
---
items:
  - title: "Start from the widget you can see"
    description: "Find its title text in the file, note which step it names, then find that step. Two searches and you are looking at the query behind the thing on screen."
  - title: "Follow the step to its dataset"
    description: "The step names the dataset and either its grouping and measure structure or raw SAQL. This is where you find out what a widget actually asks for — including filters the builder applied that you did not."
  - title: "Check the layouts last"
    description: "If something is positioned oddly, the widget is fine and a layout is wrong. Looking in the widget for a positioning problem is the most common way to waste ten minutes in here."
  - title: "Search for bindings by their syntax"
    description: "Bindings appear inline as string expressions inside step or widget properties. Searching for the binding syntax lists every one on the dashboard — which is the only way to see them all at once, and much faster than opening thirty panels."
---
::

::note{icon="i-lucide-search"}
**That last point is the best reason to open the file on a dashboard you inherited.** The previous section said bindings are invisible in the interface; in the JSON they are greppable. Ten seconds of searching gives you the dependency map that would otherwise take an afternoon of clicking — and that map is what you should then write into the dashboard's description.
::

## Names are the readable layer

Step names propagate everywhere: widgets reference them, bindings reference them, and they are what you read when tracing anything.

`step_7` tells you nothing. `closed_won_by_segment` tells the next person what the query is for before they read a line of it — and since bindings reference steps by name, good names are the difference between a legible arrangement and a puzzle.

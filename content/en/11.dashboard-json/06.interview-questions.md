interview:
  - q: "Have you worked with dashboard JSON, and what for?"
    a: "Mostly for bulk edits and for review. Renaming a field across thirty widgets or re-pointing every step after a dataset rename is one find-and-replace in text and thirty configuration panels in the builder, with a decent chance of missing one. And because JSON is text it diffs, which turns 'I updated the dashboard' into a reviewable list of exactly what changed. What I avoid is using it to do ordinary work the builder does perfectly well, because hand-written structures may not round-trip and then only I can maintain the dashboard."
  - q: "What are the parts of a dashboard document?"
    a: "State wrapping three collections: steps, widgets and layouts. Steps are the query definitions — dataset, groupings, measures, filters, sometimes raw SAQL — each with a name. Widgets are what is drawn, and they reference a step by name rather than containing a query. Layouts are position and size, separately and usually per breakpoint, which is why a widget that looks wrong on a phone is a layout problem and never a widget problem."
  - q: "How would you audit a slow dashboard from its JSON?"
    a: "Count steps against widgets. Eleven steps for twelve widgets means nothing is shared and the screen is making eleven round trips; four steps for twelve widgets is a screen somebody thought about. Then I look for steps that differ only in presentation — a headline number, a bar chart and a table over the same measure can usually be one query. That audit takes about thirty seconds in a text editor and is awkward to do in the builder at all."
  - q: "How do you find every binding on a dashboard you inherited?"
    a: "Search the JSON for the binding syntax. Bindings are invisible in the interface — they live in individual configuration panels — so in the builder finding them all means opening every widget. In the file they are greppable, and ten seconds gives you the dependency map that would otherwise take an afternoon. Then I write that map into the dashboard description so the next person does not repeat the exercise."
  - q: "What precautions do you take before editing?"
    a: "Export a copy first, every time — the undo story is whatever I saved beforehand. Validate before saving, because a trailing comma produces a file that will not load and a vaguer error than a validator gives. Round-trip it: reload in the builder and confirm it still opens and still edits visually, since valid JSON the builder cannot reconstruct is the failure that matters. And check it as a restricted user, because edits to steps and filters interact with row-level security in ways an admin account cannot see."
  - q: "Would you put dashboard JSON in version control?"
    a: "For production dashboards, yes — exported per dashboard, re-exported after significant changes, committed with a sentence about why. It is not deployment automation; the dashboards still live in the org. It is a record, and it is the closest thing to change control the product offers. When somebody asks why a number moved in March, the history usually is the whole investigation."
  - q: "What would you never hand-edit?"
    a: "Adding or removing widgets. The builder keeps the widget, its step and every layout consistent; by hand I would have to add it to each breakpoint correctly and the failure is silent — a widget present on desktop and simply absent on a phone. Mechanical, repetitive changes as text; structural changes in the interface."

# Dashboard JSON: Interview Questions

This question is usually a proxy. The interviewer wants to know whether you have maintained dashboards at scale, because that is who ends up in the JSON.

::note{icon="i-lucide-star"}
**The answer that lands is the audit one** — counting steps against widgets to explain a slow dashboard. It is concrete, it is a thing you can only know by having done it, and it shows you treat performance as something to measure rather than something to guess at.
::

## The three sentences worth memorising

1. **"Steps are queries, widgets reference them by name, layouts are position per breakpoint."**
2. **"Count steps against widgets — that is the load-time story."**
3. **"Export before editing; the undo story is whatever you saved."**

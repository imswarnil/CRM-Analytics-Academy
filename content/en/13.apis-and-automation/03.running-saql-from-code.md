# Running SAQL from Code

You send a query, you get rows back. The mechanics take an afternoon; the discrepancies take longer.

## What it is good for

## Reading the response

Results come back as JSON: a set of records, each a map of column names to values. Two things to handle rather than assume:

- **Column names come from the query's `generate` aliases**, so renaming an alias renames a key in the response and breaks whatever consumes it. Pin the names deliberately and keep them stable.
- **Types are what the dataset says they are.** Dates arrive in the dataset's representation rather than as your language's date object, and numbers may arrive as strings depending on the client. Parse explicitly instead of trusting the shape.

## Why the number differs from the dashboard

Four reasons, all legitimate, and worth checking in this order:

::field-table
---
dataset: discrepancy causes
grain: one row per cause
fields:
  - name: "A different user"
    type: "most common"
    role: "key"
    note: "Row-level security applies to the API exactly as it does to the interface. A script running as an integration user with broad access will legitimately see more than a regional viewer does. Neither number is wrong; they answer the question for different people."
  - name: "A relative date range"
    type: "time moved"
    role: "date"
    note: "'Last 90 days' means something different at 23:00 than at 01:00, and different again tomorrow. Correct for a live dashboard, and a trap when reconciling — for that, pin absolute dates."
  - name: "The dataset refreshed between the two reads"
    type: "materialisation"
    role: "date"
    note: "The dashboard was opened before the nightly run and the script ran after it. The first question about any wrong number is still when it last ran."
  - name: "The query is not the same query"
    type: "the honest answer"
    role: "measure"
    note: "The dashboard's widget carries filters from the step, the dashboard filter and the current selection. A hand-written query reproducing 'the same' metric frequently omits one — usually the selection, because it is invisible in the JSON."
---
::

::tip{icon="i-lucide-copy"}
**Start from the dashboard's own query rather than writing one from scratch.** Copy the SAQL out of the step, then add the filters the selection was applying. Reconciling two independently-written queries is a much harder problem than adapting one, and most of the time the discrepancy turns out to be a filter nobody remembered.
::

## Determinism for reconciliation

::warning{icon="i-lucide-calendar-clock"}
**A reconciliation job must pin its dates.** Comparing a rolling window against a source system produces a difference every time the clock moves, and you will spend an afternoon investigating a discrepancy that is entirely an artefact of when the two queries ran. Absolute start and end, computed once at the top of the job and used for both sides.
::

## Keep the query in the repository

A query that runs on a schedule is code. Keep it in the repository with the job, not pasted into a scheduler's text box where it cannot be reviewed, diffed or explained — and where nobody will find it when the number it produces is questioned.

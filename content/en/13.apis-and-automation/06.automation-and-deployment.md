# Automation and Deployment

The scripts are the easy half. Making them run reliably, and making changes reviewable, is the half that decides whether any of it survives.

## Scheduling and ordering

The dependency trap from the data preparation section is worse with scripts, because a script does not appear in the platform's own monitor:

::warning{icon="i-lucide-clock-alert"}
**A load that runs after the recipe that consumes it produces a dashboard that is always one day behind, successfully, forever.** Everything reports green. Order the chain explicitly — load, then sync, then recipes — with real headroom rather than optimistic gaps, and prefer a job that *checks* its dependency completed over one that merely starts later and hopes.
::

## Failure handling

::field-table
---
dataset: failure design
grain: one row per decision
fields:
  - name: "Retry transient errors"
    type: "with backoff"
    role: "measure"
    note: "Rate limits and network blips are normal operation, not exceptions. Retry a few times with increasing delay. What must not be retried blindly is a load that partially succeeded -- that needs the job's state checked first."
  - name: "Fail loudly"
    type: "non-zero exit"
    role: "key"
    note: "The scheduler reads exit codes; nobody reads logs. A job that swallows an error and exits zero is worse than one that crashes, because the crash is visible."
  - name: "Alert somewhere people are"
    type: "not an inbox nobody reads"
    role: "dimension"
    note: "A channel the team already watches. And keep the alert quiet enough to stay meaningful -- the collaboration section's threshold argument applies here: an alert that fires most nights is filtered within a fortnight."
  - name: "Make it resumable"
    type: "for long jobs"
    role: "measure"
    note: "A load interrupted at part 40 of 60 should resume rather than restart. Same principle as the translation pipeline in this repository: save progress as you go so a failure costs minutes rather than the whole run."
---
::

## Credentials

One rule, applied without exception: **the script never contains a secret.** Environment variables sourced from a secret store or the CI provider's secret storage, a dedicated integration user, and rotation that somebody owns. A credential in a public repository is not embarrassing, it is an incident.

## Change history for dashboards

The JSON section made the case; this is the mechanism.

::lesson-steps
---
items:
  - title: "Export the metadata on a schedule"
    description: "Dashboards, and recipe definitions if you can reach them. Nightly is plenty. One file per artefact, named for the artefact rather than its id."
  - title: "Commit into a repository"
    description: "The diff is the product. 'The pipeline dashboard changed on the 14th, and here are the four lines that moved' is a complete answer to the question people actually ask."
  - title: "Review significant changes"
    description: "Not every edit needs a review, but a change to a definition or a threshold on a dashboard the exec team reads is worth a second pair of eyes. The diff makes that possible in a product with no built-in review at all."
  - title: "Keep it separate from deployment"
    description: "This is a record, not a pipeline. Restoring from it is a deliberate act. Conflating backup with deployment is how a well-meant automation overwrites somebody's afternoon of work."
---
::

## Sandbox to production

Moving analytics work between orgs is genuinely awkward: datasets are org-local, ids differ, and a dashboard exported from one org references things that may not exist in the other.

::tip{icon="i-lucide-map"}
**Automate the repeatable part and keep a written checklist for the rest.** Dashboard JSON can be templated and pushed; dataset ids, security predicates and schedules usually need attention per org. A checklist that is honest about which steps are manual beats a script that pretends they are not and silently deploys a dashboard pointing at a dataset that does not exist.
::

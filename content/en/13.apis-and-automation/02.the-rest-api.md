# The REST API

Salesforce exposes analytics through its REST API: datasets, queries, dashboards and the metadata behind them.

## Authentication

Requests carry an OAuth access token, obtained through a connected app. Two practical points matter more than the mechanics:

::lesson-steps
---
items:
  - title: "Use a dedicated integration user"
    description: "Not a person. A person leaves, their account is deactivated, and every job that authenticated as them stops on a day nobody predicted. A named integration account with only the permissions it needs also makes an audit trail meaningful."
  - title: "Keep credentials in a secret store"
    description: "Environment variables from a managed store, a vault, or the CI provider's secret storage. Never in the script, never in a notebook, never in the repository — and a public repo makes that irreversible rather than embarrassing."
  - title: "Handle token expiry as normal operation"
    description: "Tokens expire; that is the design. A job that dies overnight on an expired token is a job that did not implement refresh. Assume a run may span an expiry."
  - title: "Give the integration user only what it needs"
    description: "A loader needs to write datasets, not to read every object in the org. Narrow permissions limit the blast radius of a leaked credential, and they make it obvious what the job is for."
---
::

## Versioning

Endpoints carry a version in the path. Pin it.

::note{icon="i-lucide-pin"}
**A pinned version is a script that keeps working when the platform updates, and an unpinned one is a script that changes behaviour on a date somebody else chose.** Upgrade deliberately: change the version, run against a sandbox, confirm the response shape is what you expect, then ship. This is a two-minute habit that prevents the class of failure where nothing in your repository changed and the job broke anyway.
::

## Limits to design around

Every platform has them and the specific numbers move, so the durable advice is about shape rather than figures:

::compare-cols
---
items:
  - title: "Shapes that scale"
    subtitle: "Work with the limits"
    icon: "i-lucide-check"
    pros:
      - "Batch — one call with many rows rather than many calls with one"
      - "Incremental — send what changed, not everything, every night"
      - "Back off and retry on a rate-limit response rather than hammering"
      - "Check the current limits for your edition before sizing anything"
    cons:
      - "More code than the naive version"
    verdict: "Write it this way from the start."
  - title: "Shapes that fail at scale"
    subtitle: "Fine in a test, not in production"
    icon: "i-lucide-x"
    pros:
      - "Simple, and works beautifully against 100 rows"
    cons:
      - "A call per row exhausts the daily allowance and starves everything else in the org"
      - "A full reload every night when 2% of rows changed"
      - "No retry, so one transient error loses the whole run"
    verdict: "This is how an analytics job takes down an org's API budget."
---
::

::warning{icon="i-lucide-gauge"}
**API limits are org-wide.** A greedy analytics job does not only slow itself down — it consumes allowance that integrations, mobile clients and other teams are also drawing on. That makes a badly shaped loader an operational problem for people who have never heard of your dashboard, and it is the reason to batch before anybody asks you to.
::

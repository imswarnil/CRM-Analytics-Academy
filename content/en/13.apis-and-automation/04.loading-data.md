# Loading Data

The external data API is how anything without a connector gets into CRM Analytics: a warehouse extract, a vendor file, Namilio's web sessions and spend.

## Three steps, in order

::lesson-steps
---
items:
  - title: "Declare the job"
    description: "Create a record describing what you are about to load: the dataset name, the operation — overwrite, append, upsert, delete — and the metadata describing the fields. Nothing has been uploaded yet."
  - title: "Upload the data in parts"
    description: "The rows go up as numbered parts rather than as one payload. Each part is a chunk of the file, and the numbering is how the platform reassembles them. Large loads are many parts; small ones are one."
  - title: "Signal completion"
    description: "Set the job's status to indicate all parts are sent. Only now does processing begin. Skipping this is the failure everybody hits once, and it produces no error — the parts simply sit there and no dataset appears."
---
::

::warning{icon="i-lucide-flag"}
**The silent failure is forgetting step three.** The declare succeeded, every part uploaded successfully, nothing errored — and there is no dataset. A job left un-signalled is indistinguishable from a job still in progress. When a load "worked but produced nothing", check the job's status before anything else.
::

## The metadata file decides your field types

The metadata sent with the declaration tells the platform what each field is: its name, its label, and whether it is text, numeric or date — along with formats and precision.

::note{icon="i-lucide-type"}
**This is the CSV-upload lesson from the data preparation section, in code.** The same three mistakes, with the same costs, and now they are in a file you control rather than a dialog you clicked through: a date declared as text can never be trended, a numeric-looking ID declared as a measure will be summed by somebody eventually, and a currency with the wrong scale is out by a factor of a hundred with nothing to flag it. The advantage of doing it here is that the metadata is code — it is reviewable, diffable, and identical on every run.
::

## Operations

::field-table
---
dataset: load operations
grain: one row per operation
fields:
  - name: "Overwrite"
    type: "replace everything"
    role: "key"
    note: "Simplest and the right default for a moderate dataset rebuilt from source each night. Also the most expensive as volume grows, because you are sending everything to change a fraction."
  - name: "Append"
    type: "add rows"
    role: "measure"
    note: "For accumulating data -- events, and the snapshot pattern from the datasets and modelling section, where each run adds a new period rather than restating the whole history."
  - name: "Upsert"
    type: "update or insert by key"
    role: "key"
    note: "The incremental option, and it depends entirely on a genuinely unique key. A key that is not unique quietly merges rows that should be separate, which surfaces later as a count that is too low."
  - name: "Delete"
    type: "remove by key"
    role: "dimension"
    note: "For records that disappeared at source. Without it, an overwrite is the only way to lose a deleted row, and an append-only pipeline keeps records the source no longer has."
---
::

## Incremental is not automatically better

::compare-cols
---
items:
  - title: "Full overwrite"
    subtitle: "Send everything"
    icon: "i-lucide-refresh-cw"
    pros:
      - "Self-correcting — a bad run is fixed by the next good one"
      - "No key required, no drift possible"
      - "Far easier to reason about at 2am"
    cons:
      - "Wasteful as the dataset grows"
      - "Longer run, larger API footprint"
    verdict: "Right until volume makes it wrong. Start here."
  - title: "Incremental upsert"
    subtitle: "Send what changed"
    icon: "i-lucide-git-pull-request"
    pros:
      - "Fast, small, cheap on API allowance"
      - "Necessary at large volumes"
    cons:
      - "Needs a reliable change marker and a genuinely unique key"
      - "Drifts silently when a change is missed — nothing errors, the dataset is just slightly wrong, forever"
      - "Needs periodic full reconciliation to catch that"
    verdict: "Adopt when volume demands it, with a reconciliation job."
---
::

::tip{icon="i-lucide-check-check"}
**Whichever you choose, verify the row count after the load.** Read the dataset's metadata and compare against what you sent. It is a few lines of code, it runs every night, and it catches the partial load that would otherwise be discovered by somebody looking at a dashboard a week later.
::

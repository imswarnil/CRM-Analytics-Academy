# Python End to End

The shape of a real loader, in the order you would write it. The specific library matters less than the sequence — the same five stages apply whether you use a Salesforce SDK, a REST client, or plain requests.

## The five stages

::lesson-steps
---
items:
  - title: "Authenticate as the integration user"
    description: "Credentials from environment variables, never from the file. Obtain a token, and wrap the call so an expiry mid-run refreshes rather than dying."
  - title: "Read and prepare the data"
    description: "Load the source — the Academy's web_sessions.csv, or a warehouse query — and shape it to match the metadata you are about to declare. Column names, types and order settled here, not improvised during upload."
  - title: "Declare the job"
    description: "Dataset name, operation, and the field metadata. This is the file that decides whether your dates are dates; keep it in the repository next to the script so it is reviewable."
  - title: "Upload in numbered parts and signal completion"
    description: "Chunk the rows, send each part with its number, then set the job to complete. The completion signal is the step that is forgotten, and forgetting it produces no error and no dataset."
  - title: "Verify, then report"
    description: "Read back the dataset's row count and compare it against what you sent. Log both. A loader that does not verify is a loader that fails quietly."
---
::

## The skeleton

```python
import os, csv, json, math, requests

BASE   = os.environ["SF_INSTANCE_URL"]        # from the secret store
TOKEN  = get_access_token()                    # refreshable
HEAD   = {"Authorization": f"Bearer {TOKEN}"}
CHUNK  = 10_000                                # rows per part

def declare(dataset, operation, metadata):
    """Create the upload job. Nothing is sent yet."""
    body = {"Format": "Csv", "EdgemartAlias": dataset,
            "Operation": operation, "Action": "None",
            "MetadataJson": metadata}
    r = requests.post(f"{BASE}/services/data/v62.0/sobjects/InsightsExternalData",
                      headers=HEAD, json=body, timeout=60)
    r.raise_for_status()
    return r.json()["id"]

def upload_parts(job_id, rows, header):
    """Send the rows as numbered parts. Part numbers start at 1."""
    for i in range(0, len(rows), CHUNK):
        part = i // CHUNK + 1
        payload = encode_csv(header, rows[i:i + CHUNK])
        post_part(job_id, part, payload)

def complete(job_id):
    """The step that is forgotten. Until this runs, nothing is processed."""
    requests.patch(f"{BASE}/services/data/v62.0/sobjects/InsightsExternalData/{job_id}",
                   headers=HEAD, json={"Action": "Process"}, timeout=60).raise_for_status()
```

::note{icon="i-lucide-code"}
**The endpoint paths and the exact metadata schema change between releases** — check the current documentation for your API version rather than copying a path from any blog post, including this one. What does not change is the sequence: declare, parts, complete, verify. Learn the shape and look up the details.
::

## Verification is the part that earns its keep

```python
expected = len(rows)
actual   = dataset_row_count(dataset)          # read back from metadata
if actual != expected:
    raise SystemExit(f"load mismatch: sent {expected}, dataset holds {actual}")
```

::tip{icon="i-lucide-shield-check"}
**Fail loudly on a mismatch rather than logging a warning.** A job that exits zero after loading 80% of the rows produces a dashboard that is quietly wrong for as long as it takes somebody to notice — which, on a number nobody has a prior for, can be months. An exit code is read by the scheduler; a warning in a log is read by nobody.
::

## Querying the result back

The same session can run SAQL, which makes a reconciliation step natural at the end of a load: pull the total the dataset now reports and compare it against the source system's own figure. That is the answer-key habit from the APIs section automated — and it is the single most valuable thing a loader can do beyond loading.

## Running it

Whatever runs it — cron, a CI schedule, an orchestrator — needs three things: the schedule, the credentials from a secret store, and somewhere the failure is *seen*. A job that fails into a log directory nobody opens is a job that is not running, and you find out weeks later.

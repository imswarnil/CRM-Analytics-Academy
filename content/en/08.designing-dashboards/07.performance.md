# Performance

A dashboard that takes twelve seconds is a dashboard people stop opening. The causes are few and the fixes are mostly structural rather than clever.

## Count the queries, not the widgets

Every widget is fed by a query. Several widgets can share one — and when they do not, a screen with twelve widgets issues twelve queries.

::tip{icon="i-lucide-merge"}
**This is the biggest lever available, and it is usually free.** A headline number, a bar chart and a table showing the same measure sliced three ways frequently *can* share a single query. Consolidating is often the difference between twelve seconds and two, and it changes nothing about how the dashboard looks or behaves.
::

## The grain trade

Section 3 said a dataset's grain is a decision. Here is where you pay for it:

::compare-cols
---
items:
  - title: "Fine grain"
    subtitle: "Every row preserved"
    icon: "i-lucide-microscope"
    pros:
      - "Any question is answerable from it"
      - "One dataset serves many dashboards"
    cons:
      - "Every widget aggregates a lot of rows, on every load, for every viewer"
      - "Fan-out risk is handed to every designer who touches it"
    verdict: "Right for exploration, expensive for an exec board."
  - title: "Pre-aggregated"
    subtitle: "Summarised in the recipe"
    icon: "i-lucide-box"
    pros:
      - "Fast — the aggregation happened once, overnight"
      - "The definition is settled upstream, so nobody can compute it differently"
    cons:
      - "Questions below the chosen grain are no longer answerable"
      - "Another dataset to schedule and maintain"
    verdict: "Right for a dashboard many people open daily."
---
::

::note{icon="i-lucide-layers"}
**The normal production answer is both.** A fine-grained dataset for exploration, and a pre-aggregated one behind the dashboard everyone opens. Section 7's warehouse is built this way deliberately: the tables you explore are not always the tables the executive board reads.
::

## The other causes, in rough order

::field-table
---
dataset: what makes dashboards slow
grain: one row per cause
fields:
  - name: "Too many distinct queries"
    type: "most common"
    role: "measure"
    note: "Twelve widgets each running their own. Consolidate what can share, and the change is invisible to users except that the page appears."
  - name: "Aggregating fine grain at query time"
    type: "common"
    role: "measure"
    note: "Millions of rows summed per widget per load. Pre-aggregate in the recipe if the dashboard is opened daily by many people."
  - name: "Very wide tables"
    type: "common"
    role: "dimension"
    note: "A values table with twenty columns and hundreds of rows is slow to query and unreadable anyway. Cutting it to five columns and ten rows fixes both problems at once."
  - name: "Complex bindings"
    type: "occasional"
    role: "dimension"
    note: "Chained bindings can force sequential rather than parallel queries: widget C waits for B, which waits for A. Worth checking when a dashboard is slow in a way that does not match its widget count."
  - name: "Row-level security evaluation"
    type: "structural"
    role: "key"
    note: "Predicates and especially sharing inheritance cost something per query per viewer. This is a correct cost, not a defect — but it is a reason a dashboard is slower for a viewer with complex access than it is for you."
---
::

## How to actually measure it

::lesson-steps
---
items:
  - title: "Load it as a normal user, not as yourself"
    description: "Your admin account may skip security evaluation that a real viewer pays for on every query. Testing performance as an administrator can understate it substantially."
  - title: "Watch which widgets arrive last"
    description: "They render as their queries return, so the slow ones announce themselves. Usually it is the widest table and the finest-grained chart."
  - title: "Count the distinct queries"
    description: "The dashboard's query list shows them. If there are more queries than there are genuinely distinct questions on the screen, there is a consolidation to make."
  - title: "Fix structure before cleverness"
    description: "Consolidate queries, cut table columns, pre-aggregate if warranted. Only then consider anything exotic — and if the answer requires cleverness, the dashboard is probably doing too much."
---
::

::warning{icon="i-lucide-hourglass"}
**Slow dashboards fail quietly.** Nobody files a ticket saying "this takes eleven seconds". They open it less, then they ask you for the number instead, then they keep their own spreadsheet — and the spreadsheet disagrees with the dashboard, which is how an org ends up with two truths. By the time anyone complains, the dashboard has already lost.
::

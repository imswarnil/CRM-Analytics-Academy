# Tables, KPIs and Micro Charts

Three families do most of the work on a decision dashboard. Charts get taught; these get used.

## KPI tiles

A single number, prominently. The number alone is nearly useless — it needs a comparison and a direction:

::lesson-kpis
---
columns: 4
items:
  - label: "Net New ARR"
    value: "$1.42M"
    delta: "+8.3% vs plan"
    trend: "up"
    good: true
    hint: "Comparison and direction included"
    spark: [820, 910, 1040, 980, 1180, 1310, 1420]
  - label: "Net Revenue Retention"
    value: "112%"
    delta: "+3pt QoQ"
    trend: "up"
    good: true
    hint: "The single most predictive number"
    spark: [104, 106, 105, 108, 109, 111, 112]
  - label: "CAC Payback"
    value: "14.2 mo"
    delta: "−1.1 mo"
    trend: "down"
    good: true
    hint: "Down is good here — set goodness per metric"
    spark: [17.1, 16.8, 16.2, 15.9, 15.1, 15.3, 14.2]
  - label: "Accounts at Risk"
    value: 11
    delta: "+3 MoM"
    trend: "up"
    good: false
    hint: "Under 55% utilisation"
    spark: [6, 7, 7, 8, 9, 8, 11]
---
::

::note{icon="i-lucide-gauge"}
**Three ingredients make a tile actionable:** the number, a comparison that gives it scale, and a direction that says whether to be pleased. Note the third tile — CAC payback falling is good news, so its downward arrow is green. Goodness is a property of the metric, not of the arrow's direction, and getting that wrong turns a good quarter into a wall of red.
::

## Sparklines

A tiny chart inside the tile, showing the last several periods. It answers "is this normal?" — which is the question a single number always provokes and can never answer.

::tip{icon="i-lucide-activity"}
**A sparkline is worth more than a second chart** because it costs almost no space and no attention. A KPI of 112% means little; 112% at the end of a line that has climbed steadily for seven months means something quite specific. Add sparklines before you add another chart.
::

## Tables

Charts show shape. Tables show identity. When the answer is "which specific account", a table is not a fallback — it is the correct widget:

::field-table
---
dataset: when to use a table
grain: one row per case
fields:
  - name: "Identity matters"
    type: "use a table"
    role: "key"
    note: "'Which ten accounts are at risk' needs names. A bar chart of ten account names is unreadable, and the names are the entire point."
  - name: "Several attributes per row"
    type: "use a table"
    role: "dimension"
    note: "Account, segment, ARR, utilisation, owner. A chart can show two of those; a table shows all five and lets the reader scan."
  - name: "An exception list"
    type: "use a table"
    role: "measure"
    note: "Short by construction, and empty when things are going well — which is the ideal state and needs an empty-state message so nobody thinks it broke."
  - name: "Everything, all rows"
    type: "do NOT"
    role: "measure"
    note: "140 rows with a scrollbar is an export, not a dashboard. If people genuinely need the full list, give them a download and keep the dashboard to the top ten."
---
::

::warning{icon="i-lucide-scroll"}
**The scrollbar is the tell.** A table nobody can take in without scrolling has stopped being a dashboard widget and become a data delivery mechanism. That is a legitimate need — the dashboard design section covers downloading properly — but it should not occupy the screen six people check every morning.
::

## Formatting that makes the difference

- **Right-align numbers** so digits line up and magnitudes are comparable at a glance.
- **Consistent decimals** in a column; mixed precision reads as carelessness and slows comparison.
- **Abbreviate large numbers** — $1.42M rather than $1,420,000 — on tiles, and keep full precision in the table for whoever needs it.
- **Sort by what matters**, which is almost never alphabetical.

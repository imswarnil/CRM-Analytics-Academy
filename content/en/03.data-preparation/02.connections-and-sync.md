# Connections and Sync

Two stages that feel like plumbing and decide how current every number on every dashboard is.

## Connections

A **connection** is credentials plus a reachable endpoint. The local Salesforce org is connected by default; everything else is configured once and then referenced:

- **Another Salesforce org** — common in companies that run more than one.
- **A warehouse** — Snowflake, BigQuery, Redshift and similar.
- **Object storage and databases** — S3, and direct database connections.
- **A CSV upload** — not really a connection, but the same destination.

::note{icon="i-lucide-key"}
**Credentials expire, and this is the friendliest failure in the whole pipeline** — the run stops and says so. Compare that with a permission problem, which silently drops a column. When a connection breaks you find out immediately, which is worth appreciating while you are debugging something quieter.
::

## What sync actually does

Data sync pulls **selected objects** and **selected fields** into CRM Analytics' own store on a schedule. Recipes then read that local copy.

Two reasons this exists:

1. **Speed.** A recipe joining five objects would otherwise query the source five times per run.
2. **Politeness.** The system of record is a production CRM serving live users; an analytics job should not be hammering it every hour.

The consequence worth internalising: **there are two clocks.** Sync has a schedule, and recipes have a schedule. The data on a dashboard is as old as the *earlier* of the two, plus however long the run took.

## The dependency trap

::warning{icon="i-lucide-clock-alert"}
**A recipe scheduled before the sync it depends on has finished will run successfully, on yesterday's data, every single night, forever.** Nothing errors. The Monitor tab shows green. The dashboard shows numbers that are exactly one day stale, consistently enough that nobody questions them — until someone compares against a report and the investigation takes a week. When a stakeholder says "the numbers feel a day behind", believe them and check the two schedules before anything else.
::

The fix is ordering, with real headroom: sync at 01:00, recipes at 03:00, not 01:30. A sync that usually takes twenty minutes will one day take fifty.

## Choosing a schedule

::compare-cols
---
items:
  - title: "Nightly"
    subtitle: "The default, and usually correct"
    icon: "i-lucide-moon"
    pros:
      - "Cheap, predictable, plenty of headroom"
      - "Matches how most go-to-market decisions are actually made"
      - "Runs when nobody is querying"
    cons:
      - "Anything happening today is invisible until tomorrow"
    verdict: "Start here. Move only with a reason."
  - title: "Hourly or more often"
    subtitle: "When the decision genuinely needs it"
    icon: "i-lucide-timer"
    pros:
      - "Same-day pipeline changes visible"
      - "Right for a team working leads within the hour"
    cons:
      - "More load, more cost, more failure surface"
      - "Tempting to grant because it sounds better, not because it is needed"
    verdict: "Justify it with a decision, not a preference."
---
::

::tip{icon="i-lucide-message-circle-question"}
**The question that settles the schedule argument** is not "how fresh would you like it" — everyone answers "as fresh as possible", and they are not wrong to. It is "**what would you do differently if this were an hour old instead of a day old?**" If there is no answer, nightly is correct and you have just saved the org money and yourself a maintenance burden.
::

## Sync narrow, but sync early

The tension from the data preparation section, restated here because this is where you act on it:

**Narrow**, because every field costs time and space on every run. **Early**, because a snapshot can only remember what was synced at the time. A field first synced in March has no February values and never will — the Salesforce object holds only current state, and history cannot be reconstructed from it.

The practical rule: be sparing with long text and rarely-used descriptive columns; be generous with **dates, owners, stages, segments and amounts**, because those are what you will eventually want to trend.

## What Monitor tells you

Data Manager → Monitor is the pipeline's log, and it answers four questions that between them explain most incidents:

::field-table
---
dataset: Monitor
grain: one row per question
fields:
  - name: "Did it run?"
    type: "status"
    role: "key"
    note: "A failed run is the easy case. A run that never started — because a schedule was disabled, often during a release — is the one that surprises people."
  - name: "When?"
    type: "timestamp"
    role: "date"
    note: "The single most useful number when someone says a figure is wrong. Roughly a third of 'wrong number' reports end here."
  - name: "How many rows?"
    type: "count"
    role: "measure"
    note: "Watch this over time. A dataset that has held ~2,800 rows for months and suddenly holds 2,100 has a problem upstream that no dashboard will report."
  - name: "How long?"
    type: "duration"
    role: "measure"
    note: "Creeping duration is the early warning for the dependency trap: the sync that took twenty minutes now takes fifty, and it is about to collide with the recipe that follows it."
---
::

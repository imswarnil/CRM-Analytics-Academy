# Troubleshooting a Recipe

A method, in order, so that debugging is a procedure rather than an improvisation.

## The order

::lesson-steps
---
items:
  - title: "Monitor first"
    description: "Did it run, when, and how many rows? Roughly a third of 'the number is wrong' reports end here — the answer is that it last ran on Friday. This takes fifteen seconds and rules out the largest single category."
  - title: "Compare the row count against history"
    description: "A dataset that held ~2,800 rows for months and now holds 2,100 has a problem no dashboard will report. If your org does not track this, note the expected counts somewhere — it is the cheapest regression test available."
  - title: "Walk the node previews"
    description: "Click each node in order and read its row count. The node where the count changes unexpectedly is the node with the problem. This localises a grain issue in about a minute, which is why recipes beat dataflows for anything you will have to debug."
  - title: "Filter to one entity"
    description: "Pick a single account or opportunity, filter the preview to it, and count by hand. This tells you exactly which side multiplied or which rows vanished, where staring at an aggregate tells you nothing."
  - title: "Then, and only then, the dashboard"
    description: "Widget queries, faceting and filters are the last suspects. They usually report faithfully what they were given."
---
::

## Symptom to cause

::field-table
---
dataset: diagnosis table
grain: one row per symptom
fields:
  - name: "Total is 2× or 3×"
    type: "fan-out"
    role: "measure"
    note: "A parent measure duplicated across child rows. Walk the joins; the count jumps at the offending node."
  - name: "Total is slightly high"
    type: "partial fan-out"
    role: "measure"
    note: "Only some parents have multiple children. Harder to spot because it is not a clean multiple — the real-world default."
  - name: "Rows missing for everyone"
    type: "inner join or upstream filter"
    role: "key"
    note: "An inner join is a filter wearing a join's clothes. Also check a filter node whose condition excludes nulls unintentionally: 'Stage != Closed Lost' also removes every row where Stage is null."
  - name: "Rows missing for SOME users"
    type: "row-level security"
    role: "key"
    note: "Not a recipe problem at all. The predicate or sharing inheritance, per section 2. The tell is that it is fine for you and wrong for them."
  - name: "A column is entirely null"
    type: "sync or permissions"
    role: "dimension"
    note: "The field was not selected in sync, or the integration user cannot see it. It is absent rather than empty — check the input node's column list before rebuilding anything."
  - name: "Numbers change every run"
    type: "a non-deterministic recipe"
    role: "date"
    note: "Usually a relative date filter — 'last 30 days' moves — or a join on a non-unique key picking an arbitrary match. The second one is nastier: it is stable until the data changes underneath it."
  - name: "Everything is one day old"
    type: "schedule dependency"
    role: "date"
    note: "The recipe runs before the sync finishes. Green everywhere, consistently stale. Compare the two schedules and the actual run durations."
---
::

## Three habits that prevent most of it

::lesson-cards
---
columns: 3
items:
  - title: "Write the grain in the description"
    icon: "i-lucide-file-text"
    description: "'One row per opportunity per product.' Five seconds, and it prevents the next person from summing a duplicated measure without ever knowing they did."
  - title: "Know your expected counts"
    icon: "i-lucide-hash"
    description: "140 accounts, 677 opportunities, 2,800 leads. Numbers you recognise mean a wrong one announces itself. Analysts who know their data's shape catch problems that no automated check would flag."
  - title: "Check against something independent"
    icon: "i-lucide-check-check"
    description: "The README here; a finance figure or a previously trusted report in a real org. 'It looks about right' is not a check — it is the feeling you have just before being wrong in public."
---
::

::tip{icon="i-lucide-undo"}
**When a recipe breaks after a change you made, undo the change before investigating.** It is tempting to debug forward from a broken state; it is faster to return to a working one and re-apply the change in smaller pieces. This is ordinary engineering discipline, and it is unusually easy to abandon in a visual tool where each edit feels small.
::

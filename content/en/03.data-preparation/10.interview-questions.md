interview:
  - q: "What is fan-out and how do you prevent it?"
    a: "A one-to-many join multiplies rows on the one side, so any measure belonging to that side gets repeated and double-counted. Joining 677 opportunities to 1,378 product lines and summing the opportunity Amount turns $58M into $114M, with no error anywhere. Two fixes: aggregate the many side before the join so it collapses to one row per key, or keep the finer grain deliberately and do not carry the parent's measure down — sum the line-level amounts instead. Which one depends on whether the dataset is about deals or about products."
  - q: "How do you decide the grain of a dataset?"
    a: "From the questions it has to answer. Fine enough that the questions are answerable, coarse enough that nobody downstream has to re-solve fan-out for themselves. Then I write the grain into the dataset description — 'one row per opportunity per product' — because a dataset whose grain is undocumented is a trap for the next person."
  - q: "Where do you put a calculation: recipe or dashboard?"
    a: "Recipe, almost always, because computing it once means every dashboard agrees by construction. A definition that lives in eleven widgets becomes eleven definitions within a year, and when two screens disagree neither is wrong, which is harder to resolve than one being wrong. The dashboard is right only when the calculation genuinely depends on the viewer's current selection."
  - q: "Why is 'average discount' usually wrong?"
    a: "Because it is normally computed as the average of per-deal discount rates, which weights a $5,000 deal the same as a $2M one. The number the business means is total discount divided by total list value — aggregate both parts, then divide. The same trap appears as average conversion rate across reps and average utilisation across accounts. If I want the unweighted version I say so in the metric name, because everyone else assumes weighted."
  - q: "Why would you build a snapshot dataset?"
    a: "Because Salesforce objects hold only current state. An opportunity knows today's amount and stage and nothing about March, so pipeline movement, slipped deals, forecast accuracy and an ARR waterfall are all unanswerable from the object. A snapshot appends current state each run, accumulating history that cannot be reconstructed later — which is also why I set it up early, and why I sync dates, owners, stages and amounts generously from the start. A field added in March has no February values, permanently."
  - q: "Recipes or dataflows?"
    a: "Recipes for anything new: visual, with a preview at every node, so a grain problem localises in about a minute. Dataflows are the JSON predecessor, still running in older orgs, and I can read and maintain one — but I would not start one."
  - q: "Walk me through debugging a total that is wrong."
    a: "In order. Monitor first — did it run, when, how many rows — because a third of these end there. Then compare the row count against what the dataset normally holds. Then walk the node previews and find where the count changes unexpectedly. Then filter to a single entity and count by hand, which tells me which side multiplied. The dashboard is last. And I match symptom to cause: a clean multiple is fan-out, missing rows are an inner join or permissions, an entirely null column is sync or field-level security, and consistently one-day-old data is a recipe scheduled before its sync finishes."
  - q: "When would you split one recipe into several?"
    a: "Past about twenty nodes, when it stops being readable by someone who did not write it and failure stops localising. I split on meaning — a clean base dataset, then derived ones reading it — rather than on size. The cost is another schedule to order correctly, and given that a recipe running before its dependency finishes fails completely silently, that is a real cost rather than a formality."

# Creating Datasets: Interview Questions

This section is, in practice, the technical screen. Grain and fan-out come up in almost every CRM Analytics interview, and a candidate who reaches for them unprompted when shown a wrong number is immediately distinguishable.

::note{icon="i-lucide-ear"}
**What separates the strong answers here** is the diagnostic instinct rather than the definition. Anyone can define fan-out. The signal is answering "the total is wrong" with "is it a clean multiple, or is it low?" — because that one question splits the problem space in half before any investigation starts.
::

## The three sentences worth memorising

1. **"The grain is what one row represents, and it goes in the dataset description."**
2. **"A clean multiple is fan-out; missing rows are an inner join or permissions."**
3. **"Compute it once in the recipe, or it becomes several definitions."**

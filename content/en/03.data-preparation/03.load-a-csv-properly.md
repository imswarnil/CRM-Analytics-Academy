# Load a CSV Properly

Uploading takes ten seconds. Checking takes two minutes. This lesson is about the two minutes, because every one of the three checks below prevents a rebuild rather than a nuisance.

## The three checks, in order of expense

::field-table
---
dataset: what to verify at upload
grain: one row per check
fields:
  - name: "Dates typed as dates"
    type: "most common"
    role: "date"
    note: "A text date renders perfectly in a table, so it survives every casual review. It cannot be filtered by range, grouped by month, or trended — and you discover that at the exact moment you need a trend. Fixing it means editing the attributes and reloading the file."
  - name: "IDs typed as dimensions"
    type: "common"
    role: "key"
    note: "Sum of AccountId is meaningless and available. Force every identifier to a dimension at load. This matters most on the keys you will join on, which in the Academy's case is AccountId, OpportunityId and CampaignId."
  - name: "Currency scale"
    type: "expensive when wrong"
    role: "measure"
    note: "Out by 100× is invisible: every downstream figure is consistently wrong, so nothing looks anomalous. Compare a single row against the raw file by eye before moving on."
  - name: "Row count"
    type: "always"
    role: "measure"
    note: "The dataset README states the true count for every Academy file. Off by one is a header problem. Zero is a failed load, and Monitor holds the reason."
---
::

## Why the answer key matters so much

The Academy's `README.md` states the true totals — rows per file, closed revenue, ARR by month, lead counts. Every build in this course can therefore be checked against something that is independently true.

::tip{icon="i-lucide-check-check"}
**Check every load, even when you are confident.** The value is not catching the error you expected; it is building the reflex, so that when you are working on data with no README you still instinctively look for something to reconcile against — a finance figure, a previously published count, a report somebody already trusts. Analysts who do this are trusted; analysts who do not are eventually surprised in public.
::

## When a CSV is the right answer, and when it is not

::compare-cols
---
items:
  - title: "CSV is right"
    subtitle: "Fixed extracts, learning, one-offs"
    icon: "i-lucide-file-check"
    pros:
      - "No infrastructure, no connection, no schedule"
      - "Reproducible: the same file gives the same dataset"
      - "Perfect for this entire course"
    cons:
      - "Never updates itself"
      - "Somebody has to remember to re-upload"
    verdict: "Fine when the data genuinely does not change."
  - title: "CSV is wrong"
    subtitle: "Anything anyone expects to be current"
    icon: "i-lucide-file-x"
    pros:
      - "Fast to set up, which is the trap"
    cons:
      - "It will silently age, and it looks identical to a live dataset"
      - "The re-upload becomes one person's undocumented monthly chore"
    verdict: "Use a connection and a schedule instead."
---
::

::warning{icon="i-lucide-calendar-x"}
**The manual-upload trap in production.** A CSV loaded once becomes 'the dashboard' and quietly ages. There is nothing on screen to distinguish it from a scheduled dataset, and the only person who knows is whoever uploaded it. If you must ship one, put the extract date in the dataset name — `the Academy Accounts 2026-09` — so the staleness is visible to everyone rather than remembered by one person.
::

# Set Up Your Org

You need an org to build in. This lesson gets you from nothing to a working dataset in about half an hour, and skips every explanation that can wait — the access section covers licences, the integration user and row-level security properly.

::warning{icon="i-lucide-alert-triangle"}
**Do not use the normal Developer Edition signup.** A standard free Developer org does **not** include CRM Analytics, and you cannot switch it on from Setup — the licence is not in the org. Use the CRM Analytics Developer Edition promo signup below. This is the single most common way a first evening gets wasted.
::

## The two permission sets, in one paragraph

CRM Analytics access is granted by permission set, not by profile, and not by being an administrator. **CRM Analytics Plus Admin** carries the create-and-manage permissions: apps, datasets, recipes, dashboards, and the ability to see all data through the platform. **CRM Analytics Plus User** carries the day-to-day use permissions. In a real org these go to different people and the distinction is the whole subject of the access section; in your own practice org you want both, on yourself, and then you want to forget about it until the access section explains why the split exists.

::tip{icon="i-lucide-log-out"}
**If the Analytics Studio tile is missing** after assigning the permission sets, log out and log back in. Permission set assignments sometimes need a new session before the App Launcher picks them up. This resolves it far more often than any other fix.
::

## What "app" means here, because it is confusing

An **app** in CRM Analytics is a container with sharing settings — closer to a folder than to an application. Datasets, lenses and dashboards live inside one. Sharing an app shares what is in it, which is why the exploration section on collaboration is largely a lesson about app design rather than about buttons.

Your org already contains sample apps from Salesforce. Leave them alone; they are useful reference material and occasionally a lesson points at them. Everything *you* build goes in **Academy Analytics**.

## Loading a CSV: what to check every single time

Uploading a CSV takes ten seconds. Checking it takes two minutes and saves a build. Three things go wrong, in this order of frequency:

::field-table

grain: one row per thing to check
fields:
  - name: "Date fields read as text"
    type: "most common"
    role: "date"
    note: "A date typed as text cannot be filtered by date, grouped by month, or used in a date toggle. It looks completely fine in a table, which is why it survives to the moment you need a trend line. Fixing it means editing the field attributes and reloading the file."
  - name: "IDs typed as measures"
    type: "common"
    role: "key"
    note: "A numeric-looking identifier gets inferred as a measure, so CRM Analytics will cheerfully offer to sum it — and someone, eventually, will. Force it to a dimension at upload. This matters most on AccountId and CampaignId, which you will join on constantly."
  - name: "Currency scale"
    type: "expensive when wrong"
    role: "measure"
    note: "Check the decimal scale on any amount. A value stored in cents but read as a whole number is out by 100×, every downstream number inherits it, and nothing warns you. Compare one row against the CSV by eye before moving on."
  - name: "Row count"
    type: "always"
    role: "measure"
    note: "The dataset README lists the true row count for every file. If yours is off by one you have a header problem; if it is zero the load failed and Data Manager → Monitor holds the reason."

## Do not load all twenty-one files yet

Load `accounts.csv` and stop. The Data Preparation section loads the rest properly — through recipes rather than by hand, which is how it would be done in a real org, and which teaches you something that uploading twenty-one CSVs in a row does not.

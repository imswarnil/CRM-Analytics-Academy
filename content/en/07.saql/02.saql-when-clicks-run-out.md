# SAQL When Clicks Run Out

SAQL is not SQL with different keywords. It is a **stream transformation language**: each statement takes the previous statement's result and transforms it. That makes the *order* of statements the query plan, which is the one structural difference that catches experienced SQL people.

## The shape of a query

Read a generated one and the pattern is immediately visible:

```
q = load "Namilio_Opportunities";
q = filter q by 'StageName' == "Closed Won";
q = group q by 'Segment';
q = foreach q generate 'Segment' as 'Segment', sum('Amount') as 'Revenue';
q = order q by 'Revenue' desc;
q = limit q 10;
```

Six statements, each reassigning `q`. Load, narrow, group, compute, order, limit.

::note{icon="i-lucide-arrow-down"}
**Order matters in a way it does not in SQL.** A SQL engine reorders your query for you. Here you are describing a pipeline literally: filtering after grouping means aggregating rows you were going to discard. Filter early, always — it is both faster and closer to what you meant.
::

## Three patterns worth memorising

### 1. Distinct count

At a fine grain, counting rows counts the wrong thing:

```
q = foreach q generate 'Segment' as 'Segment',
      unique('OpportunityId') as 'Deals',
      sum('LineAmount') as 'Revenue';
```

Namilio's line-item grain makes this essential: 1,378 rows, 677 deals.

### 2. Share of total

Each group compared against the whole — awkward by clicking, straightforward here. Group by `all` to get the total, then compare each group against it. This is the pattern behind every "percentage of revenue" widget, and it is the most common reason to open SAQL at all.

### 3. Period comparison

Two filtered streams, each aggregated, then joined on the grouping — this quarter beside last quarter, with the delta computed between them. Section 9's velocity build uses exactly this shape.

::tip{icon="i-lucide-lightbulb"}
**Do not memorise syntax you can generate.** Build the closest thing you can by clicking, switch to SAQL, and edit from there. You get correct field references, correct quoting and a working skeleton for free — and the quoting is where hand-written SAQL usually goes wrong: single quotes for field names, double quotes for string values, exactly as in a security predicate.
::

## When to reach for it, and when not to

::compare-cols
---
items:
  - title: "Reach for SAQL"
    subtitle: "Clicks genuinely cannot express it"
    icon: "i-lucide-code"
    pros:
      - "Share of total, ratios across groups, windowed comparisons"
      - "Multi-step calculations in one query"
      - "Precise control over what the widget asks for"
    cons:
      - "Harder for the next person to maintain"
      - "Easy to embed a business definition where nobody will find it"
    verdict: "Use it, and leave a comment saying what it computes."
  - title: "Do NOT reach for SAQL"
    subtitle: "When the recipe is the right place"
    icon: "i-lucide-database"
    pros:
      - "A company-wide metric computed once agrees everywhere"
    cons:
      - "A definition written into a widget query is invisible to everyone else"
      - "Two dashboards with the same metric in SAQL will drift, and neither will be wrong"
    verdict: "If ten dashboards need it, it belongs in the recipe."
---
::

::warning{icon="i-lucide-eye-off"}
**The maintenance trap.** A metric defined in hand-written SAQL inside one widget is invisible to anybody looking at the dataset, the recipe or the documentation. It will be rediscovered, months later, by someone trying to work out why two dashboards disagree. Use SAQL for shaping a query; use the recipe for defining a metric.
::

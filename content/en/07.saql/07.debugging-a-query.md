# Debugging a Query

A query that errors tells you where to look. A query that returns the wrong answer tells you nothing, and that is the case worth having a method for.

## The method

::lesson-steps
---
items:
  - title: "Cut back to the load"
    description: "Delete everything after `load` and check the row count against what the dataset should hold. If that is already wrong, the problem is upstream and no amount of query editing will fix it."
  - title: "Add one statement at a time"
    description: "Re-add filter, then group, then foreach, checking the count and a sample value after each. The statement where the number stops making sense is the statement with the bug. This takes about two minutes and replaces an hour of staring."
  - title: "Narrow to one entity"
    description: "Filter to a single account or opportunity where you can count by hand. An aggregate cannot tell you which side multiplied; six rows on screen can."
  - title: "Read it as a pipeline, out loud"
    description: "'Load everything, keep closed-won, group by segment, sum amount.' Said aloud, a filter in the wrong place or a missing distinct count usually becomes obvious before you have finished the sentence."
---
::

## Symptom to cause

::field-table
---
dataset: query symptoms
grain: one row per symptom
fields:
  - name: "Too high by a clean multiple"
    type: "row multiplication"
    role: "measure"
    note: "A combination fanned out and a parent measure was summed afterwards. Count rows before and after the combination."
  - name: "Slightly too high"
    type: "partial fan-out"
    role: "measure"
    note: "Only some parents have multiple children — the usual real case, and harder to spot because it is not a clean multiple."
  - name: "Too low, and rows missing"
    type: "a filter, or nulls"
    role: "key"
    note: "An inequality that also excluded nulls, or a filter narrower than intended. Also check the security predicate: too low for one viewer and right for you is never a query problem."
  - name: "Counts the wrong things"
    type: "count() at a fine grain"
    role: "key"
    note: "count() counts rows. Once a dataset is at line-item grain you want unique() on the entity key."
  - name: "Changes between runs"
    type: "non-deterministic"
    role: "date"
    note: "A relative date range genuinely moves, which is correct for a live dashboard. A window with no explicit ordering also moves, which is a bug."
  - name: "Right total, wrong breakdown"
    type: "grouping on a duplicated attribute"
    role: "dimension"
    note: "The subtle one: the measure was aggregated correctly, but the grouping distributes it in a way that does not mean what it appears to."
---
::

## Performance, briefly

Most slow queries are slow for one of three reasons, in this order:

1. **Filtering late.** Rows aggregated and then discarded. Move the filter up.
2. **Aggregating a very fine grain on every load.** If many people open this daily, pre-aggregate in the recipe.
3. **Doing in the query what belongs in the recipe.** Joins and derived fields recomputed per view, per viewer.

::tip{icon="i-lucide-gauge"}
**Measure as a normal user, not as yourself.** An administrator may skip the security evaluation that a real viewer pays for on every query, so a dashboard that feels quick to you can be noticeably slower for the people who actually use it.
::

## Leave a comment

A hand-written query that survives into a shipped dashboard should say what it computes and why it is not in the recipe. One line. It is the difference between the next person understanding it and the next person rebuilding the dashboard beside it.

# Working Across Datasets

SAQL can carry more than one stream in a query and combine them. The mechanics are straightforward; the judgement is not.

## The judgement first

::warning{icon="i-lucide-git-branch"}
**If two datasets need combining for anything more than one widget, the recipe should do it.** A join written into a widget query is computed on every load, for every viewer, and is invisible to anybody reading the dataset or its documentation. Two dashboards will eventually implement it slightly differently, both will be defensible, and the disagreement surfaces in a meeting rather than in a review. Query-time combination is for *comparisons*, not for *models*.
::

## The grain trap follows you here

Everything section 4 says about grain applies inside a query. Combining a stream at one-row-per-opportunity with one at one-row-per-line-item multiplies rows exactly as a recipe join would, and summing the parent measure afterwards double-counts in exactly the same way.

::note{icon="i-lucide-ruler"}
**State both grains before combining, in the query editor as much as in a recipe.** The query editor feels lighter than a recipe — it is just text, nothing is being rebuilt — and that lightness is precisely why people skip the check here. The arithmetic does not care where you wrote it.
::

## Practical shape

The pattern is: load and shape each stream separately, then combine on a shared key, then compute.

```
-- actuals by segment
act = load "Namilio_Opportunities";
act = filter act by 'StageName' == "Closed Won";
act = group act by 'Segment';
act = foreach act generate 'Segment' as 'Segment', sum('Amount') as 'Actual';

-- targets by segment (a small, separate dataset)
tgt = load "Namilio_Targets";
tgt = group tgt by 'Segment';
tgt = foreach tgt generate 'Segment' as 'Segment', sum('Target') as 'Target';
```

Both streams are already at one row per segment, so combining them cannot multiply anything — which is the property to arrange deliberately rather than to discover afterwards.

::tip{icon="i-lucide-check"}
**Aggregate each stream to the shared grain before combining.** If both sides are one row per key, the combination is safe by construction. This is the query-editor version of "aggregate the many side before the join", and it is the same fix for the same reason.
::

## A note on missing matches

A segment present in actuals but absent from targets, or the reverse, will produce nulls on one side. Decide what that means: a segment with no target is probably a data gap worth surfacing, while a target with no actuals is a segment that sold nothing — which is a finding, not a gap. Filling both with zero silently is the easy option and it hides the difference.

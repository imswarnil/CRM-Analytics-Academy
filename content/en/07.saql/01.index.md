# Why SAQL Exists

Every lens, every widget and every dashboard query is SAQL underneath. Clicking generates it; you only write it when the click interface runs out.

::note{icon="i-lucide-waves"}
**SAQL is a stream transformation, not a declarative query.** Each statement takes the previous statement's result and transforms it, reassigning the same stream variable. There is no optimiser reordering your work, so **the order you write statements in is the plan that runs** — filtering after grouping really does aggregate rows you were about to discard. This is the single structural difference that catches people who know SQL well.
::

## The shape

```
q = load "Academy_Opportunities";
q = filter q by 'StageName' == "Closed Won";
q = group q by 'Segment';
q = foreach q generate 'Segment' as 'Segment', sum('Amount') as 'Revenue';
q = order q by 'Revenue' desc;
q = limit q 10;
```

Load, narrow, group, compute, order, limit. Six statements, each reassigning `q`, each consuming what the last produced.

::warning{icon="i-lucide-eye-off"}
**What SAQL should NOT be used for: defining a business metric.** A definition written into one widget's query is invisible to anyone reading the dataset, the recipe or the documentation. It will be rediscovered months later by somebody working out why two dashboards disagree — and neither will be wrong. Shape queries in SAQL; define metrics in the recipe.
::

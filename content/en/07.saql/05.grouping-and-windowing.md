# Grouping and Windowing

Everything here answers a question of the form *"this row, compared with the others"* — which is exactly what plain aggregation cannot do, because aggregation collapses the others away.

## Group by all

The simplest two-level calculation. `group q by all` produces one bucket containing everything, which gives you a company total to compare individual groups against.

```
-- revenue per segment, and each segment's share of the company total
q = load "Namilio_Opportunities";
q = filter q by 'StageName' == "Closed Won";
total = group q by all;
total = foreach total generate sum('Amount') as 'Total';
seg = group q by 'Segment';
seg = foreach seg generate 'Segment' as 'Segment', sum('Amount') as 'Revenue';
```

The two streams are then combined so each segment row can see the total. This is the shape behind every "percentage of revenue" widget, and it is the most common reason anyone opens the query editor at all.

::note{icon="i-lucide-percent"}
**Share of total is the canonical two-level query.** Once you can write it, the rest of the family — index against the average, contribution to growth, concentration of the top N — is the same manoeuvre with different arithmetic.
::

## Windowing

A window function computes across a *set of neighbouring rows* without collapsing them. Three uses cover almost everything:

::field-table
---
dataset: window calculations
grain: one row per pattern
fields:
  - name: "Running total"
    type: "accumulate in order"
    role: "measure"
    note: "Cumulative ARR by month, cumulative pipeline created in a quarter. Requires an explicit ordering — the result is meaningless without one, and the query will happily run anyway."
  - name: "Moving average"
    type: "smooth a noisy series"
    role: "measure"
    note: "A trailing 3- or 7-period mean. Honest smoothing when a daily series is too noisy to read; dishonest when the spikes were the finding and you smoothed them out of sight."
  - name: "Rank within a group"
    type: "partitioned"
    role: "dimension"
    note: "Top three reps per region, top product per segment. The partition is the important part — without it you get a single global ranking and every row in the smallest region sits at the bottom."
  - name: "Period over period"
    type: "compare to the previous row"
    role: "date"
    note: "This month against last, as a delta or a percentage, in one query rather than two widgets the reader has to subtract by eye."
---
::

::warning{icon="i-lucide-arrow-down-up"}
**A window without an explicit order is a bug that does not announce itself.** Running totals, period-over-period and rank all depend on the row order, and if you do not specify it the engine uses whatever order it produced — stable today, different after the next data refresh. The numbers change and nothing in the query looks wrong.
::

## Partitioning is the part people get wrong

Ranking reps *within each region* means the window resets per region. Ranking all reps globally and then filtering to one region gives you ranks 14, 27 and 31 rather than 1, 2 and 3 — arithmetically correct and wrong for the question.

::tip{icon="i-lucide-group"}
**Say the partition out loud before writing it: "the best three reps in each region".** The phrase "in each" is the partition. If the sentence has no "in each", you probably do not need a window at all — a plain group and an order will do.
::

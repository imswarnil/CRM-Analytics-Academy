interview:
  - q: "How does SAQL differ from SQL?"
    a: "It is a stream transformation rather than a declarative query. Each statement takes the previous result and transforms it, reassigning the same variable, so statement order is literally the plan that runs — there is no optimiser reordering it. Practically that means filtering early rather than late, because filtering after a group means aggregating rows I was about to discard. The other difference that bites is quoting: single quotes for field names, double quotes for string values."
  - q: "When do you write SAQL by hand rather than clicking?"
    a: "When the click interface cannot express it: share of total, a ratio compared across groups, a period-over-period delta in one query, or any window — running totals, moving averages, rank within a partition. Even then I build the closest approximation by clicking and edit the generated query, because that gives me correct field references and quoting for free."
  - q: "What should NOT live in a widget's SAQL?"
    a: "A business metric definition. It is invisible to anyone reading the dataset, the recipe or the documentation, and it will be rediscovered months later by somebody working out why two dashboards disagree — where neither is wrong, which is harder to resolve than an error. I shape queries in SAQL and define metrics in the recipe."
  - q: "How do you count deals in a dataset joined to line items?"
    a: "unique() on the opportunity key, not count(). count() counts rows at the current grain, so at line-item grain it counts lines — 1,378 rather than 677 in our data. It is the grain problem wearing a function's clothes, and I check the result against a number I already know."
  - q: "Explain how you would compute each segment's share of total revenue."
    a: "Two levels of aggregation. Group by all to get the company total as one stream, group by segment for the per-segment revenue as another, then combine so each segment row can see the total and divide. It is the canonical two-level query and it is the most common reason anyone opens the editor — once you can write it, index-against-average and contribution-to-growth are the same manoeuvre."
  - q: "A query returns a number that is too high. Walk me through it."
    a: "Cut back to the load and check the row count against what the dataset should hold, then add one statement at a time checking the count after each — the statement where it stops making sense is the one with the bug. Then narrow to a single account where I can count by hand, because an aggregate cannot tell me which side multiplied. A clean multiple is row multiplication with a parent measure summed after it; slightly high is a partial fan-out; too low is usually a filter that also excluded nulls."
  - q: "What is the trap with `!=` in a filter?"
    a: "It drops nulls as well. Filtering stage not equal to Closed Lost also removes every row where stage is blank — often the rows with a data-quality problem worth seeing. Nothing errors, the total just falls. If I mean 'everything except X including unknowns' I write that explicitly."
  - q: "Numbers change between runs with no data change. What would you suspect?"
    a: "A relative date range, which genuinely moves and is correct for a live dashboard, or a window with no explicit ordering, which is a bug — running totals, rank and period-over-period all depend on row order, and without one specified the engine uses whatever it produced. It is stable until the next refresh, then quietly different."

# SAQL: Interview Questions

SAQL questions are less about syntax than they look. An interviewer can look up a function; what they are testing is whether you know when to reach for the query editor and when reaching for it is the mistake.

::note{icon="i-lucide-star"}
**The strongest answer here is the one about what does not belong in SAQL.** Volunteering that a metric definition hidden in a widget query is a maintenance problem — and explaining why two defensible dashboards are worse than one wrong one — is the answer of somebody who has had to untangle it.
::

## The three sentences worth memorising

1. **"It is a stream transformation, so statement order is the query plan — filter early."**
2. **"count() counts rows; unique() counts things."**
3. **"Shape queries in SAQL; define metrics in the recipe."**

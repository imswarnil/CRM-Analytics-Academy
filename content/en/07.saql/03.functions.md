# Functions by Family

You do not need the whole reference. You need five families and about fifteen functions.

## Aggregation

The functions that collapse many rows into one value, used inside `foreach … generate` after a `group`.

::field-table
---
dataset: aggregation
grain: one row per function
fields:
  - name: "sum('Field')"
    type: "the workhorse"
    role: "measure"
    note: "Ignores nulls silently. A sum over a column that is 40% null is a sum of 60% of the data, reported without comment — check null density before trusting any total."
  - name: "count()"
    type: "rows, not things"
    role: "measure"
    note: "Counts ROWS at the current grain. At the Academy's line-item grain that is 1,192 lines, not 608 deals. This is the grain problem wearing a function's clothes."
  - name: "unique('Field')"
    type: "distinct count"
    role: "key"
    note: "What you almost always want once a dataset has been joined to something. unique('OpportunityId') gives deals; count() gives lines."
  - name: "avg('Field')"
    type: "use carefully"
    role: "measure"
    note: "Averages the non-null rows, which is usually right and rarely checked. Never use it on a per-row rate that you want weighted — that is sum ÷ sum, computed from the parts."
  - name: "min() / max()"
    type: "extremes and dates"
    role: "date"
    note: "max on a date gives the latest event per group, which is the standard way to get 'last activity' without a separate query."
  - name: "median() / percentile_cont()"
    type: "when the mean lies"
    role: "measure"
    note: "The Academy's deal sizes are heavily skewed by a flat $36,000 Enterprise Programme fee alongside hundreds of $240 Academy Pro subscriptions, so the median describes the typical deal and the mean does not."
---
::

::warning{icon="i-lucide-divide"}
**Ratios: aggregate both parts, then divide.** `sum('Discount') / sum('ListTotal')` is the weighted discount rate the business means. `avg('DiscountPct')` weights a $5,000 deal the same as a $2M one and produces a number nobody recognises. And guard the denominator — a division by zero in one month poisons the whole series.
::

## Dates

Dates in SAQL are structured rather than plain values, with parts you can group by directly: year, quarter, month, week, day.

- **`date('Field_Year', 'Field_Month', 'Field_Day')`** — construct a date from the parts for comparisons.
- **`daysBetween(a, b)`** — the basis of speed-to-lead, days-in-stage, age and cycle time.
- **`toDate()` / `now()`** — for anything measured against today.
- **Relative ranges** — "current quarter", "last 90 days". Convenient, and they make a query *non-deterministic*: the same query returns different numbers tomorrow, which is correct for a live dashboard and a trap when you are reconciling against a fixed report.

::note{icon="i-lucide-calendar"}
**Always say which date you grouped by.** An opportunity has created, close, last-modified and stage-entry dates. The same dataset grouped by a different one tells a genuinely different story, and no function call in the query will tell the reader which you chose — only the widget title can.
::

## Strings

`lower()` and `upper()` for comparisons that must not care about case, `trim()` for data arriving from a CSV, `substr()` for extracting a prefix, and concatenation for building a composite label.

::tip{icon="i-lucide-spell-check"}
**Normalise before you compare, not after.** `EMEA`, `emea` and `EMEA ` are three different groups, and a grouping that splits one region into three looks like a data problem rather than a formatting one. If it matters in a query it usually matters in the recipe too — fix it upstream so every dashboard inherits the fix.
::

## Maths and conditionals

Arithmetic works as expected. The conditional worth knowing is **`case`**, which is how you bucket inside a query:

```
q = foreach q generate 'Account' as 'Account',
      (case when 'UtilizationPct' < 55 then "At risk"
            when 'UtilizationPct' > 105 then "Overage"
            else "Healthy" end) as 'Band',
      sum('ARR') as 'ARR';
```

::warning{icon="i-lucide-repeat"}
**If a `case` appears in more than one query, it belongs in the recipe.** Bucketing rules duplicated across widgets drift: "at risk" comes to mean under 55 on one dashboard and under 60 on another, both defensible, and the disagreement surfaces in a meeting. Bucket once in a transform node and every screen inherits the same bands.
::

## Null handling

Nulls are the quiet source of wrong answers:

- **`coalesce(a, b)`** — substitute a default. Use deliberately: replacing null with zero turns "unknown" into "none", which is a claim.
- **`is null` / `is not null`** — the explicit test.
- **The inequality trap** — `'Stage' != "Closed Lost"` also removes every row where Stage is null. Almost never intended, never announced.

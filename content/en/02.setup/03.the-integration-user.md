# The Integration User

Data sync does not run as you. It runs as a dedicated account — the **integration user** — and that account's visibility is the ceiling on everything downstream.

::warning{icon="i-lucide-ghost"}
**This is the quietest failure in the entire platform.** If the integration user cannot see a field, the field does not arrive. The sync reports success. The recipe runs green. The dataset builds. The dashboard renders a number that is simply computed without that field — a margin without discounts, a pipeline without a segment, a total that is confidently, plausibly wrong. Nothing anywhere says so.
::

## What it is

A special, licensed account that exists to read data on behalf of analytics. It is not a person, nobody logs in as it, and its permissions are deliberately narrow: it needs to *read* what analytics must see and nothing else.

Its object and field-level security is therefore a design decision, not a default to accept:

::field-table
---
dataset: what the integration user's access decides
grain: one row per consequence
fields:
  - name: "Object access"
    type: "what can sync at all"
    role: "key"
    note: "No read on an object means that object cannot be synced. The symptom is an object that simply is not offered in the sync selection, which reads as a product limitation rather than a permission."
  - name: "Field-level security"
    type: "which columns arrive"
    role: "key"
    note: "The dangerous one. A hidden field is absent rather than empty, so a formula referencing it either errors in the recipe — if you are lucky — or the field was never added to the recipe at all and the number is quietly incomplete."
  - name: "Record visibility"
    type: "which rows arrive"
    role: "measure"
    note: "Sync generally needs to see ALL records, because row-level security is applied later, per viewer, by the predicate. An integration user restricted at the record level produces a dataset missing rows for everyone, permanently."
  - name: "Encrypted and formula fields"
    type: "special cases"
    role: "dimension"
    note: "Platform-encrypted fields and some formula fields behave differently from plain columns. If a field looks present but always null, check whether it is one of these before rebuilding the recipe."
---
::

## The rule that prevents most of this

::tip{icon="i-lucide-clipboard-check"}
**Whenever you add a field to a recipe, confirm three things in order: the field is visible to the integration user, the field is selected in data sync, and the sync has run since you selected it.** Miss any one and the field is absent. It takes fifteen seconds and it removes an entire category of bug — one that otherwise surfaces weeks later, in front of someone who cares about the number.
::

## Sync narrow, but sync early

Two instincts pull against each other, and both are partly right.

**Sync narrow**, because every extra field costs time on every run and space in the store, and an object synced wholesale drags along dozens of fields nobody will ever group by.

**Sync early**, because a snapshot dataset can only remember what was synced at the time. A field you start syncing in March has no February values and never will. If a field is plausibly going to matter for trend analysis, add it before you need it — history cannot be backfilled from an object that only holds current state.

::note{icon="i-lucide-scale"}
**How to settle it.** Narrow on *objects*, generous on *dates and dimensions you will trend*. The expensive fields are usually long text and rarely-used descriptive columns; the cheap and valuable ones are dates, owners, stages, segments and amounts. When in doubt about a date field, sync it.
::

## Namilio, concretely

Every build in sections 8 to 10 rests on fields that would be easy to lose this way: `Discount` on quotes, `CommitState` on usage, `DeflectedByAI` on cases, `RootCause` on cases, `MovementType` on the ARR snapshots.

::warning{icon="i-lucide-pencil-ruler"}
**Lose `MovementType` and section 10's ARR waterfall does not break — it flattens.** Every movement becomes indistinguishable, so new business, expansion, contraction and churn collapse into one net number. The chart still renders. The total is still right. The entire insight is gone, and there is nothing on screen to suggest anything is missing. That is what a silent permission failure looks like in practice, and it is why this lesson is in the course.
::

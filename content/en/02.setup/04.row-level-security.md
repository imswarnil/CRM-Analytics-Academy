# Row-Level Security and the Predicate

App sharing decides *who can open the dashboard*. Row-level security decides *what they see once it opens*. They are independent, and you need both.

## The security predicate

A **security predicate** is a filter attached to the dataset itself, evaluated per viewer, at query time. Every query against that dataset — every widget, every lens, every export — has the predicate applied before anything else happens. It cannot be bypassed from the dashboard side, which is exactly the property you want.

The shape is a comparison between a column in the dataset and something about the current user:

::field-table
---
dataset: common predicate shapes
grain: one row per pattern
fields:
  - name: "Own records only"
    type: "'OwnerId' == \"$User.Id\""
    role: "key"
    note: "The simplest and most common. Each viewer sees rows they own. Requires the owner's user id to be a column in the dataset — which means it must be synced, and carried through every join in the recipe."
  - name: "By a user attribute"
    type: "'Region' == \"$User.Region__c\""
    role: "dimension"
    note: "Match a dataset column to a field on the user record. Excellent when the org already maintains that field on users, and a maintenance liability when it does not — a blank field means the viewer sees nothing at all."
  - name: "Role hierarchy"
    type: "'RolePath' contains \"$User.UserRoleId\""
    role: "dimension"
    note: "A manager sees their own rows and everyone below them. Needs the hierarchy precomputed into the dataset by a flatten node, because a predicate cannot walk the hierarchy at query time."
  - name: "Everyone sees everything"
    type: "no predicate"
    role: "measure"
    note: "A legitimate choice for genuinely non-sensitive data, and it should be a decision written down rather than an omission. 'We deliberately did not restrict this' and 'nobody thought about it' look identical in the configuration."
---
::

## The flatten node, and why it exists

A role hierarchy is a tree. A predicate is a comparison. A comparison cannot climb a tree, so the tree has to be flattened into something comparable **before** the data is queried — at recipe time.

::note{icon="i-lucide-git-branch"}
**What flatten produces.** For each role, a column containing that role and all of its ancestors — a path. The predicate then asks whether the viewer's role appears anywhere in the row's path. A regional director's role appears in the paths of every rep beneath them, so they see those rows; it does not appear in a sibling region's paths, so they do not. The whole hierarchy question becomes one string comparison, which is why it is fast enough to run on every query.
::

This is the concrete reason security has to be designed **before** the data model: the predicate needs a column, the column needs a recipe node, and the node needs fields that must be synced. Deciding on the hierarchy after the dashboards are built means rebuilding the recipe and every dataset downstream of it.

## The security user

Where the predicate is a rule you write, **sharing inheritance** lets the org's own sharing decide — and the **security user** is the account that evaluates it. It needs access to the fields the evaluation depends on, and if it cannot see them, inheritance cannot be computed.

Treat it like the integration user: narrow, deliberate, and documented. Both are special accounts whose access is a design decision rather than an afterthought.

## Writing a predicate you will still understand later

::lesson-steps
---
items:
  - title: "Write the sentence first, in English"
    description: "'A rep sees their own accounts; a regional director sees their whole region; finance sees everything.' If you cannot write that sentence, you are not ready to write the predicate — and the sentence belongs in the project notes beside it."
  - title: "Name who must see everything"
    description: "There is always somebody: finance, the exec team, the analytics team itself. Decide how they are exempted — usually a user attribute or a role high enough to cover all paths — before you write the rule, not after it locks you out."
  - title: "Check every field the predicate touches"
    description: "Each one must be in the dataset, populated, and correctly typed. A null in a predicate field does not fail open, it fails CLOSED: that viewer sees nothing, which is safe and confusing."
  - title: "Test as three people"
    description: "A rep, a manager, and someone who should see nothing. All three, every time you change the rule. Your own admin account tells you nothing useful here."
---
::

::warning{icon="i-lucide-lock"}
**Predicates fail closed, and that is the right default.** A typo, a missing column or a blank user field produces an empty dashboard rather than a leak. So when someone reports "the dashboard is blank for the whole team", suspect the predicate first — and be grateful it broke in this direction.
::

## The trap that catches everyone once

You add a predicate, and your own dashboards go empty.

Nothing is broken. The predicate is evaluated for *you* as well, and your user does not satisfy it — you own none of the records, your role is outside the paths, your region field is blank. Administrators are not exempt by default.

::tip{icon="i-lucide-user-cog"}
**Plan the exemption deliberately** rather than by granting yourself something broad in a panic. A named condition in the predicate — a role, a permission, a user attribute the analytics team carries — is explicit, reviewable, and does not quietly hand the same exemption to the next person who inherits that profile.
::

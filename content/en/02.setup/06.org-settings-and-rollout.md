# Org Settings and Rollout

Two things left before the hands-on: the switchboard, and getting this in front of people without a bad first week.

## The settings page

Setup → Analytics → Settings is where CRM Analytics is enabled and where feature toggles live. Most of it you will set once and never revisit, but three habits are worth having:

::lesson-steps
---
items:
  - title: "Read the page before you need it"
    description: "Ten minutes now means that when someone says 'can we turn on X', you know whether X is a toggle, a licence, or a redesign. Being able to answer that in the meeting is disproportionately valuable."
  - title: "Enable new features in a sandbox first"
    description: "Toggles change behaviour, and behaviour changes can alter what a live dashboard shows. A developer or sandbox org is where you find that out. This is the one genuinely important rule on this page."
  - title: "Record what you changed and why"
    description: "A toggle flipped eighteen months ago with no note is indistinguishable from a default, and nobody dares change it back. Two lines in the project notes prevents a permanent no-touch zone."
---
::

::note{icon="i-lucide-flask-conical"}
**Your free Developer org is the sandbox for this course.** Everything you enable there is consequence-free, which is exactly what makes it worth experimenting in. Treat a production org as somewhere you change things deliberately, having already seen what the change does somewhere else.
::

## Rollout: the sequence that works

The technical work is done long before the adoption work. The order below is not bureaucracy — each step exists because skipping it produces a specific, predictable failure:

::field-table
---
dataset: rollout sequence
grain: one row per step
fields:
  - name: "1 — Two or three real users"
    type: "before anything else"
    role: "key"
    note: "The people who will actually make the decision the dashboard supports. Not a committee, not a demo audience. They will tell you within ten minutes whether the screen answers their question, and that feedback is worth more than any amount of internal review."
  - name: "2 — Verify as them, not as you"
    type: "the non-negotiable step"
    role: "key"
    note: "Log in as a restricted user. An administrator sees everything, so every security mistake is invisible to whoever built it. Skipping this is how a dashboard arrives empty — or showing another region's deals — in front of its audience."
  - name: "3 — One team"
    type: "a week or two"
    role: "dimension"
    note: "Now the questions change from 'is this right' to 'how do I use it'. That is where you find out which labels are ambiguous and which widget everybody misreads."
  - name: "4 — Everyone who needs it"
    type: "with the definitions attached"
    role: "dimension"
    note: "Ship the metric definitions alongside the dashboard. A number without a definition becomes an argument the first time it disagrees with somebody's spreadsheet — and it will."
  - name: "5 — A named owner"
    type: "permanent"
    role: "measure"
    note: "Somebody owns the schedule, the definitions and the requests. An unowned dashboard degrades quietly: the recipe drifts, a field changes meaning, and trust goes before anybody files a ticket."
---
::

## The two things people actually ask

::compare-cols
---
items:
  - title: "'Why is this number different?'"
    subtitle: "Asked within the first week, always"
    icon: "i-lucide-equal-not"
    pros:
      - "Almost always a definition difference, not an error"
      - "Answerable in seconds if the metric spec exists"
    cons:
      - "Without a written definition it becomes a multi-day investigation, and trust drops while it runs"
    verdict: "Publish the definitions with the dashboard. Every time."
  - title: "'Is this live?'"
    subtitle: "Asked the moment a number looks wrong"
    icon: "i-lucide-clock"
    pros:
      - "A visible 'last refreshed' timestamp answers it permanently"
      - "Costs one text widget"
    cons:
      - "Without it, every staleness question becomes a personal support request to you"
    verdict: "Put the refresh time on the dashboard."
---
::

::tip{icon="i-lucide-timer-reset"}
**The single highest-value widget on any production dashboard** is a text box that says when the data last refreshed. It deflects an entire category of question, it makes the materialisation honest rather than hidden, and it takes two minutes to add.
::

## What to carry forward

- Enable new things somewhere safe first, and write down what you enabled.
- Verify as a restricted user before anyone else sees it — this is the habit the collaboration section keeps insisting on.
- Ship definitions and a refresh timestamp with every dashboard.
- Give every dashboard an owner, or expect it to rot.

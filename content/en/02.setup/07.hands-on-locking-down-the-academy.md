# Hands-On: Locking Down the Academy

Forty minutes. One dataset, one predicate, one test user, and the three outcomes you need to have seen before you do this in a real org.

## The syntax, since it is the common stumble

```
'Region' == "$User.Sales_Region__c"
```

**Single quotes** wrap the dataset column. **Double quotes** wrap the user attribute. The asymmetry is how the syntax tells a column apart from a value, and reversing it is the error you will make at least once.

Combining conditions uses `||` for or and `&&` for and:

```
'Region' == "$User.Sales_Region__c" || "$User.Sales_Region__c" == "ALL"
```

::warning{icon="i-lucide-spell-check"}
**Predicates compare strings exactly.** `EMEA`, `emea` and `EMEA ` with a trailing space are three different regions. If a predicate returns nothing and the syntax is right, print the distinct values of the column and the value on the user record and compare them character by character. This is the second most common cause after a blank field, and it looks identical to a broken rule.
::

## Why a user attribute here and a hierarchy in production

This lesson uses a field on the user record because it makes the mechanism visible: one column, one comparison, one place to look when it misbehaves.

Most production orgs eventually want the role hierarchy instead — a manager seeing everything beneath them without anybody maintaining a region field on hundreds of users. That needs a flatten node in the recipe, which is the data preparation section's material. The mechanism is identical; only the column the predicate compares against changes.

::tip{icon="i-lucide-notebook-pen"}
**Write the four lines now.** Which datasets have predicates, what each one says in English, who is exempt and how, and what the fallback is. It takes two minutes today and saves a week for whoever inherits the org — possibly you, having forgotten.
::

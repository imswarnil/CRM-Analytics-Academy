# Sharing Inheritance

A predicate is a rule you write and maintain. **Sharing inheritance** asks Salesforce the question instead: show this viewer the analytics rows corresponding to records they can already see in the CRM.

::tip{icon="i-lucide-link-2"}
**Why this is the stronger default where it fits.** Sharing rules change. Territories are redrawn, a team is reorganised, someone gets a new manager. A hand-written predicate does not hear about any of that — it keeps enforcing last year's structure, correctly and invisibly, until someone notices. Inheritance stays aligned by construction, because there is only one model and analytics is reading it rather than copying it.
::

## What it covers, and where it stops

Inheritance applies to analytics rows that correspond to Salesforce records. Where it applies, it is the best answer available. Where it does not, you need a predicate:

::field-table
---
dataset: inheritance boundaries
grain: one row per case
fields:
  - name: "Standard CRM objects"
    type: "supported"
    role: "key"
    note: "Accounts, opportunities, cases and similar. Verify the current supported list for your release rather than assuming — it has grown over time and will keep changing."
  - name: "External and uploaded data"
    type: "not covered"
    role: "measure"
    note: "Namilio's web sessions, marketing spend, SEO keywords and LLM visibility have no Salesforce record behind them, so there is no sharing to inherit. These need a predicate, or a deliberate decision that they are open to all viewers."
  - name: "Highly complex sharing"
    type: "falls back"
    role: "dimension"
    note: "There are limits on how much sharing detail can be evaluated. A user whose access comes through an unusually large number of rules exceeds them, and the FALLBACK decides what they see — which is why the fallback is not optional."
  - name: "Aggregated rows"
    type: "needs thought"
    role: "measure"
    note: "Once a recipe aggregates to a monthly total per segment, a row no longer corresponds to one record. Inheritance has nothing to attach to. Either keep a key that identifies ownership, or accept that this dataset is secured differently — and write down which."
---
::

## The fallback is the design decision

When inheritance cannot be evaluated for a viewer, the fallback predicate takes over. Choosing it is choosing how the system behaves under pressure:

::compare-cols
---
items:
  - title: "Restrictive fallback"
    subtitle: "Show nothing when unsure"
    icon: "i-lucide-lock"
    pros:
      - "Cannot leak — an edge case shows an empty screen"
      - "The failure is visible and gets reported quickly"
      - "The right default for anything sensitive"
    cons:
      - "A senior person with complex access may see nothing, which is a confusing first impression"
    verdict: "Default to this. Be ready to explain it."
  - title: "Permissive fallback"
    subtitle: "Show more when unsure"
    icon: "i-lucide-unlock"
    pros:
      - "No confusing blank screens"
      - "Fine for genuinely non-sensitive data"
    cons:
      - "The failure is invisible, and it fails in the leaking direction"
      - "Nobody reports seeing too much"
    verdict: "Only with a written decision behind it."
---
::

::warning{icon="i-lucide-alert-octagon"}
**Nobody reports seeing too much.** An over-restrictive rule generates a support ticket within a day. An over-permissive one generates nothing at all, until it is found by someone who should not have found it. That asymmetry is the whole argument for a restrictive fallback, and it is worth saying out loud in the design review, because "let's not confuse people with blank screens" is a genuinely reasonable-sounding argument for the wrong choice.
::

## Which to use

::lesson-cards
---
columns: 3
items:
  - title: "Use inheritance"
    icon: "i-lucide-share-2"
    description: "When the dataset is built from supported Salesforce objects and the org's sharing model is already the truth you want analytics to reflect. This is most CRM dashboards."
  - title: "Use a predicate"
    icon: "i-lucide-filter"
    description: "For external data, aggregated datasets, or a rule genuinely specific to analytics — 'finance sees all regions but not individual rep names' has no equivalent in record sharing."
  - title: "Use both"
    icon: "i-lucide-layers"
    description: "The normal production answer. Inheritance where it applies, with a restrictive fallback predicate behind it, and the combination documented so the next person knows which is doing the work."
---
::

## Write it down, once

A short note — four or five lines — that says which datasets use which mechanism, what the fallback is, who is exempt and why.

That note is the single most useful artefact in a CRM Analytics project after the metric definitions. Without it, the first person to inherit the org spends a week reverse-engineering a security model from configuration screens, and is understandably reluctant to change anything afterwards.

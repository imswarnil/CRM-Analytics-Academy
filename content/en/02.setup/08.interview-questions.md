interview:
  - q: "How is access to CRM Analytics granted?"
    a: "Two layers. The org needs a CRM Analytics licence — Growth or Plus, with Einstein Discovery in the higher tier. Then individual access comes by permission set, not by profile: an admin and a user set per tier. System Administrator on its own grants no CRM Analytics access at all, which surprises people on day one. And access to the product is separate from access to content: a user can be fully licensed and still see nothing until an app is shared with them."
  - q: "What is the integration user and why does it matter?"
    a: "It is the account data sync runs as, so its visibility is the ceiling on everything downstream. If it cannot see a field, that field never arrives — the sync succeeds, the recipe runs, the dataset builds, and the dashboard shows a number computed without it. It is the quietest failure in the platform because nothing errors and the result looks plausible. So whenever I add a field to a recipe I check three things: the integration user can see it, it is selected in sync, and sync has run since."
  - q: "Predicate or sharing inheritance?"
    a: "Inheritance where it fits, because it reuses the org's existing sharing and therefore cannot drift when the business reorganises — a hand-written predicate keeps enforcing last year's structure, correctly and invisibly. But inheritance only covers rows that correspond to supported Salesforce records, so external data, uploaded data and aggregated datasets need a predicate. In practice it is both: inheritance where it applies with a restrictive fallback predicate behind it, and a note saying which is doing the work."
  - q: "Why does a role-hierarchy predicate need a flatten node?"
    a: "Because a predicate is a comparison and a hierarchy is a tree, and a comparison cannot walk a tree at query time. The flatten node precomputes each role's ancestry into a path column at recipe time, and the predicate asks whether the viewer's role appears in that path. It is also the concrete reason security has to be designed before the data model: the rule needs a column, the column needs a recipe node, and the node needs fields that must be synced."
  - q: "A dashboard is blank for the whole sales team but fine for you. Walk me through it."
    a: "Blank for everyone but the admin points at row-level security, so I start there rather than at the dashboard. Is there a predicate, and does the team satisfy it — is the field it compares populated on their user records, and do the strings match exactly, including case and trailing spaces? Nulls fail closed, which is the right behaviour and the most common cause. Then sharing inheritance and its fallback. Then whether the app is shared with them at all, because no-access and no-rows look identical. My own account tells me nothing here, which is why I check as a restricted user before shipping rather than after."
  - q: "And if rows are missing rather than everything?"
    a: "Missing rather than duplicated still points upstream to permissions before the dashboard. Integration user field and object access first, then the predicate, then an inner join in the recipe that dropped unmatched records, then a filter narrower than intended. Duplicated is the opposite diagnosis — that is a join at the wrong grain, and I stay in the recipe for it."
  - q: "How would you test a security model before release?"
    a: "As three people, never as myself: someone who should see a slice, their manager, and someone who should see nothing. I check that the restricted total is lower than the unrestricted one by exactly the amount I expect, rather than just checking that something appears — 'not empty' is not the same as 'correct'. And I deliberately blank a predicate field once, so I have seen what a null does and recognise the symptom when it is reported."
  - q: "What would you write down for the next person?"
    a: "Four lines: which datasets carry predicates, what each says in plain English, who is exempt and why, and what the fallback is. Security configuration is unreadable as configuration — the next person inherits a set of screens with no statement of intent, and reasonably refuses to change anything. That note is the most useful artefact in the project after the metric definitions."

# Setup and Access: Interview Questions

This section is disproportionately represented in technical screens, for a simple reason: it is where real projects stall, so it separates people who have shipped from people who have studied.

::note{icon="i-lucide-ear"}
**What the interviewer is listening for.** Whether you reach for permissions when rows are missing and for grain when rows are duplicated. Whether you know that administrators are not exempt from predicates. And whether you test as somebody else — that last one, volunteered unprompted, is the strongest single signal in this whole section.
::

## The three sentences worth memorising

1. **"Access is a permission set, not a profile — and admin rights grant none of it."**
2. **"The integration user is the ceiling on what data exists at all, and it fails silently."**
3. **"Missing rows means permissions; duplicated rows means a join."**

# Recipe Nodes

Seven node types do nearly everything. The useful way to learn them is not alphabetically — it is by what each does to the **grain**, because grain is the only property you must track from the first node to the last.

## Grouped by effect on grain

::field-table
---
dataset: nodes by what they do to the grain
grain: one row per node type
fields:
  - name: "Input"
    type: "sets the grain"
    role: "key"
    note: "Reads a synced object, a dataset or an uploaded file. The grain of the recipe starts as the grain of its inputs, which is why you say both out loud before joining anything."
  - name: "Filter"
    type: "grain unchanged"
    role: "dimension"
    note: "Removes rows. Fewer rows, same meaning per row. The safest node in the list — and still worth checking the count, because a filter that removes more than you expected is a common cause of 'lower than expected'."
  - name: "Formula"
    type: "grain unchanged"
    role: "measure"
    note: "Adds a column computed per row. Nothing about what a row represents changes. Everything derived arithmetically from existing columns belongs here."
  - name: "Transform"
    type: "grain unchanged"
    role: "dimension"
    note: "Bucket, split, concatenate, change a type, flatten a hierarchy. Column-level operations. The flatten used for role-hierarchy security lives here."
  - name: "Join"
    type: "MAY MULTIPLY the grain"
    role: "key"
    note: "The dangerous one. A lookup against a one-row-per-key table is safe; joining a one-to-many relationship multiplies rows. Always count before and after."
  - name: "Aggregate"
    type: "COARSENS the grain"
    role: "measure"
    note: "Collapses many rows into one per group. This is the fix for fan-out when applied before a join, and it is also how you produce pre-summarised datasets deliberately."
  - name: "Output"
    type: "writes the dataset"
    role: "key"
    note: "Names the dataset, chooses its app, and is where you should write the grain into the description. A recipe can have several outputs, which is how one pipeline feeds a detailed dataset and a summary one."
---
::

## The pattern you will use constantly

**Aggregate, then join back.** Almost every "I need a count of X on each Y" is this shape:

::lesson-steps
---
items:
  - title: "Branch the many side"
    description: "Take opportunities as an input in their own branch, separate from accounts."
  - title: "Aggregate it"
    description: "Group by AccountId; produce count of opportunities, sum of amount, max of close date — whatever the account row actually needs."
  - title: "Join back to the one side"
    description: "Join that aggregate onto accounts by AccountId. It is now one row per account on both sides, so the join cannot multiply."
  - title: "Check the count"
    description: "140 accounts in, 140 accounts out. If it is not 140, the aggregate did not collapse the way you assumed, and you have found the problem before it reached a dashboard."
---
::

::tip{icon="i-lucide-eye"}
**Use the node preview constantly, not occasionally.** Every node shows its output. Clicking through the chain and watching the row count at each step is the fastest debugging tool in the product, and it makes a grain change impossible to miss — the number changes in front of you, at the exact node responsible.
::

## Joins: know which kind you chose

- **Lookup / left** — keeps every row on the left, adds columns from the right where a match exists. Non-matching rows keep the left values and get nulls. This is the usual choice.
- **Inner** — keeps only rows matching on both sides. Legitimate, and the quiet cause of "records are missing": an opportunity whose account was filtered out earlier silently disappears.
- **Outer variants** — keep non-matching rows from one side or both, filling gaps with nulls.

::warning{icon="i-lucide-scissors"}
**An inner join is a filter wearing a join's clothes.** It removes rows, and it does so at a point where you are thinking about adding columns rather than removing records. When rows are missing and permissions check out, the next suspect is an inner join upstream.
::

## Keep recipes small

There is no hard node ceiling, and there is a practical one. Past roughly twenty nodes a recipe stops being readable by anyone who did not write it, and failure stops localising — you can no longer tell which third of the pipeline broke.

::note{icon="i-lucide-split"}
**Split on meaning, not on size.** A clean base dataset produced by one recipe, and two derived datasets produced by others reading it, is easier to reason about *and* faster to fix than one long chain. The cost is another schedule to order correctly — which, given the dependency trap from the previous lesson, is a cost worth taking seriously rather than ignoring.
::

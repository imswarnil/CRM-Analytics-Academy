# Hands-On: Assigning Access

Hora de poner los conceptos a trabajar. Esta lección es un camino práctico Salesforce **Configuración** — comprobar la configuración de Analytics, inspeccionar cómo un usuario real está autorizado y autorizado, y luego **construir un nuevo set de permiso de alcance** desde cero. Abra su org de desarrollador gratuito y siga adelante.

## Paso 1 - Compruebe la configuración de Analytics

Empieza en **Configuración → Quick Find → Análisis → Configuración**. Aquí es donde confirmas que la org está lista. Dos cosas que vale la pena notar aquí:

- **Filas utilizadas** — CRM Analytics tiene un límite de data-row, y esta página muestra cuánto de él ha consumido. Vigílalo mientras crecen tus conjuntos de datos.
- **Comienzo** — enlaces y toggles que confirman la analítica está habilitado y apuntan al Studio.

Un vistazo rápido aquí le dice que la plataforma está activada antes de comenzar a asignar acceso.

## Paso 2 - Inspeccione el acceso de un usuario

Ahora ve. **Configuración → Usuarios** y abrir un usuario que ya tiene análisis. En su registro de usuario verá las dos capas de antes en esta sección, lado a lado:

::lesson-cards

    icon: "i-lucide-key-round"
    description: "El CRM Analytics (G)Tableau CRM) Además PSL que da derecho al usuario, y posiblemente una licencia de aplicación como Sales Analytics junto a ella."
  - title: "Ejecuciones establecidas por permiso"
    icon: "i-lucide-shield-check"
    description: "El permiso establece capacidades reales. El conjunto de administración predeterminado tiene la mayoría de las permisiones del sistema de análisis preseleccionados."

Abrir el **Permisos del sistema** de ese set de permiso de administración predeterminado y verás casi todos los permisos de análisis — Gestionar análisis incluidos — ya comprobados. Eso es lo que parece un administrador completo. La mayoría de tus usuarios no deberían parecer nada así.

## Paso 3 - Construir un conjunto de permisos

Ahora el ejercicio real: crear un **nuevo, ajustado sistema de permiso** para un constructor de tableros dashboard diarios — alguien que debe construir y ver análisis, pero no debe tocar la plomería de datos.

::lesson-steps
---
items:
  - title: "Crear el conjunto de permisos"
    description: "En Configuración → Juego de permisos, haga clic en Nuevo, darle un nombre claro como CRMA Dashboard Builder, y guardar."
  - title: "Permisos del sistema abierto"
    description: "Dentro del nuevo set, abra la sección Permisos del Sistema y haga clic en Editar para elegir capacidades analíticas."
  - title: "Conceder las capacidades diarias"
    description: "Habilitar \"Use Analytics\", la capacidad de descargar y utilizar paneles de control y el permiso para crear aplicaciones y paneles."
  - title: "Retengan a los riesgosos"
    description: "Deje OFF la capacidad de agregar conexiones de datos y editar flujos de datos —los pertenecen a administradores, no constructores."
  - title: "Guardar y asignar"
    description: "Guardar el conjunto de permisos, luego utilizar Gestion Assignments para asignarlo al usuario objetivo (que ya debe mantener el PSL)."
---
::

El resultado es un usuario que puede crear aplicaciones, construir y descargar dashboards, y explorar datos — pero **no** añadir conexiones o alterar los flujos de datos. Eso es menos privilegio en acción, y es exactamente el tipo de conjunto que entregará con más frecuencia en un despliegue real.

::tip{icon="i-lucide-lightbulb"}
Nombre de los permisos abarcados se establece después de **función** representan — "CRMA Dashboard Builder", "CRMA Viewer", "CRMA Data Engineer". Futuro-usted (y cada administrador que hereda la org) le agradecerá cuando es obvio lo que cada conjunto es para.
::

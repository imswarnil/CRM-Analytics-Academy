# El Usuario de Seguridad & Row-Level Security

Junto al Usuario de Integración, CRM Analytics naves una segunda cuenta especial: el **Usuario de seguridad**. Tiene un trabajo estrecho pero importante, y —como el Usuario de Integración— nunca debe eliminarlo. Esta lección explica sus dos roles y los utiliza para introducir una de las ideas más poderosas de la plataforma: **seguridad de nivel de filas**.

La seguridad El usuario existe para hacer exactamente dos cosas:

::note{icon="i-lucide-shield-alert"}
**No borre o desactive el Usuario de Seguridad** Tampoco. Si pierde el acceso a los campos de usuario en los que dependen sus predicados, la seguridad de nivel de fila puede romper silenciosamente y los usuarios pueden ver demasiadas filas —o ninguna en absoluto.
::

## Lo que la seguridad de nivel de fila es realmente

Imagina que dos personas abren el mismo dashboard en el mismo momento. **I** correrlo y ver **1.000 hileras**; **Tú** correrlo y ver **2.000 hileras**. Nada sobre el tablero cambió - lo que cambió es *quién* está corriendo. Eso es **seguridad de nivel de filas**: la plataforma filtra las filas de un conjunto de datos por usuario, basado en quiénes son.

El mecanismo detrás de él es un **de seguridad** — una regla de filtro adjunta a un conjunto de datos que se evalúa **en tiempo de consultas** contra el usuario en ejecución. Un predicado puede decir cosas como "Mostrar sólo filas donde el propietario del registro es igual al usuario en ejecución" o "Mostrar sólo filas para la región del usuario en ejecución". Debido a que se ejecuta a tiempo de consulta, el mismo conjunto de datos sirve diferentes secciones a diferentes personas automáticamente.

::tip{icon="i-lucide-filter"}
Un predicado de seguridad es evaluado fresco en cada consulta, para quien la está ejecutando. Es por eso que un conjunto de datos puede servir con seguridad a un representante que sólo debe ver sus cuentas y un vicepresidente que debe ver toda la región, sin construir conjuntos de datos separados.
::

## Donde la seguridad El usuario entra

Para evaluar un predicado, CRM Analytics tiene que leer atributos sobre los **usuario** — su id de usuario, papel, región, equipo o cualquier otro campo en el **Objeto de usuario**. Lee esos campos **como el Usuario de Seguridad**. Es precisamente por eso que el Usuario de Seguridad necesita acceso al objeto Usuario: es la cuenta que busca "¿quién es esta persona y cuáles son sus atributos?" para que el predicado pueda filtrar en consecuencia.

## El campo de usuario personalizado gotcha

Puedes construir un predicado **cualquier campo en el objeto Usuario** - campos estándar como `UserId` y `Role`, o su propio **personalizado Campos de usuario** (por ejemplo, una costumbre) `Region__c` o `Team__c`). Pero hay una captura que refleja el Usuario de Integración:

::note{icon="i-lucide-triangle-alert"}
Si tu predicado hace referencia a un **campo personalizado en el objeto Usuario**, el **Seguridad El usuario debe haber leído el acceso** a ese campo. Miss esto y el predicado no pueden leer el valor, y la seguridad de nivel de fila no se filtrará correctamente.
::

## Dos usuarios especiales, un patrón

Observe la simetría a través de esta lección y la última. Tanto el Usuario de Integración como el Usuario de Seguridad son cuentas de sistema que debe mantener vivo, y ambos comparten el mismo campo personalizado Gotcha: **Los campos estándar funcionan automáticamente, pero los campos personalizados necesitan acceso de lectura explícito.** Internar ese patrón y dos categorías enteras de errores de configuración desaparecen.

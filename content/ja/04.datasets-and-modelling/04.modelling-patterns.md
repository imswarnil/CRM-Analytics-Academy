# モデリングパターン

CRM Analytics 倉庫ではなく、そのデータセットはスタースキーマではありませんが、同じ形状が再発され、それらを認識することで、各々の冗談からあなたを救うことができます。

## 事実と参照

::field-table
---
dataset: "the two roles"
grain: "one row per role"
fields:
  - name: "Fact tables"
    type: "things that happened"
    role: "measure"
    note: "機会, リード, ケース, 使用法, セッション. 多くの行、対策と日付と鍵を運ぶ。 あなたが集約するものです。"
  - name: "Reference tables"
    type: "things that are"
    role: "dimension"
    note: "口座、商品、担当者、キャンペーン 行数、属性を運ぶ。 ラベルとグループ化を取得するには、それらに参加します。1つのものをまとめるのは、ほぼ常に間違いです。そして、アカウントテーブルのARRカラムは、属性と測定の両方であるため、立形トラップです。"
---
::

::warning{icon="i-lucide-alert-triangle"}
**実際のテーブルに参照テーブルを結合することは安全です。逆のマルチプライズ。** あらゆる機会にアカウントのセグメントを持たせることで、チャンスを掴むことができます。 各アカウントの行にすべての機会を持たない場合、アカウントの ARR を合計すると、そのアカウントの取引カウントによってそれを乗算できます。 前回からのファンアウトです。
::

## 広いversus長い

複数のメトリクスを1つのエンティティティごとに保持する方法:

::compare-cols
---
items:
  - title: "ワイド"
    subtitle: "One column per metric"
    icon: "i-lucide-table-columns"
    pros:
      - "Natural for charts — pick the column you want"
      - "Obvious to read in a table preview"
      - "Fine when the metric list is short and stable"
    cons:
      - "A new metric means a schema change and a rebuild"
      - "Charting many metrics together needs one widget per column"
    verdict: "Default for a small, settled set."
  - title: "ロング"
    subtitle: "One row per entity per metric"
    icon: "i-lucide-rows-3"
    pros:
      - "New metrics are new rows, not schema changes"
      - "One widget can chart any metric, chosen by a filter"
      - "Natural fit for a metric-toggle binding"
    cons:
      - "Every query must filter to a metric, and forgetting sums unrelated things together"
      - "Harder to read raw"
    verdict: "Right when metrics are added often."
---
::

::note{icon="i-lucide-alert-circle"}
**長いフォーマットの失敗は壮観で、サイレント:メトリック間でまとめる。** 1つのメトリクスにフィルターを忘れるクエリは、コンバージョン率にカウントを処理し、数を返すために収益を追加します。 エラーなし。 長い場合は、各ウィジェットのベースクエリのメトリックフィルタ部分を、各ビルダーを信頼するのではなく、覚えておいてください。
::

## 誘導層

レシピは、別のレシピの出力を読むことができます。 GTMエンジニアリングセクションの倉庫が使用するパターンは、いくつかの目的のビルドされたものを供給するクリーンなベースデータセットを取得する方法です。

::lesson-steps
---
items:
  - title: "チェーンの浅い保つ"
    description: "ベース、それから派生しました。 3つまたは4つのリンクが深くなり、スタート時の失敗は最後に見えないので、どのレイヤーが間違った番号を導入したかは誰も言うことができません。"
  - title: "ヘッドルームでスケジュールを注文する"

    description: "データセットが何であるかを言う接頭辞 - ベース、レポート、exec - 彼らが探しているチェーンで、他のプロパティはありません。"

## ブリッジテーブル

機会と製品、キャンペーン、リード、参加テーブルの2つの事柄が多々あるとき *お問い合わせ* あなたが尊敬しなければならない穀物。

`opportunity_products.csv` Namilio の: 1,378 列ブリッジ 677 機会と 6 製品. どのクエリに対しても、行の穀物でもあります。そのため、取引のカウントは異なるカウントと親の対策は要約されなければなりません。 視力でブリッジテーブルを認識 — ほとんどのキーであるテーブル — 何かを書く前に、そのすべてを伝えます。

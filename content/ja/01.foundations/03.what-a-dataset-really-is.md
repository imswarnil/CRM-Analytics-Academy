# データセットが本当にあること

データセットはテーブルのように見え、決定のように振る舞います。 このレッスンは決定次第です。

## 、住んでいない材料化されて

レシピを実行すると、そのソースを読み、その作業を行い、 **新しいコピーを書く** データの内にある CRM Analytics' 独自のカラムストア。 コピーはデータセットです。 次の実行までは、レコードが削除されたときではなく、レコードが削除されたときではなく、リポジトリが機会を編集したときには変更されません。

::note{icon="i-lucide-clock"}
**「番号が間違っている」の調査は同じ質問から始まります。この最後の実行はいつですか?** Data Manager's Monitorタブには回答があり、調査全体である程度の3分の1程度です。 それは回避策ではありません - 失礼は、設計財産であり、5つのソースに参加し、数百万行を2秒以内に集計する能力のために取引されています。
::

データセットが持つ最も有用なプロパティも生成します。 ザ・オブ・ザ・ Salesforce Opportunity オブジェクトを保持する **最近の投稿** 量と量 **最近の投稿** ステージ; メモリがない。 データセットは毎週実行され、毎回現在の状態を追加し、オブジェクトがあなたに与えることができない歴史を蓄積します。そのため、データセットとモデリングセクションのARRの滝がすべてで可能であり、なぜそれが主張するのか `arr_snapshots.csv` 現在の状態から返されたものではなく、スナップショットであること。

## 穀物: 1 つの質問

::tip{icon="i-lucide-ruler"}
**正確に1列が表すものは何ですか?** 何かをビルドする前に、すべてのデータセットに尋ね、回答を書き留めます。 分析のほぼすべての誤った数は、尋ねられなかった穀物の質問です。
::

Namilioの表は、穀物として述べています。

::field-table
---
dataset: "Namilio — grain of each table"
grain: "one row per table"
fields:
  - name: "accounts.csv"
    type: "one row per account"
    role: "dimension"
    note: "140行 参照テーブル: 参加してみると、ほとんどまとめられません。 ここで何かを召し上がることは、ほぼ常に間違いです。"
  - name: "opportunities.csv"
    type: "one row per opportunity"
    role: "fact"
    note: "677 列。 ここに住んでいる量は、一度契約します。 これは、収入が正しい穀物です。"
  - name: "opportunity_products.csv"
    type: "one row per opportunity per product"
    role: "fact"
    note: "1,378 行 — 1 回につき約 2 回 親にALSOをマウントする。 これら2つの注意を払って、Namilioの$ 58Mは$ 14Mになります。"
  - name: "usage_monthly.csv"
    type: "one row per month per account per product"
    role: "fact"
    note: "2,616行。 穀物の3次元。 何も言わずに、答えは間違いではなく意味がありません。"
  - name: "arr_snapshots.csv"
    type: "one row per month per account"
    role: "fact"
    note: "1,579行 同じアカウントは18回、月1回、各行はその月に関する声明を表示します。 全行でALRを召喚すると、18年間の収益が生まれます。"
  - name: "platform_health_daily.csv"
    type: "one row per day per product"
    role: "fact"
    note: "3,244行、アカウントキーなし 顧客ではなく、プラットフォームについて「当社」と答える点は、すべてのアカウントに結合することはできません。"
---

## ファンアウト、高価な1

2つのテーブル、対人関係、合計。 5分以内に起こり、個々の番号が適度に見えるため、レビューを存続させます。

::funnel-viz
---
stages:
  - label: "機会(正しい穀物)"
    value: 677
    note: "金額が1回表示されます。 — $58M 合計"
  - label: "製品ラインを結合した後"
    value: 1378
    note: "各契約の金額は、すべての製品行に繰り返されます"
  - label: "収益報告"
    value: 1378
    note: "≈ $114M. 何も誤って、何も警告しません。"
caption: "ナミリオ、間違った穀物で接合"
scale: "linear"
---
::

修正は巧妙ではありません: **参加する前に多くの側面を集計するか、親の対策を遂行しない。** セクション 3 は、両方の方法と RevOps セクションをビルドして、それを習慣にします。 ここで重要なのは、症状を認識することです。総体はおよそ2×、3×、または期待する複数のラウンドです。

::warning{icon="i-lucide-search"}
**言う。** グループ化を追加すると、グループ化が問題を引き起こしていない場合、それは *明らかにする* お問い合わせ 重複は既に存在していた。グループ化は、別々のバケットで表示される重複行を作った。
::

## 寸法、測定、日付

CRM Analytics フィールドを3つに分類し、フィールドができることを決定します。

- **ディメンション:** — グループまたはフィルタリングによるもの。 テキスト、通常。 `Segment`, `Region`, `StageName`すべてのID
- **測定値** — あなたが集約する何か。 数字。 `Amount`, `Quantity`, `UsedUnits`お問い合わせ
- **日程表** — 日付は、日付フィルター、月間グループ化、トレンドラインを可能とするものです。

::note{icon="i-lucide-alert-circle"}
**誤りを2つ入力すると、リアルタイムにコストがかかります。** テキストとして読み込まれた日付は、テーブルで細かく見え、範囲でフィルタリングしたり、月ごとにグループ化したり、リロードすることを意味します。 数値表示 ID は、測定値としてタイプされているため、製品が喜んでまとめるようになります。 `AccountId`結局、誰かがオファーを受け入れます。 ロード時の寸法にIDを強制し、その合計を望んでいません。
::

## データセットは、コンテナではなく決定される

ケリドではなくデータセットが組み込まれているため、誰かがその穀物、その結合、そのフィルタ、およびその分野を選択します。 これらの選択肢は、疑問がそれに答えられるかどうかを決定し、それはそうではありません。倉庫とは異なり、後で賢明なクエリでそれらをエスケープすることはできません。

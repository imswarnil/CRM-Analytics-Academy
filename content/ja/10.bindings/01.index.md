# ビンディングとは

同じデータセットのウィジェット間でフェーティングが行われます。 ツイート **バインディング** ウィジェットの状態を別のウィジェットのクエリ、タイトル、または可視性に1つのウィジェットの状態を配線します。

::note{icon="i-lucide-link"}
**精神モデル: 結合は何かを読み、どこかに書きます。** ビューアが何を読んでいるか *選択する* ウィジェット、またはクエリ *フィードバック*別のウィジェットのクエリ、そのタイトル、またはそれがすべて表示されているかどうかに書き込む。 このセクションのすべては、それらの2つの半分の組み合わせです。
::

## 2種類

::compare-cols
---
items:
  - title: "選択の結合"
    subtitle: "Reads what the viewer picked"

    pros:
      - "Responds to interaction, which is what most people mean by a binding"
      - "Powers dynamic titles and dependent filters"
      - "Predictable — the input is visible on screen"
    cons:
      - "Needs a defined behaviour when nothing is selected"
    verdict: "Start here. Most useful bindings are these."
  - title: "結果の結合"
    subtitle: "Reads what a query returned"
    icon: "i-lucide-database"
    pros:
      - "One widget can use another's computed value — a total, a max, a top category"
      - "Enables comparisons the click interface cannot express"
    cons:
      - "The input is invisible; debugging means tracing a query you cannot see on screen"
      - "Creates an execution order between widgets"
    verdict: "Powerful, and the first thing to suspect when a dashboard is slow."
---
::

## 当然のことながら、

::warning{icon="i-lucide-network"}
**ウィジェットの設定でバインディングはロジックに保存されます。** 一見読めないし、差分しないし、誰も見ない。 彼らの20のダッシュボードは、その作者のために美しく機能し、誰のためにも触れられないようになります。次の人は何かが何かを破るのを見ることができますが、なぜか、彼らはそれを横に新しいダッシュボードを構築します。 これは、組織が4つのパイプラインダッシュボードで終わる方法と、それが正しいことに関する引数です。
::

この管理可能なルール: **もしバインディングが画面を見ては明らかでないなら、それを下に書きます** — ダッシュボードの説明では、バインディングごとに1行、何をフィードするか、なぜ。

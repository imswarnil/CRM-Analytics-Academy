# Hands-On: Namilio を締める

所要時間 1つのデータセット、 1つの述語、 1つのテストユーザー、および3つの結果は、実際のorgでこれを行う前に確認する必要があります。

---
dashboard: "Account Base Overview, secured"
audience: "A regional sales rep, and their director"
question: "Which accounts in MY region hold our ARR?"

cadence: "Same as the dashboard; the predicate applies to every query"

## シンタックスは、一般的なスタンブルだから

```
'Region' == "$User.Sales_Region__c"
```

**シングルクォート** データセットの列をラップします。 **二重引用符** user 属性をラップします。 asymmetry は、構文が値とは別にカラムを指示し、それを逆転させるのは、少なくとも一度に行われるエラーです。

条件を組み合わせる `||` または `&&` と:

```
'Region' == "$User.Sales_Region__c" || "$User.Sales_Region__c" == "ALL"
```

::warning{icon="i-lucide-spell-check"}
**正確に文字列を比較します。** `EMEA`, `emea` そして、 `EMEA ` トレイルスペースは3つの異なる地域です。 述語が何も返されず、構文が正しい場合は、列の異なる値とユーザーレコードの値をプリントし、それらを文字で比較します。 これは空白のフィールドの後、2番目の最も一般的な原因であり、それは壊れたルールと同じです。
::

## ここでユーザー属性とプロダクションの階層がなぜなのか

このレッスンは、メカニズムが見えるように、ユーザーレコードのフィールドを使用します。1つの列、1つの比較、1つの場所が誤ったときに見えるようにします。

ほとんどの生産のorgsは、代わりにロール階層を望んでいます。管理者は、何百人ものユーザーで地域フィールドを維持することなく、すべてを見ている。 つまり、データの準備セクションの材料であるレシピのフラットなノードが必要です。 メカニズムは同じです。 プレジデントの列だけが変更と比較しています。

::tip{icon="i-lucide-notebook-pen"}
**4行目を書きます。** どのデータセットが述語っているか、それぞれが英語で書かれているか、免除されているか、そしてフォールバックが何であるか。 今日は2分かかりますし、誰がorgを継承するための週を保存します - おそらくあなたは、忘れました。
::

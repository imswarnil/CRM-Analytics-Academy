# 共有の継承

述語は、書くと維持するルールです。 **継承の共有** お問い合わせ Salesforce 代わりに質問:このビューアは、CRMで既に見ることができるレコードに対応する分析行を表示します。

::tip{icon="i-lucide-link-2"}
**なぜこれはそれが収まる強いデフォルトです。** ルールの共有変更 Territoriesは再編成され、チームが再編成され、誰かが新しいマネージャーを取得します。 手書きの述語は、そのどれも聞いていません。それは、昨年の構成、正しく、目に見えないように、誰かが気づくまで強制し続けます。 Inheritance は構造によって一直線にとどまります。なぜなら、モデルと分析はコピーするのではなく、それを読んでいるからです。
::

## それが覆うもの、そしてそれが止まるところ

継承は、対応する分析行に適用される Salesforce レコード。 該当する場合、利用可能な最高の回答です。 ないところ、述語が必要です。

::field-table
---
dataset: "inheritance boundaries"
grain: "one row per case"
fields:
  - name: "Standard CRM objects"
    type: "supported"
    role: "key"
    note: "口座、機会、ケースなど。 現在サポートしているリストを想定するのではなく、リリースの一覧を確認します。時間をかけて成長し、変化し続けるでしょう。"
  - name: "External and uploaded data"
    type: "not covered"
    role: "measure"
    note: "Namilio の Web セッション、マーケティングの支出、SEO キーワードと LLM の可視性がない Salesforce レコードを背後にあるので、継承する共有はありません。 これらは、すべての視聴者に公開されている述語、または審議的な決定を必要とします。"
  - name: "Highly complex sharing"
    type: "falls back"
    role: "dimension"
    note: "共有の詳細が評価できる制限があります。 アクセスが異常に多数のルールを上回るユーザーで、フォールバックがオプションでない理由であるFALLBACKは、彼らが見るものを決定します。"
  - name: "Aggregated rows"
    type: "needs thought"
    role: "measure"
    note: "レシピがセグメントごとに毎月の合計に集約されると、列は1レコードに応答しません。 相続性は、取り付けることができません。 所有権を識別するキーを保持するか、このデータセットが異なるように保護されていることを承諾するか、そのデータを書き込みます。"
---

## フォールバックは設計決定です

継承がビューアで評価できない場合は、フォールバック述語が引き継ぎます。 システムを圧力の下で振る舞う方法を選ぶことです。

::compare-cols
---
items:
  - title: "制限的なフォールバック"
    subtitle: "Show nothing when unsure"
    icon: "i-lucide-lock"
    pros:
      - "Cannot leak — an edge case shows an empty screen"
      - "The failure is visible and gets reported quickly"
      - "The right default for anything sensitive"
    cons:
      - "A senior person with complex access may see nothing, which is a confusing first impression"
    verdict: "Default to this. Be ready to explain it."
  - title: "従順なフォールバック"
    subtitle: "Show more when unsure"
    icon: "i-lucide-unlock"
    pros:
      - "No confusing blank screens"
      - "Fine for genuinely non-sensitive data"
    cons:
      - "The failure is invisible, and it fails in the leaking direction"
      - "Nobody reports seeing too much"
    verdict: "Only with a written decision behind it."
---
::

::warning{icon="i-lucide-alert-octagon"}
**あまり見ていないレポートはありません。** 過度に制限されるルールは、一日中サポートチケットを生成します。 過度なものはすべてで何も生成します。, それが発見されていない誰かによって発見されるまで. つまり、非対称性は、制限的なフォールバックのための全引数であり、それは「空白の画面で人々を混乱させない」ので、設計レビューで大声を出して言う価値があります間違った選択のための正直に合理的な議論です。
::

## それを書いて下さい、一度

短いメモ — 4 または 5 行 — どのデータセットがどのメカニズム、フォールバックが何であるか、誰が免除され、なぜなのかを使用するかを言う。

つまり、最も有用なアーティファクトは、 CRM Analytics メトリック定義後のプロジェクト。 それなしで、オーガニを継承する最初の人は、設定画面からセキュリティモデルをリバースエンジニアリングする週を費やし、その後何かを変更するためには、理解できない。

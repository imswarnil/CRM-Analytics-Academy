# Rendement

Un tableau de bord qui prend douze secondes est un tableau de bord que les gens arrêtent d'ouvrir. Les causes sont peu nombreuses et les correctifs sont principalement structuraux plutôt que intelligents.

## Compter les requêtes, pas les widgets

Chaque widget est alimenté par une requête. Plusieurs widgets peuvent en partager un — et quand ils ne le font pas, un écran avec douze widgets émet douze requêtes.

::tip{icon="i-lucide-merge"}
**C'est le plus grand levier disponible, et il est généralement gratuit.** Un numéro de manchette, un diagramme à barres et un tableau montrant la même mesure tranché trois façons fréquemment *peut* partager une seule requête. La consolidation est souvent la différence entre douze secondes et deux, et elle ne change rien à la façon dont le tableau de bord ressemble ou se comporte.
::

## Le commerce des céréales

La section 3 indique que le grain d'un ensemble de données est une décision. Voici où vous payez pour cela:

::compare-cols
---
items:
  - title: "Céréales fines"
    subtitle: "Every row preserved"
    icon: "i-lucide-microscope"
    pros:
      - "Any question is answerable from it"
      - "One dataset serves many dashboards"
    cons:
      - "Every widget aggregates a lot of rows, on every load, for every viewer"
      - "Fan-out risk is handed to every designer who touches it"
    verdict: "Right for exploration, expensive for an exec board."
  - title: "Préagrégation"
    subtitle: "Summarised in the recipe"
    icon: "i-lucide-box"
    pros:
      - "Fast — the aggregation happened once, overnight"
      - "The definition is settled upstream, so nobody can compute it differently"
    cons:
      - "Questions below the chosen grain are no longer answerable"
      - "Another dataset to schedule and maintain"
    verdict: "Right for a dashboard many people open daily."
---
::

::note{icon="i-lucide-layers"}
**La réponse de production normale est les deux.** Un jeu de données à grain fin pour l'exploration, et un pré-agréglé derrière le tableau de bord tout le monde s'ouvre. L'entrepôt de la section d'ingénierie GTM est construit de cette façon délibérément : les tables que vous explorez ne sont pas toujours celles que lit le conseil d'administration.
::

## Les autres causes, dans l'ordre brut

::field-table
---
dataset: "what makes dashboards slow"
grain: "one row per cause"
fields:
  - name: "Too many distinct queries"
    type: "most common"
    role: "measure"
    note: "Douze widgets chacun fonctionnant leur propre. Consolider ce qui peut partager, et le changement est invisible pour les utilisateurs sauf que la page apparaît."
  - name: "Aggregating fine grain at query time"
    type: "common"
    role: "measure"
    note: "Des millions de lignes résumées par widget par charge. Pré-agrégation dans la recette si le tableau de bord est ouvert quotidiennement par beaucoup de gens."
  - name: "Very wide tables"
    type: "common"
    role: "dimension"
    note: "Une table de valeurs avec vingt colonnes et des centaines de lignes est lente à requêter et illisible de toute façon. La découper en cinq colonnes et dix lignes corrige les deux problèmes à la fois."
  - name: "Complex bindings"
    type: "occasional"
    role: "dimension"
    note: "Les liaisons enchaînées peuvent forcer les requêtes séquentielles plutôt que parallèles : le widget C attend B, qui attend A. Il vaut la peine de vérifier quand un tableau de bord est lent d'une manière qui ne correspond pas à son nombre de widget."
  - name: "Row-level security evaluation"
    type: "structural"
    role: "key"
    note: "Prédices et surtout partage d'héritage coûtent quelque chose par requête par visualisateur. C'est un coût correct, pas un défaut — mais c'est une raison pour laquelle un tableau de bord est plus lent pour un spectateur avec un accès complexe que pour vous."
---
::

## Comment le mesurer réellement

::lesson-steps
---
items:
  - title: "Chargez-le comme un utilisateur normal, pas comme vous-même"
    description: "Votre compte admin peut sauter l'évaluation de sécurité qu'un vrai spectateur paie pour chaque requête. L'évaluation de la performance en tant qu'administrateur peut la sous-estimer considérablement."
  - title: "Regardez quels widgets arrivent en dernier"
    description: "Ils rendent comme leurs requêtes reviennent, donc les lentes s'annoncent. Habituellement, c'est la table la plus large et le graphique à grains fins."
  - title: "Compter les requêtes distinctes"
    description: "La liste de requêtes du tableau de bord les montre. S'il y a plus de questions que de questions véritablement distinctes à l'écran, il y a une consolidation à faire."
  - title: "Fixer la structure avant l'intelligence"
    description: "Consolider les requêtes, couper les colonnes de table, pré-agréger si nécessaire. Ce n'est qu'alors qu'on considère quelque chose d'exotique — et si la réponse exige de l'intelligence, le tableau de bord en fait probablement trop."
---
::

::warning{icon="i-lucide-hourglass"}
**Les tableaux de bord lents échouent tranquillement.** Personne ne dépose un ticket disant "Cela prend onze secondes". Ils l'ouvrent moins, puis ils vous demandent le numéro à la place, puis ils gardent leur propre table de calcul — et le table de calcul n'est pas d'accord avec le tableau de bord, c'est ainsi qu'un org se retrouve avec deux vérités. Au moment où quelqu'un se plaint, le tableau de bord a déjà perdu.
::

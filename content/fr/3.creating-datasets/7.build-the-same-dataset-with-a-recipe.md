# Construire le même ensemble de données avec une recette

Construisons la **exactement la même** dataset d'opportunités — Opportunité + Compte + Utilisateur — mais avec un **recette** Cette fois. Les recettes sont le moteur moderne de préparation des données: glisser-déposer, visuel, et beaucoup plus flexible qu'un flux de données. Le compromis est que *vous* possèdent les relations. Dataset Builder a trouvé l'objet suivant et les clés de jointure pour vous; dans une recette vous décidez ce qui rejoint à quoi, et comment.

## Démarrer une nouvelle recette

De Analytics Studio, **Créer un ensemble de données →** et choisissez à partir de vos ensembles de données ou objets de synchronisation — cela ouvre une **recette** dans le Data Manager (Flux de données) & Recettes → **Recettes** → nouvelle recette).

Dans la recette, **Sélectionner les données** montre tout ce qui est disponible pour vous : les ensembles de données que vous avez créés, les sources externes et les objets connectés/sync Salesforce. Prenez les mêmes trois... **Possibilités**, **Compte**, **Utilisateur**.

::tip{icon="i-lucide-list-checks"}
Première différence réelle Dataset Builder: vous pouvez **Tout sélectionner** champs par objet au lieu de les cliquer un par un — un énorme chronomètre sur des objets larges. Mais ne le fais pas. Si un objet a plus de 150 champs, vous n'avez pas besoin de tous; un ensemble de données trop large est malheureux à défiler et plus lent à requêter. Apportez seulement ce dont le tableau de bord a besoin.
::

Cliquez sur **Suivant** et vous atterrissez dans la toile de la recette — vos trois objets assis là, **non connecté**. C'est la différence fondamentale: dans une recette, les connecter est votre travail.

## Joindre les objets

Les règles sur les céréales s'appliquent toujours: **Les possibilités sont les plus faibles**Tout s'y joint.

::tip{icon="i-lucide-triangle-alert"}
C'est la taxe sur les recettes, et ça vaut la peine d'internaliser : **il sélectionne automatiquement une clé de jointure, et il peut choisir la mauvaise.** Pour le propriétaire vous avez besoin `OwnerId → User.Id`Pas `Opportunity.Id → User.Id`. Vous devez *connaître vos objets* Assez bien pour l'attraper. Dataset Builder ne vous aurait jamais laissé commettre cette erreur — c'est la sécurité que vous échangez contre le contrôle.
::

## Contrôlez vos colonnes

Les recettes vous donnent un véritable contrôle sur les colonnes de sortie :

- **Type de joint** — élargir le nœud de jointure pour choisir **recherche** contre une adhésion complète. (Nous avons couvert pourquoi cela compte dans la leçon de grain; gardez-les comme des recherches ici.)
- **Préfixes** — les champs du Compte entrent `Account.Name`, `Account.Industry`Et ainsi de suite. Vous pouvez renommer ces préfixes afin que les colonnes finales lisent comme vous voulez.
- **Conserver ou déposer** — prévisualiser les colonnes entrantes et **cacher** ceux dont vous n'avez pas besoin pour qu'ils n'atteignent jamais la sortie. Trim `User.` champs jusqu'au nom du propriétaire et de la photo, par exemple.

## Ajouter le noeud de sortie

Voici l'étape que les gens oublient : **rien n'existe comme un jeu de données utilisable jusqu'à ce que vous ajoutiez un noeud de sortie (registrer).** Les jointures seules ne produisent rien que vous pouvez mettre sur un tableau de bord.

## Même résultat, moteur différent

Quand il se termine, vous avez les mêmes possibilités de données — construit par un **recette** lecture à partir des mêmes objets synchronisés, au lieu d'un flux de données. Deux moteurs, un résultat.

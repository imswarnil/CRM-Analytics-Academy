# Les REST API

Salesforce expose l'analyse à travers REST API: ensembles de données, requêtes, tableaux de bord et métadonnées derrière eux.

## Authentification

Les demandes portent un jeton d'accès OAuth, obtenu par une application connectée. Deux points pratiques sont plus importants que la mécanique :

::lesson-steps
---
items:
  - title: "Utiliser un utilisateur d'intégration dédié"
    description: "Pas une personne. Une personne quitte, son compte est désactivé, et chaque travail qui s'est authentifié comme ils s'arrête un jour que personne ne prédit. Un compte d'intégration nommé avec seulement les permissions dont il a besoin rend également une piste de vérification significative."
  - title: "Gardez vos lettres de créances dans un magasin secret"
    description: "Les variables d'environnement d'un magasin géré, d'un coffre-fort ou du stockage secret du fournisseur de l'IC. Jamais dans le script, jamais dans un cahier, jamais dans le dépôt — et une repo publique rend cela irréversible plutôt que gênant."
  - title: "Manipulation de l'expiration du jeton comme opération normale"
    description: "Les jetons expirent, c'est le dessin. Un emploi qui meurt du jour au lendemain sur un jeton expiré est un emploi qui n'a pas mis en œuvre de rafraîchissement. Supposons qu'une course peut s'étendre sur une expiration."
  - title: "Donnez à l'utilisateur d'intégration seulement ce dont il a besoin"
    description: "Un chargeur doit écrire des ensembles de données, pas lire chaque objet de l'org. Les permissions restreintes limitent le rayon d'explosion d'un titre de compétence divulgué, et elles rendent évident le but du travail."
---
::

## Versionnement

Endpoints portent une version dans le chemin. Pince-la.

::note{icon="i-lucide-pin"}
**Une version épinglée est un script qui continue de fonctionner lorsque la plate-forme met à jour, et un non épinglé est un script qui change le comportement sur une date que quelqu'un d'autre a choisi.** Mettre à jour délibérément : modifier la version, courir contre un bac à sable, confirmer la forme de la réponse est ce que vous attendez, puis expédier. C'est une habitude de deux minutes qui empêche la classe d'échec où rien dans votre dépôt n'a changé et le travail a de toute façon cassé.
::

## Limites de conception

Chaque plate-forme les a et les nombres spécifiques se déplacent, de sorte que le conseil durable est sur la forme plutôt que les chiffres:

::compare-cols
---
items:
  - title: "Formes à l'échelle"
    subtitle: "Work with the limits"
    icon: "i-lucide-check"
    pros:
      - "Batch — one call with many rows rather than many calls with one"
      - "Incremental — send what changed, not everything, every night"
      - "Back off and retry on a rate-limit response rather than hammering"
      - "Check the current limits for your edition before sizing anything"
    cons:
      - "More code than the naive version"
    verdict: "Write it this way from the start."
  - title: "Formes qui échouent à l'échelle"
    subtitle: "Fine in a test, not in production"
    icon: "i-lucide-x"
    pros:
      - "Simple, and works beautifully against 100 rows"
    cons:
      - "A call per row exhausts the daily allowance and starves everything else in the org"
      - "A full reload every night when 2% of rows changed"
      - "No retry, so one transient error loses the whole run"
    verdict: "This is how an analytics job takes down an org's API budget."
---
::

::warning{icon="i-lucide-gauge"}
**API les limites sont larges.** Un travail d'analyse cupide ne se ralentit pas seulement : il consomme des avantages que les intégrations, les clients mobiles et d'autres équipes tirent également parti. Ce qui fait d'un chargeur mal façonné un problème opérationnel pour les personnes qui n'ont jamais entendu parler de votre tableau de bord, et c'est la raison pour lot avant que quelqu'un vous demande.
::

# Concevoir un ensemble de données

Commencez par les questions, pas par les tableaux. Les tableaux vous indiquent ce qui est possible; les questions vous disent quoi construire.

## La conception à quatre questions

::lesson-steps
---
items:
  - title: "Écrivez les questions qu'il doit répondre"
    description: "Cinq ou six, en langage clair. 'Quels segments tiennent notre ARR.' Quelles sont les affaires les plus longues ? Si vous ne pouvez pas les énumérer, vous construisez une copie d'une table source plutôt qu'un ensemble de données."
  - title: "Dériver le grain de la meilleure question"
    description: "Si une question concerne des transactions individuelles, le grain est une ligne par transaction. S'ils sont tous environ des totaux mensuels par segment, il peut être une ligne par segment par mois — et il sera beaucoup plus rapide."
  - title: "Énumérez les colonnes dont chaque question a besoin"
    description: "Dimensions par groupe, mesures par ensemble, dates par tendance. Tout ce qui ne répond pas à une question énumérée est un candidat à abandonner : chaque colonne supplémentaire coûte du temps et rend la liste des champs plus difficile à lire pour la prochaine personne."
  - title: "Décider ce qui est définitivement exclu"
    description: "Les dossiers de test, les comptes internes, une gamme de produits sur laquelle personne ne fait de rapport. Si une ligne ne doit jamais apparaître dans une réponse donnée par cet ensemble de données, filtrez-la ici plutôt que de demander à chaque tableau de bord de se souvenir."
---
::

## Filtre dans l'ensemble de données ou sur le tableau de bord ?

  - name: "On the dashboard"
    type: "exploratory"
    role: "dimension"

::

::warning{icon="i-lucide-filter-x"}
**Un filtre dans l'ensemble de données est invisible pour tout le monde en aval.** C'est sa valeur et son risque : un analyste conciliant votre ensemble de données avec la source trouvera une différence et n'aura aucun moyen de voir pourquoi. Placez chaque filtre de niveau dataset dans la description de l'ensemble de données — 'exclut les comptes de test et l'org interne du bac à sable' — ou vous serez interrogé à plusieurs reprises sur l'écart.
::

## Un ou deux ensembles de données ?

La tentation est toujours d'élargir l'actuel. Deux signaux que vous devriez diviser à la place:

::compare-cols
---
items:
  - title: "Séparer"
    subtitle: "Different grain, or different purpose"
    icon: "i-lucide-split"
    pros:
      - "Each is simple enough to reason about"
      - "The daily dashboard gets a fast pre-aggregated dataset while exploration keeps the detail"
      - "One recipe can produce both outputs, so the logic is still defined once"
    cons:
      - "Two things to schedule and monitor"
    verdict: "Usually right when the grains genuinely differ."
  - title: "Élargir"
    subtitle: "Add columns to the existing one"
    icon: "i-lucide-move-horizontal"
    pros:
      - "One thing to maintain"
      - "Fine when the new questions live at the same grain"
    cons:
      - "A dataset serving everybody eventually serves nobody well"
      - "Sixty columns of which fifteen matter is hostile to self-service"
    verdict: "Right only while the grain and purpose still match."
---
::

::tip{icon="i-lucide-git-branch"}
**Deux sorties d'une recette sont l'option sous-utilisée.** Les jointures, le nettoyage et les définitions arrivent une fois; la recette écrit ensuite un ensemble de données détaillé et un ensemble agrégé. Vous obtenez la vitesse où il importe et le détail où il est nécessaire, sans deux copies de la logique s'écartant.
::

## Écrivez le grain dans la description

Chaque ensemble de données, une phrase: *une rangée par opportunité par produit*. C'est cinq secondes de travail et la chose la plus utile que l'on lit en aval — la différence entre un collègue qui résume la bonne colonne et un duplicata sans jamais le savoir.
